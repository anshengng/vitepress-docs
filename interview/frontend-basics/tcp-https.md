# TCP 三次握手/四次挥手与 HTTPS

## 题目

> 画出 TCP 三次握手的过程和双方状态变化，为什么是三次而不是两次或四次？四次挥手呢，TIME_WAIT 为什么要等 2MSL？HTTPS 的握手流程是怎样的？为什么用"非对称加密交换密钥 + 对称加密传数据"的混合方案？数字证书和证书链是怎么被校验的？

## 为什么需要

面试里"从输入 URL 开始"的每道题都会路过 TCP/TLS，它们是连接层的两大基石：

- **TCP** 解决"两个进程之间如何可靠地建立/拆除字节流"——握手是**双方各确认一次"我能发、你能收"**，挥手是**双向各自优雅地关半边**。
- **HTTPS** 解决"公网裸奔的 TCP 之上如何加密与验明正身"——在 TCP 和 HTTP 之间插一层 TLS。

```
打电话类比：
三次握手 = 我："喂，听得到吗？" → 你："听到了，你听到我了吗？" → 我："听到了，开聊"
          （每人既验证了"我说得出"，也验证了"对方听得进"，3 轮刚好互证闭环）
四次挥手 = 我先说"我说完了" → 你"收到" → （你继续讲完）→ 你"我也说完了" → 我"收到，挂线"
          （说话是双向独立通道，关闭也必须一边一边来，所以 4 步）

HTTPS 类比：
非对称加密 = 公开挂锁：谁都能锁上箱子，只有店主有钥匙能开
对称加密   = 同一把钥匙开门：快，但钥匙必须先安全送到对方手里
混合方案   = 先用挂锁把"对称钥匙"锁着送过去，之后全程用对称钥匙开箱
```

## 核心要点

### 1. 三次握手状态机

SYN=同步序列号，ACK=确认。seq 随机初始是为了防历史连接混淆。

```
        客户端                                    服务器
     CLOSED                                   LISTEN
        │  ① SYN  seq=x                       │
        ├────────────────────────────────────►│
   SYN_SENT                              SYN_RECEIVED
        │  ② SYN+ACK  seq=y, ack=x+1          │
        │◄────────────────────────────────────┤
        │  ③ ACK  ack=y+1                     │
        ├────────────────────────────────────►│
    ESTABLISHED                          ESTABLISHED
        │            可以传数据了               │
```

**为什么不是两次？** 两次握手中服务器收到 SYN 就进入 ESTABLISHED 并分配资源，但服务器无法确认"自己发的包客户端收得到"。更致命的是**历史滞留 SYN**：网络里迟到的旧连接请求会让服务器白白建立半连接，客户端根本不认，造成资源浪费甚至 SYN 洪水放大。

**为什么不是四次？** 服务器的 SYN 和 ACK 可以合并成一个报文（②），信息量不丢；拆成四次只是浪费一轮往返。

### 2. 四次挥手与 TIME_WAIT

```
     主动关闭方                              被动关闭方
     ESTABLISHED                          ESTABLISHED
        │  ① FIN  seq=u                       │
        ├────────────────────────────────────►│
      FIN_WAIT_1                        CLOSE_WAIT
        │  ② ACK  ack=u+1                     │   ← 对方可能还有数据要发完
        │◄────────────────────────────────────┤      （CLOSE_WAIT 停在应用没调 close）
        │  ③ FIN  seq=w                       │
        │◄────────────────────────────────────┤
     TIME_WAIT                            LAST_ACK
        │  ④ ACK  ack=w+1                     │
        ├────────────────────────────────────►│
     （等 2MSL）                            CLOSED
        │
        ▼
     CLOSED
```

- **为什么四次**：TCP 全双工，两个方向要分别关。② 只确认"你不再发了"，被动方自己可能还有剩余数据要发，FIN 只能等发完再单独来（③），不能和 ACK 合并。
- **TIME_WAIT 等 2MSL 的两大理由**：① 保证最后的 ACK 能到达——ACK 丢了，对方 LAST_ACK 超时重发 FIN，主动方还在 TIME_WAIT 才能重新应答；② 让本次连接的"幽灵报文"在网络中自然消亡，不会污染复用同一四元组的新连接。
- 面试加分：大量短连接做客户端会堆积 TIME_WAIT，常见解法是**长连接/连接池**（HTTP keep-alive 正是其一）。

### 3. HTTPS = HTTP + TLS 握手

TLS 1.2 经典流程（1.3 简化为 1-RTT，去掉 RSA 密钥交换、强制前向保密的 ECDHE）：

```
TCP 已建立
   │
   ├─ ClientHello ────────────────────────►│  客户端支持的 TLS/密码套件版本 + 随机数 C
   │◄──────────────── ServerHello ─────────┤  选定套件 + 随机数 S
   │◄──────────────── 证书(含公钥) ────────┤  服务器证书链
   │◄──────────────── ServerHelloDone ─────┤
   │  ① 校验证书链（见第 5 小节）            │
   │  ② 生成预主密钥 premaster，用公钥加密   │
   ├─ ClientKeyExchange(加密的 premaster) ─►│
   │  ③ 双方用 C+S+premaster 算出会话密钥    │
   ├─ Finished(对称加密) ──────────────────►│  ④ 之后全部用对称密钥加密通信
   │◄──────────────── Finished ────────────┤
   ▼
应用层：HTTPS 请求/响应（对称加密的字节流）
```

### 4. 为什么"非对称换密钥 + 对称传数据"

| | 非对称加密（RSA/ECDHE） | 对称加密（AES） |
| --- | --- | --- |
| 密钥 | 公钥公开，私钥保密 | 双方共享同一把密钥 |
| 速度 | 慢（大数运算，约慢 2~3 个数量级） | 快（硬件 AES-NI） |
| 密钥分发 | 公钥天然可广播 | **怎么把密钥安全送出去？** |
| 数据量 | 只适合加密小数据 | 适合海量数据 |

```
矛盾：对称快但密钥没法送；非对称能送但太慢。
解法：各取所长——握手期用非对称（或 ECDHE 协商）
     只加密/协商一把"会话密钥"，
     数据传输期全程用这把对称密钥。

若全程非对称：每字节都做大数运算 → 性能灾难
若全程对称  ：会话密钥裸奔在网络上 → 等于没加密
```

追问点：ECDHE 相比 RSA 密钥交换的优势是**前向保密**——私钥日后泄露也无法解密历史流量，因为会话密钥是临时椭圆曲线对协商出来的，用完即弃。

### 5. 证书链校验：公钥从哪来可信

问题根源：公钥本身可能被中间人替换（拿假公钥加密=白搭）。证书 = **CA 用它的私钥对"域名+公钥+有效期"做的数字签名**。

```
服务器下发： [ 叶子证书(站点公钥) ] ← 由 [ 中间 CA ] 签名
             [ 中间 CA 证书 ]      ← 由 [ 根 CA ] 签名
             根证书预装在操作系统/浏览器信任库

浏览器校验链：
  ① 用内置"根 CA 公钥"验"中间证书"的签名 ── 通过 → 中间公钥可信
  ② 用"中间公钥"验"叶子证书"的签名       ── 通过 → 站点公钥可信
  ③ 检查叶子证书的域名 == 当前访问域名、有效期、未被吊销(OCSP/CRL)
  ④ 此后才放心用叶子公钥加密 premaster

信任本质：把"信任一个陌生公钥"递归收敛为"信任系统预置的少数根 CA"
```

没有 HTTPS 的裸 HTTP 风险三件套：**窃听**（明文）、**篡改**（无完整性校验）、**冒充**（无身份验证），TLS 分别用加密、MAC/AEAD、证书解决。

## 面试答法

### 30 秒版（可背诵）

> 三次握手：客户端 SYN，服务器 SYN+ACK，客户端 ACK，双方各完成"我能发、你能收"的互证；两次不行是因为服务器无法确认客户端收得到、且会被历史 SYN 建立无效连接，四次多余是因为服务器的 SYN 和 ACK 可以合并。四次挥手：FIN→ACK→FIN→ACK，因为 TCP 全双工要逐方向关闭；主动方 TIME_WAIT 等 2MSL 是为了重发最后的 ACK 和让旧报文在网络中消亡。HTTPS 是 HTTP 加 TLS：握手时客户端拿到服务器证书，校验证书链后用公钥保护协商出会话密钥，之后数据全走对称加密——非对称负责"安全地送钥匙"，对称负责"快速地开箱子"。证书链把对陌生公钥的信任递归到系统预置的根 CA。

### 深入版（被追问时按编号展开）

1. **画握手状态机**：标出 SYN_SENT / SYN_RECEIVED / ESTABLISHED 与 seq/ack 变化
2. **两次/四次之辩**：两次=服务器单方确认+历史 SYN 问题；四次=SYN+ACK 合并无信息损失
3. **挥手与 TIME_WAIT**：逐方向关闭 + 2MSL 两理由 + 长连接缓解
4. **TLS 握手图**：ClientHello→证书→密钥交换→Finished，标出随机数 C/S/premaster 三者算会话密钥
5. **混合加密对比表**：速度/密钥分发/数据量三行讲清"各取所长"
6. **证书链递归校验**：根→中间→叶子逐级验签，再查域名/有效期/吊销
7. **加分收尾**：TLS1.3 的 1-RTT、ECDHE 前向保密、QUIC 基于 UDP 重做可靠传输

### 常见追问

- **SYN 洪水是什么，怎么防？** → 伪造大量 SYN 占满半连接队列；SYN Cookie（不存状态、用 cookie 算法在第三次握手时还原验证）
- **CLOSE_WAIT 堆积说明什么？** → 被动方应用没调 close，对端已 FIN 而我方 socket 泄漏——通常是代码 bug 或线程池耗尽
- **为什么证书里要放公钥而不是直接传公钥？** → 裸传可被中间人替换；证书=CA 签名过的公钥，替换后验签失败
- **自签证书浏览器为什么报警？** → 它的签名链收敛不到任何受信根 CA，第①步验签失败
- **TLS1.2 和 1.3 握手区别？** → 1.3 砍掉 RSA 交换与多余往返，常见 1-RTT 甚至会话恢复 0-RTT，算法收敛到 AEAD+ECDHE
- **HTTPS 一定比 HTTP 慢吗？** → 多 1~2 个 RTT 握手，但会话复用/HTTP2 多路复用摊薄后，传输阶段对称加密开销在现代 CPU 上可忽略
