# Web 性能优化

## 题目

> 从用户输入 URL 到页面渲染出来，整个链路哪些环节可以优化？你项目里做过什么性能优化，效果怎么衡量？

## 为什么需要

页面加载是一条流水线，任何一段堵住，用户看到的都是白屏或卡顿。**背一堆零散的优化点，不如按链路串成体系**——面试按链路答，天然有框架感。

```
用户感受的"慢"            链路上的真实原因
──────────────         ──────────────
白屏半天          ←→    DNS 慢 / 建连远 / HTML 太大 / JS 阻塞解析
内容跳来跳去      ←→    图片字体后到 / 没留占位（CLS）
一点就卡          ←→    长任务霸占主线程 / 频繁回流重绘
```

## 核心要点

### 一、总览：输入 URL 到页面可见的全链路（每环节标优化手段）

```
输入 URL
  ▼
┌────────────┐  dns-prefetch / preconnect 提前解析、HTTP3(QUIC) 自带缓存
│ ① DNS 解析  │
└────────────┘
  ▼
┌────────────┐  CDN 就近接入、减少重定向、HTTP/2 多路复用、TLS 会话复用
│ ② 建立连接  │
└────────────┘
  ▼
┌────────────┐  强缓存+协商缓存、Gzip/Brotli 压缩、SSR 首屏直出
│ ③ 请求响应  │
└────────────┘
  ▼
┌────────────┐  CSS 放头部 / JS 用 defer·async 不阻塞、骨架屏、HTML 瘦身
│ ④ HTML 解析 │
└────────────┘
  ▼
┌──────────────────┐  CSS 拆分按需加载、关键 CSS 内联
│ ⑤ CSSOM+Render树 │
└──────────────────┘
  ▼
┌────────────┐  减少回流重绘、transform/opacity 走合成层、虚拟列表
│ ⑥ 布局+绘制 │
└────────────┘
  ▼
┌────────────┐  requestAnimationFrame 批量改、长任务拆分、懒执行
│ ⑦ 合成上屏  │
└────────────┘
```

### 二、网络层

| 手段 | 一句话原理 |
| --- | --- |
| HTTP/2 | 同一连接多路复用，消灭 HTTP/1 的按序排队（队头阻塞） |
| Brotli/Gzip | 传输前压缩，文本体积砍 60%~80% |
| CDN | 静态资源放边缘节点，RTT 从几百 ms 降到几十 ms |
| 强缓存 + 协商缓存 | Cache-Control 免请求；ETag 协商 304 只传状态码 |
| 资源提示 | dns-prefetch、preconnect 提前"暖"连接 |

缓存判定流程：

```
请求 → 本地缓存未过期？─是─► 直接用（200 from cache，零网络 ⚡）
                     └─否─► 带 ETag 问服务器
                            ├─ 没变：304，用本地副本
                            └─ 变了：200，下载新资源
```

### 三、资源层

| 手段 | 做什么 |
| --- | --- |
| 懒加载 | 图片 `loading="lazy"`、路由 `() => import()`、首屏外内容 IntersectionObserver |
| 图片优化 | WebP/AVIF 替代 JPG（小 30%+）、srcset 按屏幕出图 |
| 代码分包 | 路由级 chunk、组件库按需引入（babel-plugin-import） |
| Tree-shaking | ESM 静态结构让打包器删掉没用的导出 |
| 压缩混淆 | Terser/ESbuild minify + 去注释 + 变量名缩短 |

### 四、渲染层

**回流(reflow) vs 重绘(repaint)**

| 对比 | 回流 | 重绘 |
| --- | --- | --- |
| 触发 | 几何变化：宽高、位置、display:none | 外观变化：颜色、背景、visibility |
| 成本 | 高：重算布局 + 重画 | 低：只重画像素 |
| 关系 | 回流必引发重绘 | 重绘不一定回流 |

```
改 width ────► 回流 ──► 重绘 ──► 合成   （最贵 💰）
改 color ─────────────► 重绘 ──► 合成   （中等）
改 transform ──────────────────► 合成   （最便宜 ⚡ 走 GPU）
```

**transform 为什么便宜：合成层**

```
普通元素：每次改动 → 主线程重新布局+绘制 → 提交纹理 → 合成器
提升为合成层（transform: translateZ(0) / will-change）：
        ┌─ 主线程：只算一次，生成独立图层 ──┐
动画期间│  主线程在忙别的也照样流畅 🎉      │
        └─ GPU 合成器：只挪图层位置 ────────┘

动画优先用 transform: translate/scale/rotate + opacity
（这两个属性不碰布局和绘制）
```

**虚拟列表**（一句话）：只渲染视口内的几十条 + 上下缓冲，滚动时换数据不换 DOM，十万条也不卡。

### 五、JS 层

| 手段 | 场景 | 一句话 |
| --- | --- | --- |
| 防抖 debounce | 搜索框输入、表单校验 | 停下来才执行最后一次 |
| 节流 throttle | 滚动监听、resize | 固定频率执行 |
| 长任务拆分 | 大数据处理 | 切成 <16ms 的片，配合 requestIdleCallback/setTimeout 让出主线程 |
| Web Worker | 纯计算（解析大文件） | 把计算挪出主线程 |

```
不拆：主线程 ████████████ 200ms 长任务 → 期间点击无响应 ❌
拆分：主线程 ██ ██ ██ ██ ██ 每片 <16ms → 中间穿插处理用户事件 ✅
```

### 六、框架层

- Vue：`keep-alive` 缓存组件实例（切回来不重建）、`v-show/v-if` 按切换频率选、路由懒加载
- React：`memo` + `useMemo/useCallback` 减少无效重渲染（另有专篇）
- 通用：SSR/SSG 首屏直出 HTML、骨架屏安抚等待情绪

### 七、衡量指标（有数据才算优化）

| 指标 | 全称 | 是什么 | 良好目标 |
| --- | --- | --- | --- |
| FCP | First Contentful Paint | 首次出现任何内容 | < 1.8s |
| LCP | Largest Contentful Paint | 主内容（大图/大标题）就绪 | < 2.5s |
| CLS | Cumulative Layout Shift | 布局累计偏移（页面跳不跳） | < 0.1 |
| TTI | Time to Interactive | 可流畅交互的时间 | < 3.8s |
| INP | Interaction to Next Paint | 交互到下一帧响应（新核心指标） | < 200ms |

工具：Lighthouse 体检、DevTools Performance/Network 定位、web-vitals 库线上采集真实用户数据。

## 面试答法

### 30 秒版（可背诵）

> 我习惯按"输入 URL 到页面可见"的链路来答。网络层用 HTTP2、Brotli 压缩、CDN 和强缓存协商缓存，把传输时间压下来；资源层做路由懒加载、图片换 WebP 加懒加载、打包开 tree-shaking 和分包；渲染层重点是减少回流重绘，动画只用 transform 和 opacity 让它们走 GPU 合成层，长列表上虚拟列表；JS 层对输入做防抖、滚动做节流，大计算拆片或丢 Web Worker；框架层 Vue 用 keep-alive 和路由懒加载。最后用 Lighthouse 和 web-vitals 量化，盯 LCP、CLS 这些核心指标，有前后数据才能证明优化有效。

### 深入版（被追问时按编号展开）

1. **先给主线**：一句话报出"我按加载链路讲"，然后 DNS → 建连 → 请求 → 解析 → 渲染 → 交互，逐环节甩手段
2. **渲染层重点展开**：回流 vs 重绘对比表 + transform 合成层图（最容易被追问的点）
3. **讲一个落地例子**：如"项目 LCP 4.2s，排查发现首图 2MB 未压缩 + 接口阻塞渲染，改 WebP + 预加载 + CDN 后降到 1.9s"——有数字有闭环
4. **收在度量**：Lighthouse + Web Vitals，FCP/LCP/CLS/TTI 目标值信手拈来，体现"先测量再优化"的工程习惯

### 常见追问

- **首屏白屏时间长怎么排查？** → Network 看 TTFB（接口慢）和资源体积（资源慢），Performance 看主线程阻塞；对应上 SSR、压缩、懒加载
- **defer 和 async 区别？** → 都异步下载；defer 等 DOM 解析完按序执行，async 下载完立刻执行可能打断解析
- **图片懒加载原理？** → loading="lazy" 或 IntersectionObserver 监听进入视口再赋真实 src
- **什么情况用 SSR？** → 首屏极致要求或 SEO 敏感；代价是服务器成本与部署复杂度
- **CLS 怎么优化？** → 图片视频写死宽高、预留占位、字体 font-display: swap + 兜底字重对齐
