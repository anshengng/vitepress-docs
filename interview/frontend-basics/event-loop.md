# 事件循环（Event Loop）

## 题目

> 描述浏览器的事件循环机制：宏任务与微任务的执行顺序是什么？为什么需要微任务？async/await 在其中怎么表现？

## 为什么需要

JS 是**单线程**：一个调用栈，同一时刻只能干一件事（避免 DOM 操作的线程竞争）。
但定时器、网络、IO 都很慢，同步等会卡死页面 → 只能异步回调 + 任务排队。

生活化例子：柜台只有一个柜员（主线程），客户（任务）多了就取号排队（队列）；
VIP 客户（微任务）不用重新取号，**永远排在本轮结束、下一批普通客户（宏任务）之前**。

## 核心要点

### 一、完整模型图

```
┌───────────────────────────────────────────────┐
│              JS 运行环境（单线程）               │
│                                               │
│  script（同步代码）──► ┌────────┐              │
│                       │ 调用栈  │ ← 一次一个    │
│                       └────────┘              │
│                           ▲                  │
│              微任务队列 ✨ │   │ 宏任务队列      │
│  [Promise.then / then链…  ] │   [setTimeout …] │
│  [queueMicrotask …]        │                  │
│  [MutationObserver …]      │                  │
└─────────────────────────┬─┴──────────────────┘
              回调注册 ▲   │ 到时间/完成后入队
┌─────────────────────┴───┴──────────────────┐
│   Web APIs（浏览器提供，多线程）                │
│   Timer 线程 │ 网络线程 │ DOM 事件线程 │ …      │
└─────────────────────────────────────────────┘
```

关键区别一句话：**微任务本轮必须清完；宏任务每轮只取一个**。

### 二、每轮循环规则（流程图）

```
┌─────────────────────────────────────────────┐
│ ① 执行同步代码，直到调用栈清空                 │
│    ↓                                        │
│ ② 清空【全部】微任务                          │
│    （微任务里再产生微任务也继续清，直到空）        │
│    ↓                                        │
│ ③ 必要时渲染（本轮有 DOM 改动 → 样式/布局/绘制） │
│    ↓                                        │
│ ④ 从宏任务队列取【一个】执行 → 回到 ①           │
└─────────────────────────────────────────────┘

口诀：同步清完 → 微任务清完 → 渲染（可能）→ 再取一个宏任务
```

### 三、为什么需要微任务（插队机制）

宏任务（setTimeout）再短也要等一整轮循环，粒度太粗；
Promise 一旦决议，**结果要尽快响应**（接着发下一个请求、更新状态）。

```
setTimeout(f, 0)          → 排到下一轮：前面还隔着 渲染 + 其他宏任务，慢
Promise.resolve().then(f) → 本轮末尾立刻清，几乎零延迟

只有宏任务的世界：异步链 = setTimeout 套 setTimeout
每一步都要等一轮 → 慢、还总错过渲染时机 → 微任务 = 官方开的"插队通道"
```

### 四、三道经典输出题（由易到难）

**题 1：setTimeout 与 Promise 混合**

```javascript
console.log(1)
setTimeout(() => console.log(2), 0)
Promise.resolve().then(() => console.log(3))
console.log(4)
// 输出：1 4 3 2
```

| 步骤 | 动作 | 输出 |
| --- | --- | --- |
| 1 | log(1) 同步执行 | 1 |
| 2 | setTimeout 注册回调，0ms 后进宏任务队列 | - |
| 3 | Promise 已决议，then 回调进微任务队列 | - |
| 4 | log(4) 同步执行 | 4 |
| 5 | 同步代码完 → 清空微任务队列 | 3 |
| 6 | （可能渲染）→ 取一个宏任务执行 | 2 |

**题 2：async/await 混合**

```javascript
async function a() {
  console.log('a-start')
  await b()                 // b() 同步调用；await 之后 = then 微任务
  console.log('a-end')
}
async function b() { console.log('b') }

console.log('script-start')
setTimeout(() => console.log('timeout'), 0)
a()
Promise.resolve().then(() => console.log('p1'))
console.log('script-end')
// 输出：script-start a-start b script-end a-end p1 timeout
```

| 步骤 | 动作 | 微任务队列 | 输出 |
| --- | --- | --- | --- |
| 1 | log('script-start') 同步 | 空 | script-start |
| 2 | 调 a()：同步跑到 await b()，b 函数体当场执行完 | 空 | a-start、b |
| 3 | await 让出线程：a-end 之后的代码包成微任务挂起 | [a-end] | - |
| 4 | 继续同步：注册 then p1 | [a-end, p1] | - |
| 5 | log('script-end')，同步代码完 | [a-end, p1] | script-end |
| 6 | 清微任务：a-end → p1 | 空 | a-end、p1 |
| 7 | （可能渲染）→ 取宏任务 timeout | 空 | timeout |

**题 3：嵌套 setTimeout + 微任务插队**

```javascript
setTimeout(() => {
  console.log('T1')
  Promise.resolve().then(() => console.log('P1'))
}, 0)
setTimeout(() => console.log('T2'), 0)
// 输出：T1 P1 T2
```

| 轮次 | 动作 | 输出 |
| --- | --- | --- |
| 初始 | 两个回调按注册顺序入宏任务队列 [cb-T1, cb-T2] | - |
| 宏任务 1 | 取 cb-T1：log(T1)，执行中产生微任务 P1 | T1 |
| 清微任务 | P1 插在"下一个宏任务"之前执行 | P1 |
| 宏任务 2 | 取 cb-T2 | T2 |

关键：**微任务永远赶在下一个宏任务之前清光**，哪怕它是这个宏任务执行中才产生的。

### 五、async/await 的本质

```
async 函数 = 返回 Promise 的函数
await x 之后的代码 ≈ 放进 then 的微任务回调里

async function a() {           Promise.resolve(x).then(() => {
  await x                               /* await 之后的代码 */
  /* 之后的代码 */        ≈             })
}
```

所以 await 一执行就**让出线程**：本函数挂起，本轮同步代码先跑完，
等微任务队列轮到它时再从 await 处继续。

### 六、GUI 渲染时机（宏任务之间）

浏览器按 60Hz 渲染（每帧约 16.7ms）。渲染发生在**两轮宏任务之间**：
宏任务 + 微任务都清完后，检测到 DOM 有变化，才 style → layout → paint。

```
宏任务1 → 清微任务 → [可能渲染 🖼] → 宏任务2 → 清微任务 → [可能渲染] → ...
```

推论：

- 同一个宏任务里改 10 次 DOM → 合并成**一次渲染**
- 微任务里改的 DOM → 本轮渲染前生效（先清微任务再渲染）
- `setTimeout(fn, 0)` 里改的 DOM → 要等下一轮才渲染
- requestAnimationFrame 回调在微任务清空之后、渲染之前执行

> Node.js 的事件循环是分阶段的（timers → poll → check 等），每个阶段之间清微任务，浏览器以宏/微任务模型为主。

### 七、ES6+ 常考特性速览（面经同题追问点）

面经「事件循环和ES6+」是打包问法，讲完事件循环常被要求顺带列举 ES6+ 新特性，按组记不易漏：

| 分组 | 特性 |
| --- | --- |
| 变量与作用域 | `let`/`const` 块级作用域、解构赋值、默认参数、扩展/剩余运算符 `...` |
| 函数与数组 | 箭头函数（不绑定 this）、`find` / `includes` / `flat` 等新数组方法 |
| 数据结构 | `Symbol`、`Set`、`Map`、`WeakMap`/`WeakSet`、`Proxy`/`Reflect` |
| 对象与类 | `class`、模板字符串、迭代器与生成器、`Object.assign` / `Object.entries` |
| 异步与模块 | `Promise`、`async/await`、`import`/`export` 模块化 |

与本节的衔接句：**Promise 和 async/await 正是微任务的来源**——ES6+ 的新异步语法全部挂在事件循环的微任务队列上，这也是"为什么事件循环常和 ES6+ 一起考"的原因。

## 面试答法

### 30 秒版

JS 是单线程，异步任务交给 Web APIs 处理，完成后把回调放进任务队列，队列分宏任务和微任务。事件循环每一轮：先执行同步代码直到调用栈清空，然后一次性清空全部微任务，必要时做一次渲染，再从宏任务队列取一个执行，如此往复。微任务比如 Promise.then，宏任务比如 setTimeout。微任务的意义是插队——Promise 的结果要尽快响应，就让它在本轮末尾清掉，不用排到下一轮宏任务后面。await 之后的代码相当于 then 的微任务，所以 await 会先让出线程。Node 那边是分阶段循环，每个阶段之间清微任务，规则一致。

3. **讲微任务的意义**：插队机制，对比"只有宏任务"的世界有多慢

### 常见追问

- **为什么 then 是微任务、setTimeout 是宏任务？** → 决议结果要尽快消费，微任务让它在循环末尾插队；定时器本来就是"延迟执行"，等一轮不亏
- **requestAnimationFrame 算宏任务还是微任务？** → 都不算，它在微任务清空后、渲染前执行
- **微任务执行中又产生微任务怎么办？** → 追着清，直到队列彻底为空才进入下一轮宏任务
- **await 一个未决议的 Promise 会怎样？** → 函数一直挂起，直到决议后恢复为微任务
- **setTimeout(fn, 0) 是立即执行吗？** → 不是，要等本轮同步 + 微任务清完，浏览器还有 0~4ms 的最小延迟
- **ES6+ 哪些特性和事件循环直接相关？** → Promise.then、async/await（微任务来源），queueMicrotask 可手动入微任务队列
