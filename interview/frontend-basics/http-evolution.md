# HTTP/1.1 → 2 → 3 演进

## 为什么需要

HTTP 版本题的实质是**并发效率演进史**：网页从单一文档变成上百个资源，瓶颈从带宽转移到连接模型。每一版都在消灭上一版的"队头阻塞"——1.1 卡在应用层、2 卡在 TCP 层、3 下沉到传输层重做。面试官的追问链通常是固定的："1.1 解决了什么 → 2 为什么还有队头阻塞 → 3 为什么换 UDP"，能沿这条线讲清因果就是满分答法。

背景知识可交叉参考：[TCP 三次握手与 HTTPS](/interview/frontend-basics/tcp-https)、[HTTP 与 Socket 的区别](/interview/frontend-basics/http-vs-socket)、[HTTP 缓存策略](/interview/frontend-basics/http-cache)。

## 核心要点

### 1. HTTP/1.0：短连接

每个请求-响应完成后**立即关闭 TCP 连接**，下一个资源重新走 TCP 握手（HTTPS 还要再加 TLS 握手，见 [tcp-https](/interview/frontend-basics/tcp-https)）。加载一个页面 = N 个资源 × (TCP + TLS + 请求) 的往返成本。1.0 后期有 `Connection: keep-alive` 头但默认关闭。

### 2. HTTP/1.1：持久连接 + 管道化，应用层队头阻塞

- **持久连接（keep-alive）**：默认开启，多条请求-响应复用同一条 TCP 连接，省掉重复握手。
- 但 1.1 的规则是**严格的一问一答**：上一个响应没回来，不能发下一个请求。浏览器只好并行开 6 条 TCP 连接（RFC 建议值，被各浏览器沿用）来并发加载资源。
- **管道化（Pipelining）**：允许连续发出多个请求不等响应，但**响应必须按请求的顺序返回**：

```
Pipelining:
  连发 req1 req2 req3 ──────────►
  ◄───────── resp1(慢的大图) → resp2 → resp3
                    ↑
        应用层队头阻塞：响应顺序被钉死，一个慢响应堵住后面全部
```

管道化最终没普及（代理兼容性问题、响应顺序约束、错误恢复困难），主流浏览器默认禁用。

**1.1 队头阻塞的本质**：协议把一条连接当成"单一串行队列"，慢请求独占队列，后面的快请求只能排队——堵在**应用层的排队规则**，不关传输层的事。

### 3. HTTP/2：二进制分帧 + 多路复用

核心思想：不再把消息当"整个请求/整个响应"排队，而是拆成**帧（frame）**。每个帧有固定 9 字节头部：长度 + 类型 + 标志 + **流 ID**。同一请求/响应的所有帧共享一个流 ID，帧可以乱序到达，对端按流 ID 重组。

```
HTTP/1.1：开 6 条 TCP 连接绕开串行限制
  conn1: [======CSS======]
  conn2: [=======JS======]
  conn3: [API1][API2]        ← 每条连接内部仍是单队列
  conn4: [======img======]
  （连接数上限、每条都要 TCP+TLS 握手、头部明文重复）

HTTP/2：单条 TCP 连接，多个流的帧交错穿插
  conn1: [f1(s1)][f2(s2)][f3(s3)][f4(s1)][f5(s2)] ...
              │           │
        s1 = CSS 流   s3 = API 流    ← 一个流 = 一次请求/响应的双向帧序列
        帧乱序到达，按流 ID 在端点重组 → 真并发
```

效果：一条连接承载全部资源，没有 6 连接限制，没有重复握手，快响应不再被慢响应拖住（应用层队头阻塞消除）。

另外两个关键点：

- **HPACK 头部压缩**：静态表（61 个常见头部）+ 动态表（双方增量学习本次会话出现过的头部）+ Huffman 编码。重复头部只发一个索引，解决 1.1 每个请求都携带数百字节明文头部的问题。
- **服务器推送（Server Push）**：服务器发 HTML 时主动推送它预判要用的 CSS/JS，客户端缓存起来备用。**已凉**：Chrome 106 起移除支持，规范也被废弃——服务器看不到客户端缓存状态，误推纯浪费带宽；`103 Early Hints` 响应 + `link rel=preload` 覆盖了大部分收益场景。
- 二进制分帧还让解析更健壮：定长头 + 显式长度字段，避免文本协议解析差异导致的请求走私。

### 4. HTTP/2 的遗留问题：TCP 层队头阻塞

流在应用层多路复用了，但底下仍是**一条 TCP 字节流**，而 TCP 承诺全局有序可靠：

```
TCP 字节流: [s1:A][s2:B][s3:C][s2:D]
                      ↑ B 所在分包丢包

TCP 必须按序交付 → C、D 全部阻塞，等 B 重传到位才能继续
→ 流 s3、s2 明明和 B 无关，也被卡死
```

应用层修不了：重传与排序逻辑在内核 TCP 栈里，HTTP/2 无权改写。这就是 HTTP/3 的直接动机。

### 5. HTTP/3：QUIC（基于 UDP）

QUIC 在**用户态重新实现可靠传输**，并把 TLS 1.3 整合进握手过程，传输层 + 安全层一次建好。

- **流级独立重传**：每个流有自己的独立序号空间，s2 丢包只重传 s2 的数据，s1/s3 照常交付——彻底消灭队头阻塞。
- **1-RTT / 0-RTT 建连**：TCP 握手（1 RTT）+ TLS 握手（1~2 RTT）被合并；首次连接 1 RTT 内完成建连+加密协商，重连已知服务器时 0-RTT 直接带数据（代价：重放攻击风险，见追问）。
- **连接迁移**：连接用 **Connection ID** 标识，而不是 TCP 的四元组（源 IP/端口 + 目的 IP/端口）。Wi-Fi 切 4G、IP 变了，QUIC 连接不断，免重连重握手——移动场景刚需。
- 头部压缩改用 **QPACK**：HPACK 的动态表依赖 TCP 的有序交付，QUIC 乱序场景下会失效，QPACK 通过流控解除了这个依赖。

```
QUIC（UDP 之上）:
  stream1: A ──► 正常交付
  stream2: B ✗ 丢包 → 只重传 B
  stream3: C ──► 正常交付（不被 B 拖累）
  stream2: D ──► 正常交付
```

### 6. 版本特性对比表

| 维度 | 1.0 | 1.1 | 2 | 3 |
| --- | --- | --- | --- | --- |
| 传输层 | TCP | TCP | TCP | UDP（QUIC） |
| 连接复用 | 每请求即关 | 持久连接默认开 | 单连接 | 单连接 |
| 并发模型 | 串行 | 管道化（响应顺序固定） | 流多路复用 | 流多路复用 |
| 报文格式 | 文本 | 文本 | 二进制分帧 | 二进制（QUIC 分组） |
| 头部压缩 | 无 | 无 | HPACK | QPACK |
| 队头阻塞 | — | 应用层 | TCP 层 | 基本消除（流级重传） |
| 加密 | 可选 | 可选 | 事实上要求 TLS | TLS 1.3 整合进协议，强制 |
| 建连成本 | TCP(+TLS) | 复用省握手 | TCP+TLS 多次 RTT | 1-RTT / 恢复 0-RTT |
| 网络切换 | — | — | 四元组变即断，需重连 | Connection ID 迁移，不断连 |
| 服务器推送 | ❌ | ❌ | ✅（已废弃） | 不再使用 |

## 面试答法

### 30 秒版本

> HTTP 演进的主线是逐层消灭队头阻塞。1.0 每请求关连接，握手成本高；1.1 引入持久连接和管道化，但响应必须按请求顺序返回，存在应用层队头阻塞，浏览器只能并行开 6 条 TCP 连接绕开。2 改成二进制分帧，把单条连接拆成多个独立流交错多路复用，消除应用层阻塞，加上 HPACK 头部压缩和服务器推送（后者因效果差已废弃）；但流仍叠在 TCP 全局有序字节流之上，一次丢包重传会阻塞所有流，即 TCP 层队头阻塞。3 基于 UDP 的 QUIC 在用户态重做可靠传输：每流独立重传，TLS 1.3 整合进握手实现 1-RTT 甚至 0-RTT 建连，Connection ID 替代四元组让换网络不断线。

### 深入展开

1. **先报背景**：资源数暴涨 → 1.1 的 6 连接限制与明文头部冗余是 2 的动机；管道化"响应顺序固定"就是应用层队头阻塞的定义。
2. **画分帧图**：帧 = 9 字节头（含流 ID）+ 载荷；多流帧交错、乱序重组 → 单连接真并发。
3. **HPACK 一句话**：双方共享静态表 + 动态表，重复头部只发索引；顺带提压缩+加密的侧信道风险（CRIME/BREACH 家族）。
4. **推送之凉**：服务器看不见客户端缓存 → 误推浪费带宽；被 103 Early Hints + preload 取代。
5. **TCP 层队头阻塞画图**：B 丢包 → C、D 排队等重传；强调"应用层改不了内核 TCP 栈"，这是换传输层的根本原因。
6. **QUIC 三件套**：流级独立重传、0-RTT 建连（带重放风险）、连接迁移；QPACK 是 HPACK 的去依赖版。
7. **收尾上对比表**，按"并发模型/队头阻塞/建连成本"三行收束。

### 常见追问

- **为什么 HTTP/2 还用 TCP，而 3 换 UDP？** → 2 要在现有生态（防火墙、负载均衡、操作系统 TCP 栈）上快速部署，只能兼容 TCP；但 TCP 的"全局有序 + 统一重传"是内核实现，用户态改不动，队头阻塞无解。QUIC 干脆在 UDP 上用用户态代码重做可靠传输，才能按流独立排序重传。不是 UDP 比 TCP 好，是 TCP 改不动。
- **TLS 在哪一层？** → 1.1/2：TCP → TLS → HTTP，TLS 是夹在传输层和应用层之间的独立一层；3：TLS 1.3 被整合进 QUIC 握手，建连即加密，第一个分组就是密文，没有"明文 TCP 握手在前"的阶段。
- **服务器推送为什么被废弃？** → 客户端可能已有缓存，服务器无法感知，误推浪费带宽；且推送资源无法被 Service Worker 拦截。Chrome 106 移除，规范撤销，替代方案是 103 Early Hints + preload。
- **0-RTT 有什么风险？** → 恢复会话的数据在服务器验证身份之前就发出，可被攻击者截获重放；因此 0-RTT 数据只用于幂等请求（GET），写操作必须等 1-RTT 确认。
- **HTTP/2 为什么用二进制不用文本？** → 帧头定长、解析 O(1)，没有行边界歧义；文本协议解析差异正是请求走私的温床。分帧本身也需要机器可读的长度/类型字段。
- **HTTP/3 一定比 2 快吗？** → 弱网、高丢包、频繁切网（移动场景）收益显著；优质网络下差距不大，因为瓶颈本来不在协议层。
- **QUIC 怎么实现可靠性的？** → 每个分组有独立序号，每流维护自己的发送/接收窗口，丢包按流重传；拥塞控制在用户态实现，可插拔（默认类 Cubic/BBR 思路）。
