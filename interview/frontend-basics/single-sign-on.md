# 单点登录（SSO）原理

## 题目

> 什么是单点登录？CAS 票据模式的一次登录多系统通行是怎么做到的？多个子域之间怎么共享登录态？用 JWT 怎么实现 SSO？SSO 和 OAuth2 是什么关系？

## 为什么需要

公司有 OA、CRM、ERP 十个系统，用户不该登录十次。SSO 的本质一句话：**把"认证"从每个业务系统剥离到统一的认证中心，业务系统不再自己验密码，只认认证中心发的凭证**。面试考点集中在三处：票据流转的时序（谁跳转、谁验票、浏览器只见到什么）、跨域下 Cookie 的限制与绕行、token 的信任链与注销代价。

类比：游乐园。每个游乐项目（业务系统）不单独查身份证，你在总入口（认证中心）验一次身份、戴上腕带（票据/token），之后每个项目只验腕带真伪——而且验腕带是工作人员对后台核销，不需要你本人再报名字。

## 核心要点

### 1. CAS 票据模式（经典面经流程，必须会画时序）

```
用户          App A                SSO 认证中心              App B
 │ ①访问        │                     │                      │
 ├────────────►│ A 无会话             │                      │
 │  ②302 跳认证中心                    │                      │
 ├─────────────┼────────────────────►│ 认证中心也无登录态     │
 │  ③展示登录页，输入账号密码            │                      │
 │◄────────────┼─────────────────────┤                      │
 │  ④校验通过：认证中心写自己的 Cookie(sso.com 域)              │
 │    发一次性票据 ST-1，302 回 A：https://a.com?ticket=ST-1   │
 ├─────────────┼────────────────────►│                      │
 │             │ ⑤A 后端拿 ST-1 调认证中心校验接口（服务器间）  │
 │             ├────────────────────►│ 验票 → 返回用户身份    │
 │             │◄────────────────────┤                      │
 │  ⑥A 建立自己的会话，用户已登录       │                      │
 │             │                     │                      │
 │ ⑦访问 B      │                     │                      │
 ├─────────────┼─────────────────────┼─────────────────────►│
 │             │                     │ B 无会话 → 302 认证中心│
 ├─────────────┼─────────────────────┼◄─────────────────────┤
 │  ⑧浏览器自动带上认证中心域的 Cookie │                      │
 │    认证中心发现"已登录"→ 免密直接发新票 ST-2，302 回 B       │
 ├─────────────┼─────────────────────┼─────────────────────►│
 │             │                     │ ⑨B 后端验 ST-2 → 建会话│
 │  ⑩用户在 B 也是登录态 ✅（全程没再输密码）                   │
```

三个必讲关键点：
- **票据一次性**：ST 有效期仅几秒~1 分钟、用一次即作废。票据出现在 URL 里会被历史记录/日志记到，短命+单次消费把泄漏风险压到最小
- **验票走服务器间调用**（⑤⑨）：用户身份信息从不经过浏览器，浏览器只见票据
- **第⑧步免密的灵魂**：是"认证中心自己域下的 Cookie"——浏览器跳转时自动附带，认证中心据此认出"这人刚才登录过"

### 2. 跨子域方案：Cookie 的 Domain 提到根域（轻量 SSO）

```
a.example.com 与 b.example.com：同站(site)但不同主机(host)
  Domain=a.example.com 的 Cookie → b 收不到，登录态不共享

把 Cookie 种在根域：
┌────────────────────────────────────────┐
│ Set-Cookie: SSO_TOKEN=xxx;             │
│   Domain=.example.com                  │ ← 所有 *.example.com 都能收到
│   HttpOnly; Secure; SameSite=Lax       │
└────────────────────────────────────────┘
a、b 的请求都自动带同一份 token，后端统一校验 → 等价于共享登录态

局限：只对"同一根域"有效。a.com 与 b.com 完全异域时 Cookie 无法共享，
     必须回到票据（CAS）或 URL 中转 token 的方案
```

### 3. JWT/token 模式（现代主流）

```
登录：客户端 ──账号密码──► 认证中心校验
        ◄── access_token(JWT, 短效~15min) + refresh_token(长效)
使用：客户端带 Authorization: Bearer <JWT> 请求任意业务系统
验证：业务系统用密钥/公钥【本地验签】→ 解出 uid/exp → 不查认证中心（无状态）
续期：access 过期 → 用 refresh_token 静默换新
注销：JWT 签发出去就收不回 → 需要服务端黑名单或极短有效期兜底（无状态的代价）
```

### 4. 三种方案对比

| 维度 | CAS 票据 | 跨子域共享 Cookie | JWT |
| --- | --- | --- | --- |
| 登录态载体 | 一次性票据 + 各系统自己的会话 | 根域共享 Cookie（token/session id） | 自包含可验签的 token |
| 跨域能力 | ✅ 任意域名 | ❌ 仅同根域 | ✅ 放请求头，与域无关 |
| 认证中心压力 | 每次登录都要后端验票 | 依赖共享存储（Redis） | 业务系统本地验签，几乎为零 |
| 注销/吊销 | 容易（服务端会话可删） | 容易 | 难，需黑名单/短有效期 |
| 安全焦点 | 票据一次性 + 后端验票 | Cookie 的 HttpOnly/CSRF | 签名算法、XSS 存储、过期策略 |

## 面试答法

### 30 秒版（可背诵）

> SSO 是"一次登录，多个系统通行"，核心是把认证集中到认证中心、业务系统只信认证中心的凭证。经典 CAS 流程：访问系统 A 没登录就 302 到认证中心，登录成功后认证中心在自己域下写 Cookie、发一个一次性票据 ticket 带 URL 跳回 A，A 的【后端】拿票据找认证中心验出身份、建立自己的会话；之后访问系统 B，B 也跳认证中心，但浏览器自动带上了认证中心域的 Cookie，它认出你已登录，免密再发一张新票给 B 验——全程不再输密码。同根域的多子域可以更简单地共享登录态：把 Cookie 的 Domain 设成根域。现代主流是 JWT：认证中心签发 token，各业务系统本地验签、无状态好扩容，代价是注销难，要靠短有效期加 refresh token 或黑名单。

### 深入版（被追问时按编号展开）

1. **画 CAS 十步时序**：分清"浏览器可见的跳转"和"服务器间的验票"两条线
2. **讲透第⑧步**：免密靠认证中心自己域的 Cookie；票据一次性防 URL 泄漏
3. **跨子域方案**：Domain=.example.com 的原理与"只对同根域有效"的边界
4. **JWT 流程**：access+refresh 双 token、本地验签、无状态
5. **注销难题**：JWT 不可撤回 → 黑名单/短时效，对比 CAS 删会话的容易
6. **三方案对比表**：跨域能力、认证中心压力、吊销难度三行定选型

### 常见追问

- **为什么票据要一次性且短命？** → 它会出现在 URL、历史记录、Referer 里；长效票据泄漏=身份冒用，一次性+秒级有效期把窗口压到最小
- **SSO 和 OAuth2 什么关系？** → OAuth2 解决的是【授权】（第三方应用拿到用户资源的访问权，如"用微信登录"给第三方拿头像）；SSO 解决的是【认证】（你是谁）。OIDC 在 OAuth2 上加了 id_token 身份层，"第三方登录"实际是 OAuth2+OIDC 实现的 SSO
- **JWT 存 localStorage 还是 Cookie？** → localStorage 免疫 CSRF 但挡不住 XSS；HttpOnly Cookie 反过来。实践：短效 token 放内存变量 + refresh 放 HttpOnly Cookie
- **认证中心挂了会怎样？** → 已建立的会话和已签发的 token 仍可用，只影响新登录和验票 → 认证中心要高可用部署 + 业务侧降级策略
- **SameSite 对 SSO 有什么影响？** → 跨站跳回认证中心要带它的 Cookie，SameSite=Lax 下 POST 跳转不带、Strict 下连 GET 外链跳转都可能不带，SSO 常需 SameSite=None+Secure 或走前端跳转
- **单点登录和单点登出？** → 登出更难：认证中心要广播通知各业务系统销毁会话（CAS 有 back-channel 回调），JWT 方案只能靠黑名单
