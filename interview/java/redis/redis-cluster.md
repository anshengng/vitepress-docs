# Redis 主从、哨兵与集群

## 题目

> Redis 主从复制的流程是什么？哨兵怎么实现自动故障转移？Cluster 的 16384 槽位是怎么回事？三种方案怎么选型？

## 为什么需要

单机 Redis 再快也有天花板：

```
                    ┌─────────────────────────────┐
   所有请求 ──────► │        单机 Redis           │
                    │  ① 宕机 → 数据全丢、服务全停  │
                    │  ② 内存再大也就几百 GB → 容量上限 │
                    │  ③ 写 QPS 单机 ~10万 封顶     │
                    └─────────────────────────────┘
```

解决路径是三级演进：**主从复制**（多个副本）→ **哨兵**（副本自动切换）→ **Cluster**（数据分片 + 两者全要）。

## 核心要点

### 主从复制

#### 全量同步（第一次连接 / 断得太久）

```
从库                         主库
 │── PSYNC ? -（第一次，无 runid）──►│
 │                                │ bgsave 生成 RDB 快照（后台，不阻塞写）
 │                                │ 此期间新写命令 → 攒进 repl_backlog 积压缓冲区
 │◄────────── RDB 文件传输 ────────│
 │ 清空自身数据，加载 RDB            │
 │◄───── 积压缓冲区里的增量命令 ─────│
 │ 回放命令，追上主库 ✅             │
```

#### 增量同步（断线重连）

主库每条写命令都同步传播给从库；同时主库把命令流写进 **repl_backlog 环形缓冲区**（定长，旧的会被覆盖）。断线重连时从库带上 `runid + offset`：

```
从库: PSYNC <runid> <offset>
  ├─ offset 还在 backlog 范围内 → 主库只补发缺的那段（部分重传）✅ 便宜
  └─ offset 已被覆盖 / runid 对不上 → 退化为全量同步 ❌ 昂贵
```

#### 两个绕不开的问题

- **异步复制可能丢数据**：主库写完立即回客户端，不等从库确认——主库刚写入还没同步就宕机，这条数据就丢了（生产 `min-replicas-to-write` 只能缓解）
- **读写分离与延迟**：读打到从库，主从同步有毫秒级延迟，「写完立刻读」可能读不到旧值，强一致读要强制走主库

### 哨兵（Sentinel）：自动故障转移

主从有个致命空窗：主库挂了要**人肉**执行 `slaveof no one` 切换。哨兵集群就是为了把这件事自动化：

```
时间线 ──────────────────────────────────────────────────────►

 T1  主库宕机 💀
 T2  【主观下线 sdown】每个哨兵独立 ping 主库，超时单方面标记"我觉得它挂了"
 T3  【客观下线 odown】某哨兵问其他哨兵：你们也觉得挂吗？
      超过 quorum 个哨兵同意 → 官方认定主库下线
 T4  【选举 lead sentinel】哨兵之间投票选出一个执行者（先到 quorum 票者当选）
 T5  【筛选 + 排序选新主】从库中剔除断线的/与主库断开过久的，
      按优先级(replica-priority) → 复制偏移量(越大数据越全) → runid(小者胜) 依次取胜
 T6  其余从库执行 slaveof 新主；旧主恢复后也降级为它的从库
 T7  哨兵通过发布/订阅通知客户端新主地址 ✅ 服务恢复
```

**为什么哨兵至少 3 个且要奇数？** 判断下线、选 leader 都靠"多数派"投票——偶数个（如 4 个）不比 3 个更抗宕机（都是最多挂 1 个还能成多数），反而浪费机器；2 个更不行，一裂脑就无法形成多数。哨兵自身也要部署在不同机器上，否则机器一挂哨兵团灭。

**哨兵的局限**：主从每个实例都存**全量数据**——高可用和读扩展解决了，**容量和写 QPS 上限依旧没解决**。

### Cluster：分片 + 高可用全都要

#### 16384 槽位分片

```
key → CRC16(key) mod 16384 → 槽号(slot) → 槽 belongs to 某个主节点

三主三从的槽位分配：

  节点A(主) ── A'(从)   槽 0 ~ 5460
  节点B(主) ── B'(从)   槽 5461 ~ 10922
  节点C(主) ── C'(从)   槽 10923 ~ 16383

  从库不持槽，只做对应主库的热备；主挂了，从自动顶上（哨兵功能内置了）
```

客户端可以连任意节点，找错人了会收到重定向：

```
客户端 ── GET k（k 属于槽 6789，在节点B）──► 节点A
客户端 ◄─ MOVED 6789 节点B地址 ───────────── 节点A
客户端 ── 重新向节点B发命令 ──────────────►  节点B ✅
（智能客户端本地缓存槽位映射表，绝大多数请求直连，很少发生 MOVED）
```

- **gossip 协议**：节点间不断 ping/pong 交换集群状态（谁在线、槽归谁），无中心元数据服务器
- **为什么是 16384 不是 65536？** 心跳包里要携带自己负责的槽位 bitmap，16384 位 = 2KB 刚好；65536 位 = 8KB 心跳太重，且 Redis Cluster 官方建议不超过 1000 主节点，16384 个槽足够用

#### hash tag：让相关多 key 落同一槽

```
{user1}:order   ┐
{user1}:address ├──► CRC16 只算 "{user1}" 部分 → 同一个槽 → 可用 mget/事务/Lua
{user1}:profile ┘
```

#### Cluster 的限制

| 限制 | 说明 |
| --- | --- |
| 多 key 命令跨槽报错 | mset/mget/事务/Lua 涉及的 key 必须同槽（用 hash tag 解决） |
| 只能用 db 0 | SELECT 命令不可用 |
| 事务/Lua 受限 | key 不同槽无法保证原子 |
| 不支持复杂运维 | 某些客户端命令在集群模式表现不同 |

### 三级方案选型表

| 方案 | 解决什么 | 没解决什么 | 适用 |
| --- | --- | --- | --- |
| 主从复制 | 数据热备、读扩展 | 主挂了要人工切换 | 小团队、能接受手动切换 |
| 哨兵 + 主从 | + 自动故障转移（高可用） | 容量、写 QPS 上限 | 数据量单机放得下 |
| Cluster | 高可用 + 水平扩容全都要 | 多 key 跨槽受限 | 数据量/写入超单机（默认生产选择） |

## 面试答法

### 30 秒版（可背诵口语）

> Redis 单机有宕机丢数据、容量上限、写 QPS 上限三个问题，方案分三级。主从复制：从库第一次全量同步走 RDB 加积压缓冲区回放，之后命令异步传播；断线重连时按 runid 和 offset 判断，offset 还在积压缓冲区里就部分重传，否则全量。主从是异步复制可能丢数据，且主挂了要人工切换，所以加哨兵：哨兵集群先主观下线再 quorum 客观下线，选一个 leader 哨兵，从库里按优先级、偏移量选新主，哨兵要奇数个至少三个，因为投票靠多数派。哨兵解决不了容量问题，所以有 Cluster：16384 个槽用 CRC16 取模分给多个主节点，找错节点返回 MOVED 重定向，节点间用 gossip 同步状态，多 key 操作用 hash tag 保证同槽。选型就是：数据单机放得下用哨兵，放不下才上 Cluster。

### 深入版（被追问时按这条线展开）

1. **破题**：单机三大风险（宕机/容量/写 QPS）引出三级演进
2. **主从**：全量流程五步 → 增量靠 repl_backlog → 断线判定逻辑
3. **哨兵**：sdown → odown → 选 leader → 选新主 → 通知，画时间线；解释奇数原因
4. **Cluster**：槽位图 → MOVED 流程 → 16384 的权衡 → hash tag → 限制表
5. **收尾**：抛选型表，体现"够用就好，Cluster 有代价"的工程判断

### 常见追问

- **全量同步时主库还能写吗？** → 能。bgsave 在后台，期间的写命令攒在 repl_backlog，RDB 发完再补
- **主从复制怎么做的？** → 见上文全量/增量流程；注意是**异步**的，存在丢数据窗口
- **脑裂了解吗？** → 旧主没真挂（网络抖动）时哨兵已选新主，客户端分裂写两个主，恢复后旧主数据被清空重同步 → 丢写。缓解：`min-replicas-to-write` 让主库从库不足时拒绝写
- **客户端怎么知道槽位映射的？** → 启动时拉取集群拓扑缓存在本地，收到 MOVED/ASK 时更新
- **ASK 和 MOVED 什么区别？** → MOVED：槽已永久迁走，请更新映射；ASK：槽迁移中的临时重定向，本次去新节点执行但映射不变
- **Cluster 什么情况下会整体不可用？** → 某段槽的所有主从都下线（如 A 和 A' 同时挂），整个集群报错——所以主从不要同机部署
