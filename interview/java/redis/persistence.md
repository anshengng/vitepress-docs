# Redis 持久化：RDB 与 AOF

## 题目

> Redis 有哪些持久化方式？RDB 和 AOF 的原理、优缺点和选型？

## 为什么需要持久化

先想清楚 Redis 为什么快，才能理解它持久化的全部设计约束：

```
客户端 ──命令──► Redis 主线程（单线程）
                   │ ① 纯内存操作：读写不碰磁盘，微秒级
                   │ ② 单线程：无锁竞争、无线程切换，不用考虑并发改同一份数据
                   │ ③ IO 多路复用（epoll）：一个线程监听海量客户端连接
                   ▼
                命令串行执行
```

代价：数据全在内存，进程重启 / 机器断电 → **全丢**。持久化要在"不拖慢内存操作"的前提下把数据落盘：

```
快  ◄───── RDB（粗粒度快照，丢得多）── AOF（细粒度日志，丢得少）─────► 安全
                        混合持久化 = 两头兼得（4.0+，生产主流）
```

## 核心要点

### RDB：定时全量快照（bgsave）

```
主进程                                fork 出的子进程
  │                                        │
  ├── fork() ─────────────────────────────►│ 拿到与主进程"同一份"内存视图
  │   （fork 极快：只复制页表，不拷贝数据）   │
  │   继续接客，读写命令照常执行              ├── 遍历全量数据
  │   （对主进程的阻塞只有 fork 一瞬间）      ├── 生成紧凑二进制文件 dump.rdb
  │                                        └── 写完 exit，通知主进程
```

fork 后父子进程**共享同一批内存页**，靠 **COW（Copy-On-Write 写时复制）** 做到"快照冻结在 fork 那一刻，同时主进程还能继续写"：

```
fork 瞬间：共享全部内存页，一个字节都不复制
  父进程页表                     子进程页表
    页A ────► [物理页A] ◄──── 页A     ← 两边页表指向同一页
    页B ────► [物理页B] ◄──── 页B

父进程改到哪页，内核才复制哪页：
    页B ══复制══► [新页B']   ← 父进程此后读写 B'
                  [旧页B]    ← 子进程快照仍读旧值 → 快照数据永远一致
```

### RDB 优缺点

| 优点 | 缺点 |
| --- | --- |
| 二进制文件紧凑，恢复时直接载入，**恢复快** | 两次快照之间的数据**全丢**（分钟级窗口） |
| 干活的是子进程，主进程基本无感 | fork 有瞬时阻塞；大内存实例复制页表也吃 CPU |
| 单文件，易备份、易跨机传输 | **COW 极端风险**：快照期间所有页都被改 → 内存占用最多翻倍 |

### AOF：追加写命令日志

```
客户端 ──写命令──► 主线程执行
                    │ ① 命令执行成功后，追加命令文本到内存缓冲区 aof_buf
                    ▼
                 aof_buf（内存缓冲区）
                    │ ② 按 appendfsync 策略调用 fsync 刷盘
                    ▼
                 appendonly.aof 文件
恢复 = 把文件里的命令从头到尾重放一遍（所以恢复比 RDB 慢）
```

三种刷盘策略对比：

| appendfsync | 机制 | 最多丢 | 性能 | 一句话 |
| --- | --- | --- | --- | --- |
| always | 每条命令都 fsync | 1 条 | 最慢 | 最安全，磁盘压力大，很少用 |
| everysec（默认） | 后台线程每秒 fsync 一次 | 1 秒 | 好 | 安全与性能的折中 ✅ |
| no | 只写 buf，何时落盘交给 OS | 约 30 秒 | 最快 | 不可控，不推荐 |

### AOF 重写（bgrewriteaof）：日志越滚越大怎么办

`set k 1` 执行 100 次，AOF 里就有 100 条，但内存里只剩 1 个值 → 重写按**当前内存状态**生成最小命令集：

```
主进程                                   子进程
  │                                        │
  ├── fork ───────────────────────────────►│ ① 遍历当前内存，生成"最小命令集"
  │  主进程继续接客                          │   （100 次 set k 1 → 1 条 set k 100）
  │  ② 重写期间的新写命令同时写两份：
  │     aof_buf          → 落旧 AOF（旧文件不断档）
  │     aof_rewrite_buf  → 攒给新 AOF（新文件不缺数据）
  │◄──────────── ③ 新 AOF 文件写完 ──────────│
  │ ④ 把 aof_rewrite_buf 里的增量命令追加到新 AOF 尾部
  │ ⑤ 原子 rename 替换旧 AOF
  ▼ 全程不阻塞主进程，重写期间的数据一条不丢
```

AOF 尾部损坏（断电写了一半）修复一句：`redis-check-aof --fix appendonly.aof` 自动截掉不完整的最后一条命令。

### 混合持久化（Redis 4.0+，aof-use-rdb-preamble）

```
appendonly.aof 文件布局（AOF 重写时生成）：
┌──────────────────────────────────────────────┐
│  RDB 格式的全量快照（重写那一刻的数据）          │ ← 恢复时直接载入：快
├──────────────────────────────────────────────┤
│  AOF 格式的增量命令（重写之后的写命令）          │ ← 最多丢这一段的秒级数据
└──────────────────────────────────────────────┘
兼得：RDB 的恢复速度 + AOF 的数据安全
```

### 选型建议

| 场景 | 推荐 |
| --- | --- |
| 纯缓存，数据可从数据库重建 | 不开持久化，或只 RDB |
| 允许丢分钟级数据 | 只 RDB |
| 最多丢 1 秒 | AOF everysec |
| 生产推荐 | 混合持久化 + everysec |

## 面试答法

### 30 秒版（可背诵）

> Redis 持久化有 RDB 和 AOF 两种。RDB 是 fork 一个子进程把全量内存拍成二进制快照，靠写时复制让主进程全程继续服务，优点是文件小、恢复快，缺点是两次快照之间的数据会丢；AOF 是把每条写命令追加到日志文件，everysec 策略下最多丢一秒，文件膨胀靠重写机制压缩，重写期间的增量命令会暂存到 rewrite 缓冲区最后追加，数据不丢。4.0 之后有混合持久化，AOF 文件前半段是 RDB 全量、后半段是增量命令，恢复快又只丢秒级数据，生产环境一般开混合加 everysec。

### 深入版（被追问时按这条线展开）

1. **先定调**：Redis 快靠纯内存 + 单线程 + IO 多路复用，所以持久化设计全部绕开主线程 → "fork 子进程 + 内存缓冲"两板斧
2. **RDB**：bgsave 流程 → fork 只复制页表 → COW 改哪页才复制哪页 → 报优缺点表（恢复快 / 丢分钟级 / COW 内存翻倍风险）
3. **AOF**：命令进 aof_buf → 三种 fsync 策略对比 → 文件膨胀 → 重写原理（最小命令集 + rewrite_buf 双写不丢）
4. **混合**：画文件布局图，RDB 头负责快、AOF 尾负责不丢
5. **收尾**：按场景报选型表

### 常见追问

- **bgsave 期间还能写数据吗？** → 能。COW：父进程改到哪页才复制哪页，子进程快照永远读 fork 那一刻的旧页
- **COW 有什么风险？** → 快照期间大量页被修改时，内存占用最高接近翻倍，大实例要预留余量
- **RDB 恢复为什么比 AOF 快？** → 二进制直接载入内存；AOF 要逐条重放命令
- **AOF 重写期间新数据会丢吗？** → 不会。新命令双写 aof_buf 和 aof_rewrite_buf，新文件生成后追加增量再原子替换
- **AOF 文件损坏怎么办？** → redis-check-aof --fix 截掉尾部不完整的命令
- **怎么尽量不丢数据？** → 混合持久化 + everysec；机器级故障靠主从复制 + 哨兵/集群兜底，持久化本身救不了物理损坏
