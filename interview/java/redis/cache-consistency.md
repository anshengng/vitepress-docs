# 缓存与数据库一致性

## 题目

> 更新数据时，如何保证 Redis 缓存与 MySQL 的一致性？先删缓存还是先更新数据库？

## 为什么有一致性问题

缓存和数据库是**两个独立存储**，写数据要写两边，而"写两份"**不是原子操作**，并发下任何交错都会留下旧值。先看"更新缓存"方案怎么翻车——**两种顺序各画一个异常时间线**：

顺序一：**先更新数据库，再更新缓存** —— 并发写覆盖：

```
初始：price = 10；并发写：T1 要改成 8，T2 要改成 6

时刻   T1（写）                     T2（写）                DB      缓存
 t1    更新库 price=8                                        DB=8
 t2                                 更新库 price=6           DB=6
 t3                                 更新缓存 price=6                  缓存=6
 t4    更新缓存 price=8 ❌                                           缓存=8

最终：DB=6（T2 的结果），缓存=8（T1 晚到的覆盖）
→ T2 的更新被 T1 晚到的"改缓存"覆盖，长期不一致
```

顺序二：**先更新缓存，再更新数据库** —— 同样错位：

```
时刻   T1（写）                     T2（写）                DB      缓存
 t1    更新缓存 price=8                                      缓存=8
 t2                                 更新缓存 price=6                  缓存=6
 t3                                 更新库 price=6           DB=6
 t4    更新库 price=8 ❌                                     DB=8

最终：DB=8，缓存=6 → 两边各拿一个版本，同样不一致
```

结论：**两个并发写一交错，"更新缓存"无论谁先谁后都可能留下旧值** → 主流方案不"改"缓存，改成"删"。

## 核心要点

### Cache Aside 标准流程（旁路缓存，推荐）

```
读请求 ──► 查缓存 ──命中──► 直接返回（绝大多数请求走这条，快）
             │
           miss（未命中）
             ▼
          查数据库 ──► 回填缓存（带过期时间）──► 返回

写请求 ──► ① 更新数据库 ──► ② 删除缓存（是删，不是改）
```

### 为什么是"删缓存"而不是"改缓存"

- **并发写覆盖**：见上面两个时间线，两个"改缓存"交错必留旧值；两个"删缓存"怎么交错结果都是"缓存空"，下次读自然回填最新值，**天然安全**
- **懒加载不浪费**：改缓存是"预计算"，改完没人读就白算一遍；删缓存是"谁读谁回填"
- 缓存值常常是**多表聚合结果**，改缓存的维护成本和出错率都远高于删

### 为什么"先更新库，再删缓存"

**反过来（先删缓存，再更新库）会被并发读污染**：

```
时刻   T1（写：price 10→8）        T2（并发读）              缓存       DB
 t1    删除缓存                     缓存=空
 t2                                  查缓存 miss
 t3                                  查库，读到旧值 10                  （还没更库）
 t4    更新库 price=8                                                  DB=8
 t5                                  回填缓存 price=10 ❌    缓存=10

最终：DB=8，缓存=10 → 脏数据长期驻留（直到 TTL 过期）
```

**先更库再删缓存也有理论窗口，但概率低得多**：

```
需要同时满足：① 读时缓存恰好 miss ② 读库拿到旧值 ③ 期间写请求完成了"更库+删缓存" ④ 读才慢吞吞回填旧值

时刻   T2（读）                    T1（写）                 缓存       DB
 t1    查缓存 miss（恰好不在）
 t2    查库，读到旧值 10（之后被慢查询/GC 卡住）
 t3                                 更新库 price=8                      DB=8
 t4                                 删除缓存                缓存=空
 t5    （卡完）回填缓存 price=10 ❌                          缓存=10

对比：先删后更 = 删缓存到更库完成之间来一个读就翻车（毫秒级窗口，概率高）
      先更后删 = 读请求要横跨整个写操作还没返回（秒级慢读，概率极低）
```

### 延迟双删：覆盖"主从延迟 + 并发读回填旧值"

```
T1（写线程）
 ① 更新数据库（主库）
 ② 删除缓存
 ③ 延迟几百毫秒（MQ 延迟消息 / 定时任务，别在写线程里裸 sleep 占连接）
    目的：a) 等 ①~③ 之间并发读的"回填旧值"动作发生完
         b) 等主从同步完成（如果读走从库，避免删早了又被旧从库污染）
 ④ 再删一次缓存 ← 把窗口期内被污染的旧值清掉
 ⑤ 兜底：所有缓存必须设 TTL，就算删失败也只是不一致到过期为止
```

### 订阅 binlog 异步删（Canal 方案）

```
业务代码只管写库，完全不碰缓存
MySQL（binlog 开 ROW 模式）──► Canal（伪装成 MySQL 从库订阅 binlog）
                                 │
                                 ▼
                             删除 Redis 缓存（失败进 MQ 重试）
优点：业务零侵入；binlog 一定产生，删除可靠；天然覆盖主从延迟场景
代价：多一个中间件、链路变长，删除必然滞后（最终一致）
```

### 强一致的代价

以上全是**最终一致**：短暂窗口 + TTL 兜底。业务非要强一致（如账户余额）只有一条路：

```
读写都走分布式锁，全部串行化
  代价：读也要抢锁 → 缓存对读的加速意义大幅下降，吞吐骤降
结论：一般业务用"先更库再删缓存 + 延迟双删/binlog + TTL"足够；
      强一致场景要么上锁串行化，要么干脆别用缓存（读写都走库）
```

### 方案对比

| 方案 | 一致性 | 复杂度 | 侵入性 | 适用 |
| --- | --- | --- | --- | --- |
| 先更库再删缓存 | 最终一致（极小概率窗口） | 低 | 低 | 绝大多数场景 ✅ |
| + 延迟双删 | 同上，窗口更小 | 中（延迟任务） | 中 | 读走从库、并发回填多 |
| + Canal 订阅 binlog | 可靠最终一致 | 中（多中间件） | 极低 | 大型系统 |
| 分布式锁串行读写 | 强一致 | 高 | 高 | 资金级极少数场景 |

## 面试答法

### 30 秒版（可背诵）

> 缓存一致性问题的根源是"写库和写缓存"不是原子操作，并发下"更新缓存"会写覆盖，所以主流做法是 Cache Aside：读的时候 miss 就查库回填，写的时候先更新数据库再删除缓存——用删而不是改，因为并发删怎么交错都安全，还能懒加载。这个方案在读请求恰好横跨整个写操作时仍可能回填旧值，概率极低，生产上用延迟双删或者订阅 binlog 的 Canal 异步删做补偿，再加缓存过期时间兜底，整体是最终一致。真要强一致就只能用分布式锁把读写串行化，但那样缓存的性能收益基本没了，一般业务不这么干。

### 深入版（被追问时按这条线展开）

1. **先抛结论**：本质是两个存储的写操作非原子，方案分"最终一致"和"强一致"两派
2. **排除法讲清演进**：更新缓存并发写覆盖（时间线）→ 改成删缓存；先删缓存的方案被并发读回填旧值（时间线）→ 改成先更库再删
3. **承认不完美**：先更后删仍有极小概率窗口 → 延迟双删 / binlog 订阅 / TTL 兜底
4. **强一致的代价**：分布式锁串行化，性能换一致，一般不值得
5. **落到项目**：说清自己项目用的哪套（一般是"先更库再删缓存 + Canal + TTL"）

### 常见追问

- **为什么删缓存而不是更新缓存？** → 并发"删"怎么交错都安全，并发"改"会覆盖留旧值；删是懒加载、改是预计算白算
- **先更库再删缓存，删除失败了怎么办？** → MQ 重试 / Canal 订阅 binlog 兜底删 / TTL 过期兜底
- **延迟双删的时间怎么定？** → 覆盖"读回填耗时 + 主从同步延迟"，一般几百毫秒，读流量大就调大
- **为什么不用分布式锁做强一致？** → 读也串行化后缓存失去意义，吞吐骤降，业务一般接受最终一致
- **回填旧值还有救吗？** → 回填用短过期、延迟双删清理，核心是让脏值活不过 TTL
