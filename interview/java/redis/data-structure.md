# Redis 底层数据结构与编码

## 题目

> Redis 五大数据类型底层用什么结构实现？SDS 比 C 字符串好在哪？跳表为什么不用红黑树？渐进式 rehash 是怎么做的？ziplist 的连锁更新是什么，listpack 怎么解决的？

## 为什么需要

Redis 的快（纯内存 + IO 多路复用，见[持久化篇](./persistence.md)开头）只是一半，另一半是**为"小数据"精心挑选的内存结构**：同样存 1 万个短 key，用对结构和用错结构，内存能差 5~10 倍。所以 Redis 对每种类型都准备了两套编码——**小数据用紧凑结构省内存，大数据换标准结构保效率**。

## 核心要点

### 五大类型与底层编码总览

| 类型 | 底层结构（小数据 → 大数据） | 转换条件（示例） |
| --- | --- | --- |
| String | int → SDS | 值是整数用 int；否则 SDS |
| Hash | listpack → hashtable | 元素数 > 128 或单值 > 64 字节 |
| List | quicklist（节点内是紧凑列表） | 始终 quicklist，节点内自动转 |
| Set | intset → listpack → hashtable | 全整数用 intset；有字符串小集合用 listpack；超阈值转 hashtable |
| ZSet | listpack → skiplist + dict | 元素数 > 128 或单成员 > 64 字节 |

> Redis 7.0 起用 **listpack 全面替代 ziplist**，还从 quicklist 里移除了 ziplist，老资料里的 ziplist 直接按 listpack 理解即可。

用 `OBJECT ENCODING key` 可以查看某个 key 当前的实际编码。

### SDS：简单动态字符串

结构是「头部元信息 + 字节数组」：

```
+--------+--------+-------+---------------------------+--------+
|  len   | alloc  | flags |           buf[]           |  '\0'  |
| 已用长度| 总容量 | 类型  |  'h' 'e' 'l' 'l' 'o' ...  | 1字节  |
+--------+--------+-------+---------------------------+--------+
  len=5, alloc=10：预分配了一倍空间，下次追加不用 realloc
```

对比 C 字符串（`char[]`）的三大优点：

| 优点 | C 字符串 | SDS |
| --- | --- | --- |
| 取长度 | `strlen` 遍历 O(n) | 读 `len` 字段 **O(1)** |
| 二进制安全 | 以 `\0` 判结尾，存图片/序列化数据遇 `\0` 被截断 | 以 `len` 判长度，**buf 里可以存任意字节** |
| 内存管理 | 每次拼接都可能 realloc（还要自己防溢出） | **空间预分配**（扩容多留一倍）+ **惰性释放**（缩短不还内存），减少 realloc 次数且自动检查容量够不够 |

### 跳表（skiplist）：ZSet 的排序引擎

多层索引链表，上层是下层的"快速通道"。查找 55 的路径：

```
L3:   1 ──────────────────────────────── 67 ──► nil
      │  55 < 67，退回上一层往下走
L2:   1 ──────── 24 ──────────── 55 ──── 67 ──► nil
      │          │（从 24 往右走到 55）✔ 命中
L1:   1 ── 9 ── 24 ── 37 ── 55 ── 67 ── 89 ──► nil

查找 55：L3 从 1 出发 → 撞到 67 退回 → L2 走到 55 命中
只跳了 3 步，链表遍历要 5 步；n 个元素平均 O(log n)
```

每个节点随机决定"长多高"（每层晋升概率 1/4，最高 64 层），所以**插入/删除只改前后指针，不用旋转**。

为什么不用红黑树/AVL 树（面试必问）：

1. **实现简单**：无旋转、无变色，代码量是平衡树的零头，出 bug 好排查
2. **范围查询天然占优**：定位起点后沿最底层链表顺序走即可（`ZRANGEBYSCORE`）；红黑树要中序遍历，还得维护栈
3. **无平衡维护成本**：平衡树插删要旋转维持平衡，跳表靠概率近似平衡
4. ZSet 实际是 **skiplist + dict 双结构**：dict 管 O(1) 查分数（`ZSCORE`），skiplist 管排序，各干各的

> 红黑树唯一优势是单点查询更稳，但 Redis 有 dict 补位，这个优势被抵消了。

### dict 渐进式 rehash

dict 里放两张哈希表，扩容时不是一次搬完，而是**每次增删改查顺带搬一个 bucket**：

```
正常状态（只用 ht[0]）:
  dict ──► ht[0] ──► [bucket0][bucket1][bucket2][bucket3] ...

触发扩容（装填因子 ≥ 1）后，rehashidx = 0，开始渐进搬迁：

  dict ──► ht[0]（旧表，逐步搬空）    ht[1]（新表，容量 ×2）
            [bucket0] ✅已搬 ──┐       [bucket0..7] 新写入只进这里
            [bucket1] ←当前   │            ▲
            [bucket2]          ├────────────┘
            [bucket3]          └─ 每次操作搬一个 bucket，rehashidx++

  期间读：先查 ht[0]，查不到再查 ht[1]（新旧表并读）
  期间写：新键一律插 ht[1]（保证 ht[0] 只减不增）
  搬完：rehashidx 置 -1，释放 ht[0]，ht[1] 变成新的 ht[0]
```

**为什么要渐进式？** Redis 主线程单线程执行命令（见[持久化篇](./persistence.md)），几百万 key 一次性 rehash 会让 Redis 卡住几秒，所有请求排队。渐进式把一次大搬迁摊薄成百万次微小开销，每次命令只慢一点点。

### ziplist 连锁更新 → listpack 修复

ziplist 是一整块连续内存，**每个 entry 的头部记录了"前一个 entry 的长度"**：

```
ziplist: [zlbytes][zltail][zllen][entry1][entry2][entry3][zlend]
                                    │       │       │
entry 头部: [prevlen=5][自身数据]    ───► 记录前项长度，为了能往回走

连锁更新：entry1 从小变大（<254字节 → ≥254字节）
  → 头部长度字段从 1 字节膨胀到 5 字节 → entry1 整体变长
  → entry2 的 prevlen 也得跟着变大 → entry2 变长
  → entry3、entry4 ... 一路级联改下去 ❌ 最坏 O(n²)
```

**listpack 的修复思路**：每个 entry 只记录**自己的长度**，不记录前一项的——想往前走就从头/尾部用"自身长度"累加推算。前项变了与我无关，**连锁更新问题从根上消除**。代价是反向遍历要稍作计算，可接受。

### small 档优化思想总结

```
写入小 Hash/ZSet（如 2 个字段）
  → listpack：一块连续内存，无指针开销，CPU 缓存友好，超省内存
  → 元素增多/单值变大，超过阈值
  → 转成 hashtable / skiplist：查询效率优先

一条 RedisObject 的指针就要 8 字节，
小数据如果直接用大结构，"指针+元数据"比数据本身还大 —— 所以才要紧凑编码兜底
```

- 阈值可调：`hash-max-listpack-entries`、`zset-max-listpack-entries`、`*-max-listpack-value` 等
- 实战意义：把大 Hash 拆成多个小 Hash（分段存储），让它们留在 listpack 里省内存

## 面试答法

### 30 秒版（可背诵口语）

> Redis 每种类型都有两套编码：小数据用紧凑结构省内存，超阈值自动转标准结构保效率。比如 String 底层是 SDS，相比 C 字符串有三个优点：len 字段让取长度 O(1)、按长度而不是 \0 判断结尾所以二进制安全、空间预分配加惰性释放减少 realloc。ZSet 底层是跳表加字典，跳表实现比红黑树简单、范围查询天然有序、插入删除不用旋转。字典扩容用渐进式 rehash，两个表同时存在，每次操作顺带搬一个桶，避免单线程一次搬迁卡顿。Redis 7 之后 listpack 替代了 ziplist，解决了 ziplist 记录前项长度导致的连锁更新问题。

### 深入版（被追问时按这条线展开）

1. **先给总览**：五大类型 → 编码映射表，点出"small 档紧凑、large 档标准"的设计哲学
2. **SDS 三优点**：O(1) 长度 / 二进制安全 / 预分配+惰性释放
3. **跳表**：画多层索引，演示跳着找 55；对比红黑树三点 + dict 补位
4. **渐进式 rehash**：两表并读、新写进新表、逐 bucket 搬，强调单线程不能卡顿
5. **连锁更新**：ziplist 记前项长度的因果链 → listpack 只记自身长度的修复
6. **收尾**：阈值可配置，实战可拆大 key 挤进紧凑编码

### 常见追问

- **intset 是什么？** → 全是整数的 Set 用的有序整数数组，二分查找，省内存；一旦插入字符串就升级转 listpack/hashtable（升级不可逆）
- **quicklist 是什么？** → 双端链表套紧凑节点：节点内是 listpack（省内存），节点间用指针串（解决单个 ziplist 过大的连续内存问题），兼顾两头
- **跳表最高多少层？晋升概率？** → 最高 64 层，每层晋升概率 1/4，节点越多层概率越低，期望高度 O(log n)
- **装填因子到多少扩容？** → 无 bgsave 时 ≥1 扩容；有 bgsave 时提高门槛到 5，避免子进程写时复制放大内存
- **怎么知道 key 用的什么编码？** → `OBJECT ENCODING key`；`DEBUG OBJECT` 看更细
- **编码转换阈值能改吗？** → 能，`hash-max-listpack-entries` 等配置项，但要明白改小省内存、改大保查询，看业务取舍
