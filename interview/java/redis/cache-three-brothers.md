# 缓存穿透 / 击穿 / 雪崩

## 题目

> 说说缓存穿透、击穿、雪崩的区别？分别怎么解决？布隆过滤器原理是什么，有什么坑？你们项目里是怎么防的？

## 为什么需要"三兄弟"这套防御

缓存的价值是把读流量挡在 Redis，保护后面的 MySQL。但 Redis 里的数据是**有边界、会过期、会挂**的——三种异常恰好对应三种"流量绕过缓存直打数据库"的方式。名字像、本质不同，面试先考你能不能分清。

## 核心要点

### 一句话类比 + 三者对比

| | 生活类比 | 本质 | 触发条件 |
| --- | --- | --- | --- |
| 穿透 | 查一个**根本不存在**的身份证号，前台没记录，每次都跑去档案室问 | 查**不存在**的数据，缓存永远拦不住 | 恶意刷 id=-1、随机 id |
| 击穿 | 热门演唱会门票信息刚过期的一瞬间，所有人同时涌向柜台 | **单个热点 key 过期**，并发重建 | 高并发 + 热点 key TTL 到点 |
| 雪崩 | 整个档案室停电（或大批档案同一天到期） | **大批 key 同时失效 / Redis 宕机** | TTL 设置雷同、Redis 集群挂 |

### 请求流向对比图

```
正常请求：                          穿透：查不存在的 key
┌───┐   ┌───────┐   ┌─────┐       ┌───┐   ┌───────┐   ┌─────┐
│客户端│→│ Redis │→命中│ MySQL │     │客户端│→│ Redis │→未命中│ MySQL │
└───┘   └───────┘  (少数)        └───┘   └───────┘  查无数据→不缓存
                                     ↑ 每次都打到 MySQL ❌

击穿：热点 key 过期瞬间               雪崩：大批 key 同时到期/Redis 挂
  10万 QPS ──► [key 过期]              10万 QPS ──► [Redis 不可用]
  10万个线程同时未命中                    全部流量瞬间直达
       ↓                                  ↓
   同时打到 MySQL ❌                    MySQL 被打垮 ❌❌
```

### 解决方案总表

| 问题 | 方案 | 说明 |
| --- | --- | --- |
| 穿透 | 缓存空值 | 查不到也缓存 `key→null`（短 TTL，防内存被垃圾 key 撑爆） |
| 穿透 | 布隆过滤器 | 在缓存前加"存在性安检门"，不存在直接拒绝 |
| 击穿 | 互斥锁重建 | 只放一个线程去重建缓存，其余等待 |
| 击穿 | 逻辑过期 | key 永不过期，值里带过期时间，异步重建 |
| 雪崩 | TTL 加随机 | 基础 TTL + random(0~300s)，打散到期时间 |
| 雪崩 | 多级缓存 | 本地 Caffeine → Redis → MySQL，一层挂还有上层 |
| 雪崩 | 高可用 + 熔断 | Redis 哨兵/集群；DB 侧 Sentinel/Hystrix 熔断限流兜底 |

### 布隆过滤器原理图解（穿透必考细节）

```
判断 "id=123 存在吗？"：
用 k 个 hash 函数把 key 映射到位数组的 k 个位置

插入 123：   h1→位2, h2→位5, h3→位9  全部置 1
  bits: [0 1 0 0 0 1 0 0 0 1 0 0 ...]

查询 123：   检查位 2、5、9 → 全 1 → "可能存在"
查询 456：   检查位 3、5、9 → 位3 是 0 → "一定不存在" ✅ 直接拦截

两个结论（面试原话）：
- 说"不存在" → 一定准确（有一个 0 就不是插入过的）
- 说"存在"   → 可能误判（位是别人插的时候顺手置 1 的）
- 不支持删除（置 0 会误伤别人）→ 用 Counting Bloom / 定期重建
```

### 击穿：互斥锁——模拟两个线程同时发现 key 失效

```
key=hot:product:1 过期，T1、T2 同时来查：

时刻  T1                          T2                        Redis / MySQL
 t1   GET → nil（未命中）
 t2   SET lock:product:1 NX → ✅ 拿到重建权
 t3                               GET → nil（也未命中）
 t4                               SET lock NX → ❌ 失败
 t5                               短暂 sleep 后重新 GET → 还没好 → 再等
 t6   SELECT ... FROM product ──────────────────────────► 查库（只有 1 次）
 t7   SET hot:product:1 值 + DEL lock
 t8                               GET → 命中 ✅              返回缓存值

没有锁：t6 变成 10 万次查库 → 击穿。
加锁效果：并发重建收敛成 1 次，其余线程"等待+读缓存"。
```

逻辑过期方案（不阻塞、最终一致）：

```
value 里带 expireAt 字段，key 本身不设 TTL：
线程读到 now > expireAt → 拿锁的线程异步去重建，
其余线程先返回【旧值】（短暂脏数据，但不阻塞、不查库）
适合对一致性不敏感的高热点（首页商品、热搜）
```

### 雪崩：TTL 加随机图解

```
危险：10 万个 key 都 TTL=3600 → 同一秒集体过期，流量尖峰
      ──┬──────┬──────┬──  （到期时刻重叠）
安全：TTL = 3600 + random(0,300)
      ─┬─┬─┬─┬─┬─┬─┬─┬─  （到期时刻摊平）
```

Redis 宕机型雪崩：哨兵/Cluster 保可用 + 缓存不可用时直接走 DB 限流降级（熔断），别硬扛。

## 面试答法

### 30 秒版（可背诵口语）

> 三者的区别看流量路径：穿透是查数据库里根本不存在的数据，缓存里没有、库里也查不到，每次直打 DB；击穿是某个热点 key 过期瞬间，大量并发同时未命中、同时去重建；雪崩是大批 key 同时过期或 Redis 整个宕机，流量全面压垮 DB。方案上，穿透用缓存空值加布隆过滤器——布隆说不存在一定准、说存在可能误判；击穿用互斥锁只放一个线程重建，或者逻辑过期异步刷新不阻塞；雪崩把 TTL 加随机数打散、上多级缓存和 Redis 高可用，再用熔断兜底。答题时我会先分清三者再给方案，最后结合项目说我们商品详情用的是空值缓存加互斥锁。

### 深入版（被追问时按编号展开）

1. **先区分三者**：画三张流量图，强调"不存在 vs 单 key vs 大批 key"
2. **穿透**：空值缓存的 TTL 要短、防 key 污染；布隆过滤器位数组 + k 次 hash、误判率与容量、不支持删除
3. **击穿**：完整讲两个线程抢重建锁的时间线；追问"等锁线程怎么办"→ 自旋重试读缓存
4. **逻辑过期**：牺牲一致性换可用性，讲清 value 结构
5. **雪崩**：TTL 随机、多级缓存、高可用、熔断降级四层递进
6. **落到项目**：说一个真实场景（商品详情/秒杀），点出用了哪两招、为什么

### 常见追问

- **布隆过滤器误判了怎么办？** → 接受误判（放行后 DB 查无数据再缓存空值兜底）；删除用计数布隆或定期全量重建
- **缓存空值会不会撑爆内存？** → 会，所以短 TTL + 只缓存高频 miss；恶意随机 id 场景上布隆
- **互斥锁死了怎么办？** → 锁必须带超时（SET NX PX），重建线程宕机后锁自动释放
- **击穿和穿透同时发生？** → 布隆挡不存在的，互斥锁挡热点重建，两层互不冲突
- **Redis 挂了 DB 也扛不住，还有招吗？** → 熔断降级（返回兜底数据/排队页），多级缓存里本地缓存还能撑一阵
