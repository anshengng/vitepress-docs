# Redis 分布式锁

## 题目

> 为什么要用分布式锁？Redis 分布式锁怎么演进？锁误删问题怎么解决？看门狗原理？RedLock 听说过吗，和 ZooKeeper 锁怎么选？

## 为什么单机锁不够

```
单体：一个 JVM，synchronized / ReentrantLock 够用
      ┌──── JVM ────┐
      │ 线程A 线程B  │ ← synchronized 能互相看见
      └─────────────┘

微服务：两个实例各自一个 JVM，锁互不可见
  ┌─实例1 JVM─┐   ┌─实例2 JVM─┐
  │ 线程A 抢到 │   │ 线程B 抢到 │   ← 两边都以为自己持有锁 ❌
  └───────────┘   └───────────┘
  扣同一件库存 → 超卖

→ 需要一把"所有实例都看得见"的公共锁：放 Redis 这种共享存储上
```

## 核心要点：六步演进，每步都有竞争时间线

### ① setnx 裸用 —— 宕机死锁

```
SETNX lock 1     （key 不存在才 set，天然互斥）
时刻  T1(实例1)              T2(实例2)
 t1   SETNX → 1 ✅ 进临界区
 t2                          SETNX → 0 ❌ 等待
 t3   💥 业务没做完进程宕机
 t4   lock 永远没人删 ──► T2 永远拿不到锁（死锁）
```

### ② setnx + expire 两条命令 —— 非原子，中间宕机还是死锁

```
 t1   SETNX lock 1 ✅
 t2   💥 还没来得及执行 EXPIRE 就宕机 → lock 永不过锁 ❌
```

### ③ 一步到位：set key value NX PX

```
SET lock "uuid-1" NX PX 30000
      │      │       │    └─ 30 秒自动过期，宕机也能解锁
      │      │       └────── 不存在才写（互斥）
      │      └────────────── 唯一标识：谁能删这把锁
      └─ NX+PX 在一条命令里，原子 ✅ 这就是锁的"最小可用形态"
```

### ④ 误删别人的锁（必考）—— 完整时间线

A 的业务执行时间 > 锁 TTL：

```
时刻  线程A(实例1)                 线程B(实例2)              Redis: lock
 t1   SET lock A NX PX=30s ✅
 t2   A 进入 GC/慢查询，业务卡住 40s…                    (锁还在，但 30s 后…)
 t3                               （B 在重试）
 t4        ⏰ 30s 到，锁自动过期 🔓
 t5                               SET lock B NX ✅ 拿到新锁
 t6                               B 进入临界区干活
 t7   A 苏醒，干完业务 → DEL lock ──────────────────► 把 B 的锁删了 ❌❌
 t8                               B 干活中锁已没了
 t9        线程C 此时 SETNX 也能成功 → A/C 并发进临界区 ❌ 锁失效
```

解法：**删锁前先校验 value 是自己的 uuid，且"校验+删除"必须原子**——Lua：

```lua
if redis.call('get', KEYS[1]) == ARGV[1]
   then return redis.call('del', KEYS[1])
   else return 0 end
```

（为什么必须原子：get 完确认是自己的、del 前锁恰好过期被 B 拿走，照样误删。GET+DEL 两条命令 = 又回到②的非原子问题。）

### ⑤ 看门狗续期（Redisson）—— 图解

```
问题：TTL 设短了业务没干完（见④），设长了宕机后要干等很久。
Redisson：lock() 默认 leaseTime=-1 时启用看门狗

客户端持锁后：
  每 10s（TTL 30s / 3）检查一次："我还持有这把锁吗？"
  是 → 把 TTL 重新续满 30s          否（已释放）→ 停止续期
  ┌────────────┐   续期   ┌───────┐
  │ 业务线程干活 │◄───────│ 看门狗 │  只要进程活着，锁一直续
  └────────────┘          └───────┘
  进程宕机 → 看门狗随进程死 → 没人续期 → 30s 后锁自然过期 ✅
  → 既不用猜业务时长，宕机又能自动解锁

  业务超过 30s？没关系，看门狗一直在续；
  显式传 leaseTime=60s 则不启用看门狗，到点强解。
```

### ⑥ RedLock 争议（点到为止）

单 Redis 主从的隐患：主节点加锁成功、**没同步给从就宕机**，从库升主后锁"消失"，两个客户端同时持锁。

```
RedLock：向 5 个独立 Redis 节点依次加锁，
多数派(≥3)成功且总耗时 < TTL 才算持锁。

Martin Kleppmann 的质疑：
- 时钟漂移：某节点时钟跳快 → 锁提前过期 → 两人同时持锁
- GC 停顿：客户端"以为"自己还持锁，其实早已过期（同④）
antirez 反驳：假设足够好的时钟/NTP 纪律则可用。

一句话立场：对"锁必须绝对安全"的场景（资金、防重复扣款），
用 ZooKeeper/etcd 这类 CP 锁，或把正确性交给数据库唯一约束；
Redis 锁适合"大部分时候互斥即可"的防并发优化场景。
```

### 与 ZooKeeper 锁对比

| 对比 | Redis 锁 | ZooKeeper 锁 |
| --- | --- | --- |
| 一致性模型 | AP 优先（主从异步复制） | CP（ZAB，过半写成功才返回） |
| 实现 | SET NX PX + Lua + 看门狗 | 临时顺序节点 + watch 前一个节点 |
| 解锁 | TTL 到期 / 主动 DEL | 会话断开自动删临时节点，天然防死锁 |
| 惊群 | 自旋重试 | 只 watch 前一个节点，逐个唤醒 |
| 性能 | 高（内存、单命令） | 较低（写要过半落盘） |
| 适用 | 高并发防重复、效率型互斥 | 强正确性、选主、配额发放 |

## 面试答法

### 30 秒版（可背诵口语）

> 微服务多实例部署，JVM 内的 synchronized 互相看不见，所以要把锁放到 Redis 这种共享存储上。演进分几步：裸 setnx 宕机死锁；setnx 加 expire 两条命令不原子，中间宕机还是死锁；所以用 SET key value NX PX 一条命令原子地"加锁+过期+唯一标识"。最经典的坑是误删：A 业务超过锁 TTL，锁过期 B 拿到，A 干完把 B 的锁删了——解法是删除前用 Lua 原子校验 value 是不是自己的 uuid。时长问题交给 Redisson 看门狗：默认 30 秒锁、每 10 秒检查仍持有就续期，宕机没人续自然过期。RedLock 有时钟漂移的争议，强正确性场景我会选 ZooKeeper 临时顺序节点或直接用数据库唯一约束兜底。

### 深入版（被追问时按编号展开）

1. **引出**：多实例 JVM 锁不可见 → 超卖例子
2. **演进①②③**：每步画宕机/竞争时间线，讲清 NX+PX 为什么必须一条命令
3. **④误删**：完整讲 A 慢→锁过期→B 拿锁→A 删 B 锁的时间线；value 存 uuid；Lua 原子删
4. **⑤看门狗**：30s/10s 续期图；显式 leaseTime 则不启用
5. **⑥RedLock**：主从切换丢锁引出 → 5 节点多数派 → 时钟漂移/GC 停顿两质疑 → 立场
6. **对比 ZK**：CP vs AP、临时节点自动释放、watch 前驱防惊群、性能差异
7. **收尾**：锁只解决"同一时刻"，业务正确性最终仍靠幂等/唯一索引兜底

### 常见追问

- **为什么不用 UUID 时间戳拼 value？** → 只要 value 全局唯一即可，uuid 够用；重点是"删前校验 + 原子"
- **Redisson 可重入怎么实现？** → hash 结构记 field=线程标识、value=重入次数，Lua 保证原子
- **锁过期业务没执行完，除了看门狗还有啥？** → 合理估 TTL、业务拆分缩短临界区、最终靠幂等兜底
- **Redis 主从切换丢锁怎么彻底防？** → RedLock（有争议）或换 CP 的 ZK/etcd；资金场景推荐"锁+唯一索引"双保险
- **ZooKeeper 死锁风险？** → 客户端会话断开临时节点自动删除，比 Redis 裸用更不容易死锁
