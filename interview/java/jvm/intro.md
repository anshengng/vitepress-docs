# JVM 入门：先建立一张全局地图

## 题目

> JVM 是什么？为什么 Java 需要它？一段 `.java` 代码从源码到跑起来，JVM 内部发生了什么？运行时内存区域里的那些名字，到底在什么时候出现？

## 为什么需要

直接去看「运行时内存区域」，会一下子撞到程序计数器、虚拟机栈、栈帧、元空间、TLAB 一堆名词，却不知道它们为什么存在。原因不是这些概念难，而是**缺少上下文**：不知道 JVM 干活分几步，自然不知道每一步用哪个区域。

这页先只做一件事：**把 JVM 是干什么的、一次运行经历哪些阶段讲清楚**。等你脑子里有了这张全局地图，再去看内存区域，就变成「这个部件在哪个环节用得上」，而不是背名词。

## 核心要点

### 一、JVM 到底是什么

**JVM（Java Virtual Machine，Java 虚拟机）是一个用软件模拟出来的计算机**：它有自己的指令集（字节码）、自己的内存划分、自己的执行引擎。它不直接运行 Java 源码，而是运行编译后的 `.class` 字节码。

它只做四件事：

1. **加载类**：把 `.class` 文件读进内存，变成 JVM 能用的数据结构
2. **执行字节码**：把一条条字节码指令跑起来
3. **管理内存**：给对象、方法调用分配空间
4. **回收垃圾**：把不再使用的对象占用的内存收回来

**跨平台的真相**：

```
Hello.java  ──javac──►  Hello.class（字节码）  ──►  各平台的 JVM  ──►  机器码
（平台无关的源码）       （平台无关的中间格式）        （平台相关实现）
```

Java 的「一次编写，到处运行」，靠的不是 Java 语言本身，也不是 JVM 跨平台——**JVM 自己并不跨平台**，而是 Windows、Linux、macOS 各有一份对应的 JVM 实现，它们都能读懂同一份字节码。

顺带理清三个容易混的名字：

```
JDK（Java 开发工具包）
 ├─ javac 编译器、javap、jconsole 等开发工具
 └─ JRE（Java 运行环境）
      ├─ Java 标准类库（java.lang、java.util…）
      └─ JVM（真正执行字节码的虚拟机）
```

> 传统上 JDK ⊃ JRE ⊃ JVM；JDK 9 模块化之后边界变模糊，但「开发用 JDK、运行靠 JVM」这个理解仍然成立。

主流的 JVM 实现是 **HotSpot**（Oracle/OpenJDK 默认），此外还有 IBM 的 OpenJ9、能编译原生镜像的 GraalVM。本系列默认讲 HotSpot。

### 二、从 `.java` 到运行：五个阶段

```
Hello.java
    │  ① javac 编译：语法检查、生成字节码
    ▼
Hello.class
    │  ② 类加载：找到文件 → 读入 → 校验 → 准备 → 解析 → 初始化
    ▼
方法区（类的"设计图"就位）
    │  ③ 内存分配：方法调用建栈帧，new 对象进堆
    ▼
运行时数据区
    │  ④ 执行：解释器逐条执行字节码，热点代码交给 JIT 编译
    ▼
输出结果（打印、写文件、返回）
```

几个关键点，先有个印象：

- **编译发生在运行之前**（`javac`），产出的是字节码，不是机器码。
- **类加载是"懒"的**：不是一启动就把所有类加载进来，而是**第一次主动用到**某个类时才触发（`new`、调用静态方法、访问静态字段、反射等）。
- 类加载分五步：**加载 → 验证 → 准备 → 解析 → 初始化**。其中后四步合称「连接 + 初始化」；验证是为了防止恶意或错误的字节码把 JVM 搞崩。
- 「双亲委派」是类加载器找类的规则，专门有一页讲，这里只需知道：**类加载器负责把 `.class` 变成方法区里的类信息**。

### 三、JVM 内部三大块

```
┌──────────────────────── JVM 进程 ─────────────────────────┐
│                                                          │
│   ┌──────────────┐      ┌───────────────────┐            │
│   │ 类加载子系统   │─────►│   运行时数据区      │            │
│   │ 加载/验证     │      │  方法区   堆       │            │
│   │ 准备/解析     │      │  虚拟机栈 PC       │            │
│   │ 初始化        │      │  本地方法栈        │            │
│   └──────────────┘      └─────────┬─────────┘            │
│                                   │                      │
│                                   ▼                      │
│                        ┌────────────────────┐            │
│                        │     执行引擎        │            │
│                        │ 解释器 | JIT | GC   │            │
│                        └─────────┬──────────┘            │
│                                  │                       │
│                        ┌─────────▼──────────┐            │
│                        │  本地库接口 JNI     │──► C/C++ 库 │
│                        └────────────────────┘            │
└──────────────────────────────────────────────────────────┘
```

| 部件 | 干什么 | 类比 |
| --- | --- | --- |
| 类加载子系统 | 把 `.class` 搬进内存，变成方法区里的类信息 | 把剧本送进剧组 |
| 运行时数据区 | 存放运行时的数据：类信息、对象、方法调用现场 | 剧本库、道具间、拍摄现场 |
| 执行引擎 | 解释执行字节码、把热点代码编译成机器码、垃圾回收 | 导演 + 演员 + 清场人员 |
| 本地库接口 | 调用操作系统和 C/C++ 库（`System.out.println` 最终也要走到这里） | 找外援 |

**这里要先纠正一个新手最容易卡住的认知**：运行时数据区是 **JVM 规范里的逻辑划分**，不是操作系统给你的物理内存分区。规范只规定「有这么几块、各自存什么」，至于每一块具体落在进程地址空间的哪里，由 JVM 实现自己决定。

最典型的就是方法区：规范里它是一个概念，HotSpot 在 JDK 8 之后用「元空间」实现它，而元空间用的是**本地内存**，不在 Java 堆里。所以看到「方法区不在堆里」时不要觉得矛盾——它本来就不是按物理位置划分的。

### 四、跟着一段代码走一遍

这是本页最重要的部分。下面这段代码，把运行时数据区几乎全部串了一遍：

```java
public class Main {
    public static void main(String[] args) {
        Person p = new Person("Tom", 18);
        int newAge = p.grow(1);
        System.out.println(newAge);
    }
}

class Person {
    String name;
    int age;

    Person(String name, int age) {
        this.name = name;
        this.age = age;
    }

    int grow(int years) {
        return age + years;
    }
}
```

按执行顺序，JVM 内部发生的事：

| 步骤 | 代码 | JVM 内部发生了什么 |
| --- | --- | --- |
| 1 | 启动 | 类加载器找到 `Main.class`，类信息放进**方法区**；创建一个 main 线程，为它分配**程序计数器**和**虚拟机栈** |
| 2 | 进入 `main` | `main` 的**栈帧**压入虚拟机栈；`args` 放进栈帧的**局部变量表** |
| 3 | `new Person(...)` | 首次用到 `Person` → 触发类加载，`Person` 的类信息进方法区；对象本体在**堆**的 Eden 区分配；引用 `p` 存在 main 栈帧的局部变量表里 |
| 4 | `p.grow(1)` | 为 `grow` 新建一个栈帧压栈：`this`（指向堆里那个对象）和 `years=1` 在局部变量表，计算过程在操作数栈；返回后栈帧弹出，结果回到 `main` 栈帧 |
| 5 | `System.out.println` | 进入 Java 类库，最终通过**本地方法接口（JNI）**调用操作系统输出 |
| 6 | `main` 返回 | `main` 栈帧弹出，线程结束；`p` 指向的对象不再可达，成为垃圾等待 GC；方法区里 `Main` / `Person` 的类信息**不会**跟着方法结束而消失 |

第 3 步的「引用」和「对象」分居两地，是理解后面所有内存问题的起点：

```
虚拟机栈（main 栈帧）                堆
┌────────────────────┐        ┌──────────────────────┐
│  p  ───────────────────────►│  Person 对象          │
│  newAge = 19       │        │  name ──► "Tom"       │
│  args              │        │  age = 18             │
└────────────────────┘        └──────────────────────┘
      栈：执行现场                   堆：对象本体
```

一句话总结这一节：**栈跟着方法走，堆跟着对象走，方法区跟着类走**。这三种生命周期，就是下一章「运行时内存区域」真正的骨架。

### 五、三种生命周期，对应三个区域

| 区域 | 生命周期跟着谁 | 谁负责释放 | 空间不够时 |
| --- | --- | --- | --- |
| 程序计数器 | 线程 | 线程结束自动消失 | 不会 OOM |
| 虚拟机栈 / 本地方法栈 | 方法调用 | 方法返回自动弹栈 | `StackOverflowError` |
| 堆 | 对象是否可达 | **GC 回收** | `OutOfMemoryError: Java heap space` |
| 方法区（元空间） | 类是否被卸载 | 类卸载（条件苛刻） | `OutOfMemoryError: Metaspace` |

这张表解释了一个高频疑问：**为什么 GC 主要管堆？** 因为栈和程序计数器是「跟着方法/线程自动释放」的，根本不需要 GC 操心；只有堆里的对象，什么时候没人用了是不确定的，才需要专门的可达性分析去判断。

### 六、堆和栈到底怎么区分

新手最常见的误解是「对象存在栈里」，或者「`p = null` 就把对象删了」。记住下面这段：

```java
void test() {
    Person p = new Person("Tom", 18);  // 对象在堆，引用 p 在栈
    p = null;                          // 只是断开了引用，堆里的对象还在
}
```

| 对比项 | 虚拟机栈 | 堆 |
| --- | --- | --- |
| 存什么 | 栈帧、局部变量、对象引用 | 对象本体、数组 |
| 共享范围 | **线程私有** | **线程共享** |
| 谁管理 | 随方法进出自动管理 | GC 管理 |
| 典型异常 | `StackOverflowError` | `OutOfMemoryError` |
| 分配速度 | 快（指针移动即可） | 相对慢，还涉及 GC |

「线程私有」的意思是：每个线程都有自己的程序计数器和虚拟机栈，所以方法调用互不干扰；堆和方法区则被所有线程共享，因此才会有并发安全和 GC 的问题。

### 七、解释器与 JIT：为什么 Java 不慢

字节码不是 CPU 能直接执行的机器码，JVM 用了两条腿走路：

- **解释器**：读一条字节码，执行一条。启动快，不用等编译，但峰值性能一般。
- **JIT 编译器**：某段代码反复执行（热点代码）时，把它编译成当前平台的机器码并缓存起来，后续直接跑机器码。
- **分层编译**：先用 C1 快速编译保证响应，再对更热的代码用 C2 做深度优化。

一句话：**先解释着跑起来，跑热了再编译**。所以「Java 是编译型还是解释型」这个问题，答案是混合的。

### 八、术语速查

| 术语 | 一句话解释 |
| --- | --- |
| 字节码 | `.class` 里的指令，面向 JVM 而不是面向 CPU |
| 类加载器 | 负责查找并加载 `.class` 的组件 |
| 双亲委派 | 类加载器先让父加载器找，父加载器找不到自己再找 |
| 栈帧 | 一次方法调用的现场：局部变量表、操作数栈、返回地址等 |
| 程序计数器 | 记录当前线程执行到哪条字节码指令 |
| 方法区 / 元空间 | 存类信息、常量等；JDK 8 起 HotSpot 用元空间实现，位于本地内存 |
| 堆 | 存对象实例和数组，GC 主战场 |
| 引用 | 变量里存的地址，指向堆中的对象（不是对象本身） |
| GC | 垃圾回收，自动回收不可达对象 |
| JIT | 即时编译，把热点字节码编译成机器码 |
| JNI | Java 调用 C/C++ 等本地代码的接口 |
| HotSpot | 最主流的 JVM 实现 |

## 面试答法

### 30 秒版（可背诵）

> JVM 是运行 Java 字节码的虚拟机，主要由三部分组成：类加载子系统负责把 class 文件加载进方法区，运行时数据区负责存放类信息、对象和方法调用现场，执行引擎负责解释执行字节码、用 JIT 把热点代码编译成机器码并做垃圾回收。Java 的跨平台靠的是「平台无关的字节码 + 各平台各自的 JVM 实现」。运行时数据区按线程分为私有和共享两类：程序计数器、虚拟机栈、本地方法栈是私有的，堆和方法区是共享的；栈跟着方法走，堆跟着对象走，方法区跟着类走。

### 深入版（编号答题线索）

1. **先定义**：JVM 是软件模拟的计算机，有自己的指令集（字节码）、内存划分和执行引擎
2. **讲跨平台**：`javac` 产出平台无关的 `.class`，各平台 JVM 把字节码翻译成机器码；JVM 自身不跨平台
3. **讲分层**：JDK ⊃ JRE ⊃ JVM，区分开发、运行、执行三个概念
4. **讲流程**：编译 → 类加载（加载/验证/准备/解析/初始化）→ 内存分配 → 解释 + JIT 执行
5. **讲结构**：类加载子系统、运行时数据区、执行引擎、本地库接口四块各一句
6. **讲生命周期**：栈随方法释放、堆靠 GC、方法区靠类卸载，用 `new Person()` 的例子串起来
7. **收尾**：说明「运行时数据区是规范划分，不是物理分区」，引出元空间位于本地内存

### 常见追问

- **Java 是编译型还是解释型？** → 混合：`javac` 先编译成字节码，运行时由解释器执行，热点代码再由 JIT 编译成机器码
- **JVM、JRE、JDK 什么关系？** → JDK 包含 JRE，JRE 包含 JVM 和标准类库；开发用 JDK，运行最少只要 JRE（JDK 9 后模块化，界限变模糊）
- **字节码为什么能跨平台？JVM 跨平台吗？** → 字节码是面向 JVM 规范的中立指令集；JVM 本身不跨平台，每个操作系统各有一份实现
- **为什么说栈是线程私有的？** → 每个线程有自己的程序计数器和虚拟机栈，方法调用互不干扰；堆和方法区被所有线程共享
- **对象一定分配在堆上吗？** → 不一定，逃逸分析判定不逃逸的对象可以栈上分配或标量替换，但这是优化，逻辑上对象仍在堆
- **`p = null` 之后对象就立刻消失了吗？** → 没有，只是断开了引用；对象要等 GC 判断不可达后才回收
- **方法区就是堆的一部分吗？** → 不是。规范只把方法区定义为逻辑区域，HotSpot JDK 8 起用元空间实现，位于本地内存
- **GC 为什么不管栈？** → 栈帧随方法返回自动弹出，生命周期确定，不需要 GC；只有堆里对象的生命周期不确定，才需要可达性分析
