# GC 算法与收集器

## 题目

> 怎么判断一个对象能不能回收？四种引用有什么区别？三大基础 GC 算法各自的优缺点？常见收集器如何演进？G1 和 CMS 的原理与区别？

## 为什么需要

Java 把人从 C 的 `malloc/free` 中解放出来：对象不用了就该自动回收，但"不用了"由谁说了算？

最直觉的方案是引用计数（每被引用一次 +1，减到 0 就回收），但它有个致命伤——**循环引用**：

```
a.field = b;
b.field = a;
a = null;
b = null;
// 两个对象互相拉着对方，计数永远是 1，但外界再也够不着 → 永远回收不掉
```

JVM 的选择是**可达性分析**：好比判断一间黑屋里有没有活人，不去数屋里的人（他们可能互相握手装热闹），而是**看有没有一条路能让外面的人走进去**——从"根"出发摸得到的才算活着。

## 核心要点

### 一、可达性分析：从 GC Roots 出发

GC Roots 通常包括：

- 虚拟机栈中栈帧的**局部变量**（方法参数、临时变量）
- 方法区中的**类静态变量**
- 方法区中的**常量**（如字符串常量池里的引用）
- **JNI 句柄**（native 方法引用的对象）

```
GC Roots
├── 栈帧局部变量 ──► objA ──► objB        可达 → 存活 ✅
├── 静态变量     ──► objC                  可达 → 存活 ✅
├── 常量         ──╳（引用已断）           不可达 ❌
└── JNI 句柄     ──► ...

孤立环：objD ⇄ objE （互相引用，但从任何根都摸不到）
        引用计数：俩都活着 ❌
        可达性分析：不可达，一起回收 ✅
```

引用四级别（"多积极回收"的精细控制）：

| 引用级别 | 什么时候回收 | 典型用途 |
| --- | --- | --- |
| 强引用 | 只要可达就永不回收 | 普通赋值 `Object o = new Object()` |
| 软引用 | 内存不足时才回收 | 内存敏感的缓存 |
| 弱引用 | 下次 GC 必回收 | WeakHashMap、ThreadLocal 的 Entry |
| 虚引用 | 随时回收，只拿回收通知 | 堆外内存回收通知（DirectByteBuffer） |

### 二、三大基础算法对比

```
① 标记-清除 Mark-Sweep
   [活██][死░][活██][死░░][活██]
   标记所有活对象 → 其余整体清空
   ✔ 简单           ✘ 碎片多（大对象放不下 → 提前触发下一轮 GC）

② 标记-复制 Copying
   ┌───────────┬───────────┐        ┌───────────┬───────────┐
   │ 活死混杂的  │    空     │ 复制 → │  整块清空  │ 活██活██  │
   └───────────┴───────────┘        └───────────┴───────────┘
   存活的复制到另一半 → 旧区整块清零
   ✔ 无碎片         ✘ 浪费一半空间；存活多时复制开销大
   → 适合"朝生夕死、存活极少"的新生代

③ 标记-整理 Mark-Compact
   [活██][死░][活██][死░]  活的往一端挪  →  [活██活██][ 空  ]
   ✔ 无碎片         ✘ 要移动对象并更新所有引用，成本高
   → 适合"存活率高"的老年代
```

### 三、分代收集：算法按区域组合

```
新生代：绝大多数对象活不过第一轮 Minor GC（存活率极低）
        └─►【标记-复制】：Eden + 两块 Survivor，只需复制那一小撮幸存者，代价小

老年代：能熬到这的都是"钉子户"（存活率高）
        └─►【标记-清除】（CMS）或【标记-整理】（G1 / Parallel Old）
```

### 四、收集器演进时间轴

```
Serial ───► Parallel ───► CMS ───► G1 ───► ZGC
串行         并行           并发       区域化     亚毫秒
单线程全停顿  多线程全停顿    标记/清除与  停顿可预测   几乎全程并发
                            用户线程并发

一句话定位：
Serial    串行，单核小内存客户端模式，简单省心
Parallel  并行，吞吐量优先（JDK8 默认），适合后台批处理
CMS       首个并发低停顿收集器；有碎片+浮动垃圾+并发失败，JDK14 已移除
          （ParNew 是配合 CMS 的年轻代版本，随 CMS 一起退场）
G1        堆切成 Region，优先收垃圾最多的，停顿时间可设目标（JDK9 起默认）
ZGC       着色指针 + 读屏障，停顿 <10ms 走到亚毫秒级，撑 TB 级大堆
```

### 五、G1：Region 化 + 停顿时间可预测

```
物理上连续的新生代/老年代没了，取而代之：
整个堆切成约 2048 个等大 Region（1~32MB），角色动态分配

┌────┬────┬────┬────┬────┬────┬────┐
│ E  │ S  │ O  │ H  │ ◻  │ E  │ O  │   E=Eden  S=Survivor
├────┼────┼────┼────┼────┼────┼────┤   O=Old   H=Humongous（大对象占连续多个）
│ O  │ ◻  │ O  │ E  │ S  │ ◻  │ O  │   ◻=空闲
└────┴────┴────┴────┴────┴────┴────┘

回收思路（面试核心句）：
① G1 跟踪每个 Region 的"回收价值"= 能腾出的空间 / 需要花费的时间
② 每轮按 -XX:MaxGCPauseMillis=200 的停顿预算，
   优先收集【垃圾占比最高】的那批 Region —— 少干活、多腾地
③ 停顿时间从"看天吃饭"变成"可设置的目标"
④ 整体是标记-整理、Region 之间是复制 → 不产生碎片
```

### 六、CMS：四阶段与三大缺点

```
① 初始标记  ─ STW（短）：只标 GC Roots 直连的对象
② 并发标记  ─ 与用户线程并发：沿引用链遍历全堆（最耗时但不暂停）
③ 重新标记  ─ STW（较短）：修正并发期间用户线程造成的引用变动
④ 并发清除  ─ 与用户线程并发：清掉垃圾

时间轴：  ▂①▂ ━━━━②━━━━━━ ▂③▂ ━━━━④━━━━━━
GC线程    工作  并发标记      工作  并发清除
用户线程   暂停 ─────运行───── 暂停 ─────运行─────

三大缺点（必背）：
1. 标记-清除 → 碎片：大对象放不下 → 提前 Full GC，甚至退化 Serial Old
2. 浮动垃圾：并发阶段用户线程新产生的垃圾，本轮收不掉，只能下轮
3. 并发失败：老年代预留空间不够并发期间分配用 → Concurrent Mode Failure
   → 全停顿退化为 Serial Old 整理，体验断崖式下跌
```

### 七、三色标记与漏标（并发标记的底层原理）

```
白 = 未访问    灰 = 自己扫完、成员没扫完    黑 = 完全扫完
并发标记时用户线程还在改引用：
黑对象新指向了白对象，但又没被重新扫到 → 漏标 → 活对象被误回收 ❌

解决思路：写屏障拦截所有引用变动
  CMS → 增量更新：记录"黑→白"的新引用，重新标记阶段重扫
  G1  → SATB：标记开始时拍快照，快照里的引用关系一律按活算
```

下面逐步推演经典漏标场景（初始引用：A.field=B，B.field=C）：

```
时刻 | GC 标记线程                    | 用户线程                        | 对象颜色状态
 t1  | 扫完 A：A 涂黑；A.field=B → B 入灰队列 |                                | A=●黑  B=◐灰  C=○白
 t2  |                                | A.field = C;  B.field = null    | A=●黑  B=◐灰  C=○白
     |                                | （引用从 B 挪到 A）              | （A.field 已指 C，但 A 已黑不会再扫）
 t3  | 继续扫 B：B.field = null       |                                | A=●黑  B=●黑  C=○白
     | → B 无引用指向 C → C 保持白     |                                |
 t4  | 标记结束 → 所有白色对象回收     |                                | C 被回收 ❌
     |                                |                                | 但 A.field 还指着 C → 悬空指针！

──────────────────────────────────────────────────────────────────────────
写屏障如何拦截 t2 的引用变动：

  增量更新（CMS）：A.field = C 触发写屏障
    → 发现 A 是黑、C 是白 → 把 A【重新标灰】
    → t3 重新扫 A 时扫到 C → C 标灰 → 存活 ✅
    拦截点：【新引用 A→C 的建立】

  SATB（G1）：B.field = null 触发写屏障
    → 记录被删除的旧引用 B→C（"快照里活着的一律按活算"）
    → C 被加入待标记集合 → 存活 ✅
    拦截点：【旧引用 B→C 的删除】
```

### 八、Minor GC / Full GC 触发条件

| 类型 | 触发条件 | 特点 |
| --- | --- | --- |
| Minor GC | Eden 区写满 | 频繁但快（幸存者少、复制量小）；有 STW 但时间短 |
| Full GC | ① 老年代空间不足 ② 元空间不足 ③ 晋升失败/担保失败 ④ `System.gc()`（建议式） | 又慢又伤吞吐，频繁出现必须排查 |

### 九、调优思路

- **先定目标**：吞吐优先（批处理 → Parallel + 大新生代）还是停顿优先（在线服务 → G1/ZGC；G1 自适应强，别乱动参数）
- **再看日志**：`-Xlog:gc*`（JDK9+）观察 GC 频率与单次耗时——频率高说明对象活得久（泄漏/缓存滥用），单次长说明活对象太多
- **大方向**：让对象"朝生夕死"尽快死掉、防内存泄漏和大对象进老年代；Full GC 频繁先查根因（元空间不足 / 晋升失败 / 显式调用），不是无脑加内存

## 面试答法

### 30 秒版（可背诵）

> 判断对象死亡主流用可达性分析：从 GC Roots 出发——栈帧局部变量、静态变量、常量、JNI 句柄——沿引用链遍历，摸不到的对象就可回收，循环引用也不受影响；引用计数因为解决不了循环引用，Java 没采用。基础算法三种：标记-清除快但有碎片；标记-复制无碎片但浪费空间，适合存活少的新生代；标记-整理无碎片但要移动对象，适合老年代。收集器从 Serial 到 Parallel 到 CMS 到 G1 再到 ZGC，分别对应串行、并行吞吐、并发低停顿、区域化可预测停顿、亚毫秒停顿。G1 把堆切成等大 Region，优先回收垃圾最多的区域，能在停顿目标内干活，JDK9 后是默认收集器；CMS 是低停顿先驱，但有碎片、浮动垃圾和并发失败退化问题。调优先看 GC 日志，分清频率问题还是耗时问题，再定吞吐或低停顿方向。

### 深入版（编号答题线索）

1. **判活**：引用计数的循环引用缺陷 → 可达性分析 + GC Roots 清单 → 引用四级别收尾
2. **算法**：三图对比 → 按分代组合：新生代复制、老年代整理/清除
3. **演进**：时间轴串起五代收集器，每一代讲清"解决了上一代的什么痛点"
4. **重点展开 G1**：Region 化、回收价值排序、停顿目标；对比 CMS 四阶段 + 三缺点
5. **原理加分**：三色标记、写屏障、增量更新 vs SATB
6. **落地**：Minor/Full GC 触发条件表 + "先看日志、先定目标"的调优方法论

### 常见追问

- **为什么新生代不用标记-整理？** → 新生代存活极少，复制算法只需复制那一小撮；整理要移动大量对象反而亏，所以整理留给存活率高的老年代
- **G1 和 CMS 本质区别？** → G1 基于整理（Region 间复制）无碎片且停顿可预测；CMS 是标记-清除，有碎片和并发失败风险
- **什么是浮动垃圾？** → 并发标记/清理期间用户线程新产生的垃圾，本轮处理不了，留到下一轮才能回收
- **对象什么时候直接进老年代？** → 大对象超过 `-XX:PretenureSizeThreshold`、年龄到阈值（默认 15）、动态年龄判断、Survivor 放不下
- **System.gc() 一定会 Full GC 吗？** → 默认触发（建议式），可用 `-XX:+DisableExplicitGC` 禁掉；但 NIO 堆外内存依赖它通知回收，更稳妥的是配 `-XX:+ExplicitGCInvokesConcurrent`
