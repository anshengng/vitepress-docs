# JVM 调优思路与常用参数

## 题目

> 你是怎么做 JVM 调优的？GC 日志怎么看？常用的 JVM 参数有哪些？举一个你实际调优的案例。

## 为什么需要

先破题：**调优不是背参数，是带着指标找瓶颈**。内存区域和 GC 算法是基础（见[内存区域篇](./memory-model.md)、[GC 篇](./gc.md)），调优就是在这之上做"资源再分配"。而且三个目标互相牵制，不可能全都要：

```
            低停顿（接口 RT 稳）
              ▲
             ╱ ╲
        牺牲吞吐 ╲ 牺牲
          换取 ▼ ▼ 换取
   高吞吐（GC 占总时间少）◄──► 少占用（堆越小越好）

 例：堆调大 → Full GC 频率降低（吞吐↑）但单次停顿更久（停顿↑）且占用↑
 例：CMS/G1 低停顿 → 并发标记占 CPU（吞吐↓）
→ 先定目标，才知道往哪个方向调
```

## 核心要点

### 调优标准流程（面试先说这个）

```
┌─► ① 定目标：低停顿 or 高吞吐？量化指标（如 P99 < 200ms、GC 占比 < 5%）
│     │
│   ② 采集证据：GC 日志 + 监控（Prometheus/Grafana）+ jstat
│     │
│   ③ 定位瓶颈：什么 GC？频率×耗时？哪块区域异常？
│     │
│   ④ 两类手段：改代码（内存泄漏/大对象/缓存滥用）> 调参数
│     │
│   ⑤ 压测验证：对比调优前后指标
│     │
└── 没达标 → 回到 ①（循环）；达标 → 固化参数 + 写入文档
```

### GC 日志怎么读

一段 G1 的 Young GC 日志，逐字段拆解：

```
[GC pause (G1 Evacuation Pause) (young), 0.0234567 secs]
   │                              │        │
   │                              │        └─ 本次停顿 23ms ← 看"耗时"
   │                              └─ GC 类型+触发原因 ← 看"什么GC、为什么"
   └─ 发生了停顿

[Eden: 512M(512M)->0B(512M) Survivors: 64M->64M Old: 300M->302M  3072M->302M]
    │  │    │      │                                              │      │
    │  │    │      └─ 回收后                      回收前 3072M ───┘      └─ 回收后
    │  └─ 回收了 512M，腾出最多 → 有效 GC ✅
    └─ Old 300M→302M：老年代还在涨，涨不停=有对象持续晋升（警惕泄漏/ Survivor 太小）
```

**判断标准 + 频率×耗时四象限：**

```
                       耗时长
                         │
     ② 频繁且长          │        ① 偶尔且长
     最危险：先查大对象/  │   可接受：大堆正常 Full GC，
     泄漏，可能是元空间满 │   或定时任务触发，观察即可
 频繁 ──────────────────┼────────────────── 偶尔
     ③ 频繁且短          │   ④ 偶尔且短
     新生代偏小：Young    │   健康 ✅
     GC 几秒一次 → 调大   │
                         │
                       耗时短

Minor GC 频繁 = 新生代太小；Full GC 频繁/耗时长 = 老年代或元空间出问题
```

### 常用参数速查表（按场景分组）

| 场景 | 参数 | 说明 |
| --- | --- | --- |
| 堆大小 | `-Xms` / `-Xmx` | 初始/最大堆。**建议相等**，避免运行期扩容缩容抖动 |
| 新生代 | `-Xmn`、`-XX:SurvivorRatio=8` | 新生代大小；Eden 与单个 Survivor 之比 8:1:1 |
| 元空间 | `-XX:MetaspaceSize=256m` | 达到阈值触发 Full GC，设太小会频繁 FGC |
| GC 选择器 | `-XX:+UseG1GC`、`-XX:+UseParallelGC`、`-XX:+UseZGC` | G1 大堆低停顿 / Parallel 吞吐优先 / ZGC 超低停顿 |
| GC 日志 | `-Xlog:gc*:file=gc.log`（JDK9+）<br>`-XX:+PrintGCDetails`（JDK8） | 生产必开，只留最近几份，否则磁盘被吃光 |
| OOM 现场 | `-XX:+HeapDumpOnOutOfMemoryError`<br>`-XX:HeapDumpPath=/data/dump` | OOM 自动 dump，排查入口见[OOM 排查篇](./oom-troubleshoot.md) |

### 三大典型场景案例

#### 案例 1：高峰期 Young GC 飙升

```
现象：晚高峰 Young GC 从 30s 一次 → 3s 一次，每次 20ms（频繁且短 → 四象限③）
日志：Survivor 使用率 100%，Survivors 回收前后几乎没腾出 → 存活对象多
推理：Survivor 太小 → 一次 Minor GC 存活对象装不下 → 提前晋升 Old
     → Old 涨快 → 引发更糟的 Full GC（连锁反应）
处理：调大新生代 -Xmn，或 -XX:SurvivorRatio=8 改成 4（Survivor 各占更大）
     让对象在 Survivor 里多熬几轮，死在年轻代
验证：Young GC 间隔恢复到 20s+，Old 增长速率明显放缓 ✅
```

把整个恶性循环放到时间线上逐步推演，连锁反应就很直观了（旧参数：新生代 1g、SurvivorRatio=8，S 区仅 10% = 100M）：

```
时间      请求/分配速率          Young GC 频率       Survivor(仅100M)        老年代走势
09:00  平峰 130M/s             10 次/分          回收后 S0=50%           平稳 300M
       Eden(800M) 约 6s 填满          (6s 一次)         50M 存活对象装得下       零晋升
09:15  秒杀开始 流量 ×8               80 次/分          回收后 S0=100% 打满        开始爬升
       分配速率 1000M/s             (0.75s 一次)      150M 存活对象装不下    首次溢出晋升
09:30  高峰持续 流量 ×20              200 次/分          每次 GC 溢出 150M       陡涨 ⚠
       分配 2600M/s，Eden 0.3s 填满      (0.3s 一次)       溢出部分 → 直接进 Old    每次都大量晋升
10:00  ── 恶性循环成型：Eden 填得更快 → Young GC 更频繁 → 存活对象在两轮 GC 间来不及死 → 晋升更多更大 → Old 加速逼近占满 → 即将触发 Full GC 连锁 ──

调优后同一时间轴（新生代 ×3 + SurvivorRatio 8→4，S 区 500M = 绝对容量 ×5）：

时间      Young GC 频率       Survivor(500M)        老年代走势
09:15  30 次/分            回收后 S0=30% 装得下  +2M/分（极少晋升）
09:30  75 次/分            回收后 S0=50% 装得下  +5M/分
10:00  70 次/分 ✅ 稳住         回收后 S0=48%            老年代平稳，循环破掉
       频率降到调优前约 1/3 = Eden 更大、更久才填满   存活对象全在 Survivor 装下，死在年轻代
```

#### 案例 2：每小时一次 Full GC，停顿数秒

```
现象：Full GC 固定周期出现，单次 3~5s（频繁且长 → 四象限②最危险）
分叉排查：
 ├─ 日志显示 Metadata 区接近 MetaspaceSize → 元空间太小：
 │    动态类生成（CGLIB/反射）撑爆 → 调大 -XX:MetaspaceSize=256m
 └─ 日志显示 Old 回收后只降一点点 → 老年代缓慢增长：
      ├─ 回收后 Old 稳定在低位 = 缓存/对象太大 → 限制缓存上限
      └─ 回收后 Old 持续走高 = 泄漏 → 拿 dump 用 MAT 找支配树（见 OOM 排查篇）
```

把每小时的锯齿搬上时间轴，两种形态并排放，"泄漏还是配置不足"一眼可辨——重点看锯齿的"谷底"和"跳变点"：

```
时刻     曲线 A：老年代缓慢爬升（泄漏嫌疑）              曲线 B：老年代阶梯式跳涨（配置嫌疑）
08:00    Full GC → Old 回落到 300M ✅                     Full GC → Old 回落到 300M ✅
         之后以 3M/分 爬升                                  之后平稳（无动静）
09:00    Old 爬到 480M → 触发 Full GC                      09:15 大查询结果 600M 涌入 Old
         回收后只降到 340M ⚠ 谷底抬高 40M                    Old：300M → 900M（阶梯跳涨）
10:00    Old 爬到 520M → Full GC                           09:16 触发 Full GC → 回落到 300M ✅
         回收后只降到 395M ⚠ 谷底又抬高 55M                      跳涨部分全回收（短命对象为主）
11:00    谷底轨迹 300→340→395M 逐级抬升                     10:40 下一次大查询跳到 900M，Full GC 后又回落
         没有大操作，水位却稳步上抬                          跳变点与大查询对得上，谷底恒为 300M
12:00    谷底爬到 455M，照此趋势半天后逼近 Old 上限          依旧 300M，跳涨/回落节奏规律稳定
─── 用锯齿形态区分泄漏 vs 配置不足 ───────────────────────
  曲线 A 谷底逐级抬高 = 每轮 GC 都有一批对象活着收不回 → 泄漏，拿 dump 查 MAT 支配树
  曲线 B 谷底持平、跳变点对应大查询/发布 = 一次性占用涌入 → 容量/配置不足，分页查询、限缓存解决
  特殊：Full GC 成因是 Metadata GC Threshold → 病根不在 Old，元空间太小，调大 -XX:MetaspaceSize
  一句话口诀：谷底走高防泄漏，跳变对事查容量，成因看日志里的触发原因
```

#### 案例 3：G1 大对象（humongous）频繁

```
现象：G1 日志频繁出现 "Humongous Allocation"，甚至并发标记周期被频繁触发
原理：对象 > Region/2 就算大对象，直接进老年代连续 Region，回收代价高
     （典型元凶：一次加载几十万行的查询结果、超大 byte[]）
处理：两条路
 ├─ 调大 Region：-XX:G1HeapRegionSize=16m（让对象不再算"大"）
 └─ 改代码（更治本）：分页查询、流式读取，把大对象拆小 ✅
```

### G1 专属参数

- `-XX:MaxGCPauseMillis=200`：目标停顿，G1 据此动态调整每次回收的 Region 数。**不是设小就真停 20ms**——太小会牺牲吞吐、且回收不过来反而更频繁
- `-XX:G1HeapRegionSize`：Region 大小（1~32MB），堆/2048 自动算
- 什么时候别用 G1：小堆（< 4~6GB，Parallel 更简单高效）、极致吞吐场景、超大堆 + 超低停顿需求可直接上 ZGC

### 容器环境注意

```
Docker 内存 limit = 4G
├─ ❌ -Xmx4g：堆顶满 4G，加上元空间/线程栈/堆外/direct memory → OOMKilled
└─ ✅ -Xmx3g 留 1G 余量：JVM 总耗内存 ≈ 堆 + 元空间 + 栈×线程数 + 堆外

JDK 8u191+ 默认感知 cgroup 限额（-XX:+UseContainerSupport），
旧版本会读到宿主机内存，把 128G 宿主机当 128G 容器 → 默认堆直接爆 limit
```

## 面试答法

### 30 秒版（可背诵口语）

> 我的调优思路是先说流程再谈参数。第一步定目标，低停顿、高吞吐、少占用三者互相牵制，得先定量化指标比如 P99 小于两百毫秒。第二步开 GC 日志和监控采集证据。第三步用频率乘耗时四象限定位瓶颈：频繁且短说明新生代太小，频繁且长最危险，要查大对象或者泄漏。第四步优先改代码，参数只是辅助，比如分页查询拆掉大对象比调 Region 更治本。第五步压测验证，对比前后指标，没达标就循环。举个实际例子：我们服务晚高峰 Young GC 从三十秒一次飙到三秒一次，日志里 Survivor 打满、对象提前晋升，我把新生代和 Survivor 调大之后，Young GC 间隔恢复，老年代增长也放缓了。最后强调一点：参数是最后手段，代码问题和容量规划才是根因。

### 深入版（被追问时按这条线展开）

1. **破题**：调优 = 带着指标找瓶颈，三目标牵制图先立住
2. **流程**：定目标 → 读日志 → 定位 → 改代码/调参 → 压测，闭环循环
3. **读日志**：逐字段拆一条日志，抛出四象限判断法
4. **案例**：讲一个自己经历过的（案例 1/2/3 任选），现象 → 日志证据 → 推理 → 动作 → 验证，有始有终
5. **收尾**：容器留余量的细节 + "参数是最后手段"，体现克制和工程素养

### 常见追问

- **-Xms 和 -Xmx 为什么建议设相等？** → 避免堆动态伸缩带来的 GC 抖动和内存申请开销
- **MetaspaceSize 是元空间上限吗？** → 不是，是首次触发 Full GC 的阈值；上限是 `MaxMetaspaceSize`，不设则只受物理内存限制
- **线上怎么快速看 GC 情况？** → `jstat -gcutil <pid> 1000` 看各代使用率和 GC 次数/耗时
- **MaxGCPauseMillis 设 10ms 会怎样？** → G1 每次只敢回收很少 Region，垃圾回收速度赶不上产生速度 → 垃圾堆积 → 退化为更频繁更长的 GC
- **怎么确认内存泄漏？** → 老年代回收后水位一次比一次高 + dump 文件对比，MAT 看支配树和引用链（详见[OOM 排查篇](./oom-troubleshoot.md)）
- **什么时候用 ZGC？** → JDK17+、堆 10GB 以上、要求停顿 < 1ms 且能接受少量吞吐损失；线上需评估分代 ZGC 的成熟度
