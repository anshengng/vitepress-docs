# CAS 原理与原子类

## 题目

> CAS 是什么？AtomicInteger 为什么不加锁也能保证原子性？ABA 问题是什么，怎么解决？LongAdder 为什么比 AtomicLong 快？

## 为什么需要 CAS

`i++` 是"读→改→写"三步复合操作，两个线程交错执行会丢更新（双线程丢更新时间线详见 volatile 篇）。

```
方案一：volatile     → 只保证可见性，防不了三步交错，丢更新照旧 ❌
方案二：synchronized → 原子性 ✅，但读个数字也要加锁、可能阻塞线程，太重 ❌
方案三：CAS          → 不挂起线程，冲突了就重试，轻量级原子操作 ✅
```

生活化类比：CAS = 抢会议室——进门先看白板上写的还是不是"空闲"，是就当场把"空闲"擦成"占用"再进去；发现已被人改成"占用"，就重新观察再试一次，而不是蹲在门口睡觉（阻塞）。

## 核心要点

### CAS 语义：compareAndSwap

三个操作数：**内存值 V、期望值 E、新值 N**。仅当 `V == E` 时才把 V 写成 N；否则什么都不做并返回失败。"比较 + 交换"由 CPU 一条指令保证不可分。

```
单线程视角（目标是把 5 改成 6）：

 成功路径                          失败路径
┌──────────────────────────┐    ┌──────────────────────────┐
│ 读到期望值 E = 5           │    │ 读到期望值 E = 5           │
│ 此刻内存 V == 5 ?          │    │ 此刻内存 V == 6（被人改了） │
│   是 → 写入 N = 6  ✅      │    │   否 → 放弃写入，返回失败 ❌│
└──────────────────────────┘    └──────────────────────────┘
```

### 模拟两个线程 CAS 同一变量 i（初始 0，各做一次 +1）

```
时刻   T1                                T2                     i
 t1    读 i = 0（E=0），算出 N=1
 t2                                      读 i = 0（E=0），算出 N=1
 t3    CAS(0→1)：V==E==0，写入 ✅                                  0→1
 t4                                      CAS(0→1)：V=1 ≠ E=0 ❌ 失败
 t5                                      失败不阻塞 → 自旋：重读 E=1
 t6                                      CAS(1→2)：V==E==1 ✅          1→2

结果 i = 2，正确！T2 第一次 CAS 输给 T1，靠【自旋重试】扳回来。
关键：CAS 失败 ≠ 阻塞，而是"发现有人抢先 → 重读最新值再试"。
```

### 底层实现一句

`Unsafe.compareAndSwapInt` 底层对应 x86 的 `lock cmpxchg` 指令：lock 前缀保证多核下"比较+交换"不可分；现代 CPU 只锁该变量所在的缓存行（**缓存锁**），而不是锁整个总线，开销小得多。

### AtomicInteger.incrementAndGet：自旋代码示意

```java
public final int incrementAndGet() {
    for (;;) {                              // ① 自旋
        int current = get();                // ② 读当前值作为 E
        int next = current + 1;             // ③ 算出新值 N
        if (compareAndSet(current, next))   // ④ CAS：E 仍是最新才写入
            return next;                    // ⑤ 成功返回
    }                                       //    失败 → 回到①重读重试，绝不阻塞
}
```

### CAS 三大问题

| 问题 | 现象 | 解法 |
| --- | --- | --- |
| ① ABA | 值变走又变回，CAS 察觉不到中间变化 | AtomicStampedReference 加版本戳 |
| ② 自旋开销 | 长期 CAS 失败空转，白烧 CPU | 高竞争计数改用 LongAdder 分流 |
| ③ 只能保证单变量 | 一次 CAS 只原子改一个变量 | AtomicReference 打包成对象 / 加锁 |

#### 问题① ABA：完整时间线

```
共享变量 x 初始 A；T1 要做"确认还是 A 就改成 C"

时刻   T1                          T2（频繁存取）            x
 t1    读 x = A（E=A，N=C）
 t2                                CAS：A → B ✅             A→B
 t3                                CAS：B → A ✅             B→A
 t4    CAS(A→C)：V==E==A ✅                                 A→C

T1 以为"期间没人动过"，其实中间经历了 A→B→A。
纯数字场景无伤大雅；但无锁栈/链表里，"引用还是那个引用，
对象可能已被删除又复用"——按旧引用操作就出事了。
```

#### ABA 解法：AtomicStampedReference 版本戳

```
不带戳：T1 期望 (A) ──┐   实际历史：A(v1) → B(v2) → A(v3)
                      ├── 值相等 → CAS 成功 ❌（错过了中间变化）

带戳：  T1 期望 (A, v1)，实际是 (A, v3)
                      └── 值相等但版本戳不等 → CAS 失败 ✅（识破 ABA）
```

`AtomicMarkableReference` 是简化版：只用一个 boolean 标记代替版本号。

#### 问题②③ 简述

- **自旋开销**：竞争激烈时大量线程 CAS 失败空转，CPU 100% 却没干活；极限场景下反而不如直接加锁（挂起让出 CPU）。
- **只能保证单变量**：`AtomicReference` 把多个变量包成一个对象再整体 CAS；字段多了仍要靠锁。

### LongAdder 为什么更快

```
AtomicLong：所有线程挤同一个 value 单点 CAS

  T1 ─┐
  T2 ─┼──► 全部 CAS 同一个 value ──► 失败自旋再挤
  T3 ─┘     缓存行在核间来回失效，越挤越慢 ❌

LongAdder：base + Cell[] 分段累加

  无竞争 → 直接 CAS base
  有竞争 → 各线程按 hash 散列到不同 Cell，各改各的槽位

  T1 ──► Cell[0] += 1   ┐
  T2 ──► Cell[1] += 1   ├── 不同槽位互不碰撞，并行累加 ✅
  T3 ──► Cell[2] += 1   ┘

  sum() = base + Cell[0] + Cell[1] + Cell[2] + ...
```

代价：`sum()` 是**非精确快照**——汇总时别的线程可能还在写自己的 Cell，拿到的是"加总瞬间"的近似值（对统计计数无所谓，对精确序列号是致命的）。

### AtomicLong vs LongAdder 选型

| 对比 | AtomicLong | LongAdder |
| --- | --- | --- |
| 原理 | 单 value 自旋 CAS | base + Cell[] 分段，空间换时间 |
| 高并发写性能 | 差（单点竞争） | 好（热点分散） |
| sum()/get() | 精确即时值 | 近似快照，读时需遍历求和 |
| 典型场景 | 序列号生成、需要精确读改写 | QPS 打点、监控计数等纯累加统计 |

## 面试答法

### 30 秒版（可背诵口语）

> CAS 是硬件级的原子操作，三个操作数：内存值 V、期望值 E、新值 N，只有 V 等于 E 才写入，否则失败，底层是 lock cmpxchg 指令加缓存锁。AtomicInteger 的 incrementAndGet 就是自旋：读旧值、算新值、CAS，失败了重读重试，不加锁也不阻塞线程。它有三个问题：ABA 用 AtomicStampedReference 版本戳解决；自旋空转让高竞争计数换 LongAdder；还有只能保证单变量原子。LongAdder 把一个 value 拆成 base 加 Cell 数组，线程散列到不同格子各改各的，sum 时再汇总，所以高并发写比 AtomicLong 快，代价是 sum 是近似快照。

### 深入版（被追问时按编号展开）

1. **引出问题**：i++ 三步交错丢更新（一句带过，详见 volatile 篇）；synchronized 能解但太重
2. **CAS 语义**：V/E/N，画单线程成功/失败两条路径
3. **双线程时间线**：T1 赢、T2 失败后自旋重试成功——"失败不阻塞、重读再试"
4. **底层**：lock cmpxchg + 缓存锁，不是总线锁
5. **三大问题**：ABA 时间线 + 版本戳；自旋空转；单变量限制
6. **LongAdder**：单点竞争 vs 分段分流图，sum 非精确的代价
7. **选型收尾**：要精确读改写用 AtomicLong，纯高并发计数用 LongAdder

### 常见追问

- **CAS 和锁的本质区别？** → 锁失败会挂起（ park 让出 CPU），CAS 失败自旋重试（不挂起但烧 CPU）；低竞争 CAS 完胜，极高竞争锁反而稳
- **ABA 在什么场景真的会出事？** → 无锁数据结构：节点被弹出又复用，旧引用 CAS 上去，操作的是"同名不同命"的对象；纯数值计数无碍
- **为什么缓存锁比总线锁快？** → 只锁变量所在缓存行，别的核照样读写内存其他区域；总线锁则全核访存全部串行
- **AtomicInteger 的 value 有 volatile 吗？** → 有，保证 get 读到最新值，配合 CAS 使用
- **LongAdder 什么时候会退化？** → Cell 数组极小或 hash 撞车时仍会撞同一个格子，但概率远低于单 value
