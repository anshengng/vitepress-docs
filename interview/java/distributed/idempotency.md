# 接口幂等设计

## 题目

> 什么是幂等？为什么会产生重复请求？你项目里下单/支付接口怎么做幂等？Token 机制讲一下？MQ 消费重复了怎么办？

## 为什么会重复——先看清"敌人"

**幂等**：同一个操作执行一次和执行多次，对资源产生的影响相同。`set age=20` 幂等；`age=age+1` 不幂等。

重复请求不是用户手残这么简单，三条主要来源：

```
① 用户连点/重复提交：点了没反应，再点一次 → 两个请求
② 网络超时重试（最隐蔽）：
   时刻  客户端                 服务端
    t1   POST 扣款 ──────────►  收到，执行成功 ✅
    t2   等待响应…               响应在回程路上丢了 💥
    t3   ⏰ 超时，自动重试 ───►  又执行一次扣款 ❌❌
       （请求"看起来"失败，实际"已经"成功 → 重试即重复）
③ MQ 重投：消费成功但 ack 丢了 /  rebalance → Broker 再投一遍
```

HTTP 方法天然幂等表：

| 方法 | 幂等？ | 说明 |
| --- | --- | --- |
| GET | ✅ | 只读 |
| PUT | ✅ | 用请求体整体覆盖（put 同一个值多次结果相同） |
| DELETE | ✅ | 删一次和删多次，结果都是"没了" |
| POST | ❌ | 每次调用可能新建资源，**幂等设计主要对付它** |
| PATCH | ❌ | 局部更新，语义不保证 |

## 核心要点：六种方案逐个图解

### ① 数据库唯一索引 —— 最后一道闸

```
order_item 表： UNIQUE KEY uk_order_no (order_no)

第一次 INSERT order_no='A001' ✅ 成功
第二次 INSERT order_no='A001' → Duplicate entry ❌ 被拦下
捕获 DuplicateKeyException → 返回"已处理"而非报错

图解：唯一索引 = B+ 树里该 key 只允许一个叶子位置，
      第二条在插入定位时直接撞锁冲突。
优点：零依赖、绝对可靠；缺点：只防 insert，防不了 update 类重复
```

### ② Token 机制 —— 流程图 + 并发抢 token 时间线

```
流程：
┌──────┐ ① 申请token   ┌──────────┐ ② 存 uuid→token ┌───────┐
│ 客户端 │────────────►│ 服务端     │────────────────►│ Redis │
└──────┘  拿到 token   └──────────┘                  └───────┘
③ 业务请求携带 token
④ 服务端原子校验并删除 token：存在→放行执行；不存在→拒绝（重复请求）

两个并发请求抢同一个 token：
时刻  请求A(第一次)          请求B(用户连点/重试)        Redis: token
 t1   带 token=T 到达
 t2                         带 token=T 到达
 t3   Lua: EXISTS+DEL 原子 → ✅ token 是 A 的，执行业务
 t4                         Lua: EXISTS+DEL → token 已没了 ❌ 拒绝
                            （没有原子性：A、B 都 EXISTS 成功 → 双双放行）
```

- 关键：**校验和删除必须一步完成**（Lua 或 Redisson），否则并发下 token 会被用两次
- 缺点：多一次申请 token 的交互；token 过期时间要覆盖用户操作时长

### ③ 乐观锁版本号 —— update 天然去重

```
库存扣减：
UPDATE stock SET count=count-1, version=version+1
WHERE id=1 AND version=5;

第一次：version 匹配 → 影响行数 1 ✅
重复请求带着旧 version=5 再来 → 匹配不到 → 影响行数 0 ❌ 识别为重复
（也可用状态字段代替 version：WHERE status=0）
```

### ④ 状态机 —— 订单只许单向流转

```
待支付 ──支付──► 已支付 ──发货──► 已发货 ──签收──► 已完成
  ▲______❌ 任何逆向/跨级跳转一律 UPDATE ... WHERE status=期望前态 拦掉

重复的"支付成功回调"：第二次回调时 status 已是"已支付"，
UPDATE ... SET status='已支付' WHERE order_no=? AND status='待支付'
→ 影响行数 0 → 判定重复，直接返回成功。
```

### ⑤ MQ 消费端去重

```
方案 A：消费前查 Redis  SETNX msgId 1 NX → 失败说明已消费过，直接 ack
方案 B：去重表 INSERT IGNORE consume_log(msg_id UNIQUE) → 0 行 = 重复
注意：setnx 成功但业务失败要删标记，否则消息永久丢失（配合重试次数上限）
```

### ⑥ 分布式锁实现幂等（一句话 + 缺点）

对业务键加锁串行化重复请求——**只解决并发重复，不解决先后重复**（锁释放后重试请求照样执行），必须配合"查执行记录"才完整；且引入锁的复杂度，一般不如 token/唯一索引直接。

### 幂等键怎么选

```
优先级：业务单号(订单号/流水号) > 客户端生成的请求ID > 用户ID+接口+参数指纹 > 时间戳 ❌
理由：时间戳每次重试都变，根本识别不出"同一个请求"；
      业务单号由"一次业务动作"唯一决定，重试时保持不变 ✅
```

### 方案选型表

| 场景 | 推荐方案 |
| --- | --- |
| 创建类（下单、开户） | 唯一索引（业务单号）+ 前端防重 |
| 支付/扣款接口 | Token 机制（防并发+先后重复） |
| 库存/余额增减 | 乐观锁版本号 / 状态机 |
| 状态流转类回调 | 状态机（WHERE 前态） |
| MQ 消费 | msgId + Redis setnx / 去重表 |
| 兜底（所有方案通用） | 唯一索引 + 对账 |

## 面试答法

### 30 秒版（可背诵口语）

> 幂等就是同一请求执行一次和多次效果相同。重复请求主要来自用户连点、超时重试——特别是请求已经执行成功但响应丢了，客户端以为失败就重试——还有 MQ 重投。设计思路统一是"给请求一个唯一标识（业务单号或 token），服务端处理前先原子判重"。具体方案：创建类用数据库唯一索引兜底；支付接口用 token 机制，先申请 token、处理时 Lua 原子校验删除，并发重复请求只有一个能抢到；增减类用乐观锁版本号或订单状态机，UPDATE 带前态条件、影响行数为 0 就是重复；MQ 消费端用 msgId 加 setnx 或去重表。幂等键要选业务单号这种重试不变的，别用时间戳。我们项目下单就是唯一索引加 token 双保险。

### 深入版（被追问时按编号展开）

1. **先讲清重复来源**：重点画"响应丢失→重试"时间线，说明为什么服务端"必须"防而不是客户端防
2. **HTTP 语义**：GET/PUT/DELETE 天然幂等，POST 不幂等
3. **统一思路**：唯一标识 + 原子判重（先查后写不原子，并发会双过）
4. **逐方案展开**：唯一索引 / token（画抢 token 时间线）/ 版本号 / 状态机 / MQ 去重 / 分布式锁（讲清缺点）
5. **幂等键选择**：业务单号优于时间戳的原因
6. **组合拳收尾**：前端置灰只是体验，服务端判重才是安全；唯一索引永远做最后兜底

### 常见追问

- **先 SELECT 判断存在再 INSERT，有问题吗？** → 并发下两个请求都 SELECT 不到 → 双插；要么唯一索引，要么锁/原子操作
- **token 校验通过但业务执行失败怎么办？** → 业务回滚时把 token 放回（或换新 token 重试），否则用户无法再次提交
- **重试请求带了新 token 怎么办？** → 幂等键应取业务单号而非 token；token 只防"同一提交动作"的重复
- **支付回调重复且乱序（先"退款成功"后"支付成功"）？** → 状态机 + 时间戳/流水号单调校验，逆向流转直接拒绝并告警
- **怎么验证幂等做没做对？** → 用同一请求重放测试（curl 重发、MQ 手动重投），断言只产生一次副作用
