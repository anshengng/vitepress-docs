# 分布式事务方案

## 题目

> 什么是分布式事务？CAP/BASE 是什么？常见的分布式事务方案有哪些，如何选型？你项目里是怎么落地的？

## 为什么需要分布式事务

单体应用：一个流程 = 一个库 + 一个 `@Transactional`，本地事务就能保证 ACID。

微服务拆分后：一个业务操作横跨**多个服务、多个数据库**，本地事务管不了别人家的库。

```
转账 100 元（A、B 已拆成两个服务，各用各的库）

账户A服务：update 余额 -100   ✅ 本地事务成功
账户B服务：update 余额 +100   ❌ 调用超时 / 宕机

→ 钱凭空消失，两边数据不一致
```

分布式事务要解决的就是：**让分散在多个库上的操作"要么都成功，要么都失败"**（或最终达成一致）。

## 理论基础：CAP 与 BASE

### CAP（三选二的真相）

| 字母 | 含义 | 说明 |
| --- | --- | --- |
| C 一致性 | 所有节点同一时刻数据相同 | 强一致 |
| A 可用性 | 请求永远能正常收到响应 | 不报错、不超时 |
| P 分区容错 | 节点间网络断了系统还能运行 | **必然要保**（网络不可靠是客观事实） |

- P 是必选项，所以真正的取舍是 **CP 或 AP**：
  - **CP**：ZooKeeper、etcd —— 网络分区时宁可拒绝服务（选主期间不可写），也要保证数据一致
  - **AP**：Eureka —— 分区时照常返回注册表（可能是旧数据），先保可用

### BASE（互联网场景的务实妥协）

- **B**asically **A**vailable 基本可用：高峰期砍掉非核心功能、允许响应变慢
- S**o**ft state 软状态：允许中间状态短暂不一致（订单已创建、积分还没到账）
- **E**ventually consistent 最终一致：过一段时间后，数据一定达成一致

一句话：**BASE = 放弃 ACID 的强一致，换取可用性 + 最终一致**。分布式事务方案基本都是围绕 BASE 设计的。

## 主流方案（按一致性从强到弱）

### 1. 2PC / XA —— 两阶段提交（同步强一致）

```
协调器(TM)                    参与者(RM，各数据库)
   |---- ① prepare：你们能提交吗 --->| 执行SQL但不提交，锁住资源，回 yes/no
   |<--- yes / no ------------------|
   |---- ② commit / rollback ------>| 正式提交或释放锁
```

三个硬伤（面试必答）：

1. **同步阻塞**：prepare 之后资源一直被锁，所有参与者干等协调器指令
2. **协调器单点故障**：TM 挂了，参与者锁着资源不知所措
3. **仍可能不一致**：② 阶段"commit"消息只送达一半（网络分区），就出现部分提交

- 应用：数据库自带的 XA 协议，传统银行等低并发、强一致场景；互联网高并发基本不用

### 2. TCC —— 业务层的两阶段提交

把"锁资源"从数据库层面搬到**业务代码层面**，每个服务提供三个接口：

```
Try     预留资源：A 账户冻结 100 元（钱还在，但不可用）
Confirm 真正执行：用冻结的钱完成扣款（幂等）
Cancel  释放预留：解冻 100 元（幂等）

正常：Try(A) → Try(B) 都成功 → Confirm(A) → Confirm(B)
异常：任何一个 Try 失败 → Cancel 已成功的分支
```

三个必考坑点：

| 坑 | 场景 | 解法 |
| --- | --- | --- |
| 空回滚 | Try 没执行成功，框架却发来 Cancel | Cancel 时先查 Try 的事务记录，没试过就直接标记返回 |
| 悬挂 | Cancel 先到、Try 后到（网络乱序），Try 白冻结了钱 | Try 时发现该事务已 Cancel，拒绝执行 |
| 幂等 | Confirm/Cancel 会被重试多次 | 用事务 ID + 状态机控制只执行一次 |

- 优点：不锁数据库资源、性能好、一致性强
- 缺点：**侵入大**，每个操作要写三个接口；适合支付、库存等资金核心链路

### 3. Seata AT —— 低侵入的自动补偿

TCC 要人肉写三个接口，Seata AT 让框架代劳（可理解为"自动版 TCC"）：

```
① 执行 SQL 前，自动记录数据快照 → undo_log（前像 + 后像）
② 执行业务 SQL，本地事务【立即提交】（很快释放行锁，这是与 2PC 最大的区别）
③ 全局成功 → 异步删 undo_log
   全局失败 → 拿快照生成反向 SQL 写回去（补偿）
④ 并发隔离靠【全局锁】：同一行数据，全局事务没结束前别人不能改
```

#### 模拟场景：两个线程改同一行

账户 `balance = 100`，两个全局事务并发操作这一行：

- **T1 转账事务**：扣 20 后，调用下游失败 → 需要全局回滚
- **T2 返现事务**：扣 30，正常提交

#### 模拟 A：只有 DB 行锁、没有全局锁 → 更新丢失

```
时刻  T1（转账）                       T2（返现）                  DB: balance
 t1   记 undo 前像=100
      update -20 ──[行锁]──► 80                                     100→80
 t2   本地事务提交 ✅ 行锁立刻释放
 t3                                   记 undo 前像=80
                                      update -30 ──[行锁]──► 50     80→50
 t4                                   本地事务提交 ✅ 行锁释放
 t5   下游失败 → 全局回滚：
      拿自己的前像 100 写回 ────────► balance=100                   50→100 ❌
```

结果：T2 的 30 元扣款**被 T1 的回滚覆盖**，钱凭空"长出"30。

**为什么 DB 行锁拦不住？** 行锁只在 update 语句执行的那一瞬间互斥，本地事务一提交就释放（AT 模式恰恰是立即提交）。它能防"同时写"，防不了"**事后拿旧快照补偿**"——t5 时 T1 写回的依据还是 t1 时刻的旧值。

#### 模拟 B：加上全局锁 → 串行化，回滚安全

全局锁由 TC（Seata 协调器）持有，本质是 TC 库里的 `lock_table` 一行记录，key = `资源ID:表名:主键`。Seata 代理数据源，**发 update 前先向 TC 抢全局锁**：

```
时刻  T1（转账）                       T2（返现）                  TC 全局锁表
 t1   抢 balance:100 的全局锁 ──────────────────────────────────►  ✅ T1 持有
      undo 前像=100，update→80，本地提交（行锁已放，无所谓）
 t2                                   update -30
      └─ TC 检查：该行锁被 T1 持有 → 阻塞重试 ⏳                   ⏳ T2 等待
 t3   下游失败 → 全局回滚：undo 写回 80→100
      释放全局锁 ──────────────────────────────────────────────►  🔓 空出
 t4                                   抢到锁，此时读到的是最新值 100
                                      记前像=100，update→70 ✅      ✅ T2 持有
```

结果：T2 的 update 被排到 T1 的**全局事务结束之后**，它记的"前像"永远是最新值，谁也不会覆盖谁。

#### 两种锁的分工（面试加分点）

| 对比 | DB 行锁（InnoDB） | Seata 全局锁 |
| --- | --- | --- |
| 谁持有 | 本地事务 | TC 的 lock_table |
| 作用范围 | 单个数据库内的同一行 | 跨服务、跨库的同一资源标识 |
| 持有到 | 本地事务 commit/rollback（AT 秒放） | **全局事务** commit/rollback |
| 防什么 | 同一时刻的写写冲突 | 并发全局事务 + 事后补偿互相覆盖（模拟 A） |
| 防不了 | 已提交事务的事后回滚覆盖 | 脏读——**读不加锁**，t2~t3 之间别人能读到中间值 80 |

一句话总结：**AT 用"本地事务早提交"换吞吐，再用"全局锁"把丢掉的写隔离补回来；读隔离没补，所以默认是类 RC 的脏读语义。**

- 使用：方法上加 `@GlobalTransactional`，业务代码几乎零改动
- 代价：全局锁影响吞吐（同热点行的并发全局事务被串行化）；中间状态可被读到

### 4. 可靠消息最终一致（RocketMQ 半消息）—— 异步主流方案

```
下单服务                          MQ Broker            积分服务
  |--- ① 发半消息（普通消费者不可见）--->|
  |--- ② 执行本地事务（创建订单）        |
  |--- ③a 本地成功 → Commit 消息 ------->|--- ④ 投递消息 ---> 加积分
  |--- ③b 本地失败 → Rollback ---------->|  消息作废
                （③ 迟迟不来，Broker 定时【回查】② 的本地事务状态）
```

- **可靠**体现在两处：半消息 + 回查保证"发得出"；手动 ack + 重试保证"收得到"
- 消费端必须**幂等**（唯一订单号 / 状态机），因为消息可能重复投递
- 一致性强度：最终一致，存在秒级~分钟级不一致窗口
- 应用：订单 → 积分 / 通知 / 物流等非核心异步链路（面试讲项目就用这个）

### 5. 最大努力通知 —— 跨企业对接

只能保证"我尽力通知了"，无法强求对方收到：

```
支付成功后回调商户：按 1min、5min、10min、30min… 间隔重试 N 次
仍失败 → 放弃，靠商户【主动查询接口】+ 每日对账单兜底
```

- 适用：对接外部/第三方（支付回调、开放平台），因为你控制不了对方系统

## 选型总结

```
需要强一致吗？（同步、资金敏感）
├─ 要 → 能接受写三个接口？
│        ├─ 能 → TCC
│        └─ 不能 → Seata AT（内部微服务）/ XA（低并发）
└─ 不要 → 在自己系统内？
          ├─ 是 → 可靠消息（MQ）✅ 最常用
          └─ 否（跨企业）→ 最大努力通知 + 对账
```

| 方案 | 一致性 | 性能 | 侵入性 | 典型场景 |
| --- | --- | --- | --- | --- |
| 2PC/XA | 强 | 差（锁资源） | 无 | 传统金融、低并发 |
| TCC | 强 | 好 | **大**（写3接口） | 支付、库存 |
| Seata AT | 强（全局锁） | 中 | 极小 | 微服务内部 |
| 可靠消息 | 最终一致 | 好 | 中 | 异步解耦，主流 |
| 最大努力通知 | 最终一致 | 好 | 小 | 跨企业回调 |

**选型心法：能异步就消息最终一致；非要同步才考虑 Seata/TCC；跨企业只能最大努力通知。**

## 面试答法

### 30 秒版（先给框架）

> 分布式事务的本质是：服务拆分后一个业务横跨多个数据库，本地事务保证不了整体一致。方案按一致性强度分两派：同步强一致派是 2PC 和 TCC——2PC 有同步阻塞和单点问题基本不用了，TCC 性能好但要在业务层写 Try/Confirm/Cancel 三个接口；最终一致派是可靠消息和最大努力通知——自己系统内用 RocketMQ 半消息加回查保证消息不丢，跨企业就重试通知加对账。选型原则是：能用异步就用消息，资金核心链路才上 TCC 或 Seata。我们项目的下单送积分就是用的半消息方案。

### 深入版（被追问时按这条线展开）

1. **引出问题**：拿转账/下单举例，说明本地事务为什么失效
2. **理论铺垫**：CAP 里 P 必选，实际是 CP/AP 取舍；BASE 是互联网对 C 的妥协，分布式事务方案都源自 BASE 思想
3. **方案光谱**：从 2PC → TCC → Seata AT → 可靠消息 → 最大努力通知，讲清每一环"解决了上一环的什么问题、又付出了什么代价"（如：TCC 解决 2PC 阻塞，但侵入大；Seata 解决侵入，但靠全局锁；消息放弃强一致换性能）
4. **落到项目**：讲一个具体链路（下单→积分），说清半消息流程、回查机制、消费端幂等怎么做
5. **收尾**：抛选型原则，体现工程判断力

### 常见追问

- **TCC 的空回滚/悬挂怎么处理？** → 事务状态表：Cancel 查 Try 是否执行过，Try 查是否已 Cancel
- **Seata AT 为什么比 2PC 快？** → 本地事务立即提交、不长期锁行，回滚靠 undo_log 补偿而非挂起等待
- **DB 行锁不是能防并发写吗，为什么还要全局锁？** → 行锁随本地提交立刻释放，防不了"已提交事务事后拿旧快照回滚"造成的更新丢失；全局锁把同一行的写串行化到全局事务粒度（见模拟 A/B）
- **半消息发了但本地事务失败怎么办？** → 回滚半消息；若 commit 请求也丢了，Broker 定时回查本地事务表兜底
- **消息重复消费怎么防？** → 业务唯一键 + 数据库唯一索引 / Redis setnx / 状态机校验
