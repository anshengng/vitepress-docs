# 限流、熔断与降级

## 题目

> 常用限流算法有哪些？熔断和降级有什么区别？三者怎么配合使用？

## 为什么需要

先看一次典型的**雪崩传导**：

```
大促流量 ──► 订单服务 ──► 库存服务（DB 突然变慢）
                │
                ▼
  库存服务响应 3s+，订单服务线程全部阻塞在等库存
  → 订单服务线程池打满，自己也失去响应
  → 上游看到订单服务也挂了，故障向上蔓延
  → 本来只挂 1 个服务，10 分钟后全站雪崩 💥
```

三个角色正好各管一段：

```
流量 ──► ┌──────────────────────────────────────────┐
         │ 限流：入口闸门，保"自己"不被流量打垮           │
调用下游 ┤ 熔断：下游故障时快速失败，别让等待拖死自己       │
         │ 降级：扛不住时有损服务，保核心弃枝叶           │
         └──────────────────────────────────────────┘
```

| 手段 | 管哪段 | 一句话 |
| --- | --- | --- |
| 限流 | 入口 | 控制并发/速率，超出就拒绝，保自己不被打垮 |
| 熔断 | 出口 | 下游故障时快速失败，不再真实调用，防传导 |
| 降级 | 触发后 | 有损服务，弃非核心保核心 |

## 核心要点

### 一、限流算法四连图

#### 1. 固定窗口计数：临界突刺问题

```
限制：每分钟 100 次
时刻        第 1 个窗口(00:00~00:59)   │ 翻转   第 2 个窗口(01:00~01:59)
 t1 00:50   计数 0 → 80 ✔             │
 t2 00:59   计数 → 100 ✔（触顶拒绝）   │
 t3 01:00   ───── 窗口翻转，计数清零 ───│─► 计数 = 0
 t4 01:01                                │   计数 → 100 ✔（又放行一批）

→ 00:59~01:01 两秒内放进 200 个请求 ≈ 瞬间双倍流量打穿下游
  问题不在总量，而在"窗口一翻转计数清零"，边界两侧各打满限值
```

#### 2. 滑动窗口：细化格子平滑统计

```
把 1 分钟切成 6 个 10s 小格，窗口随时间滑动累加：
  │格1 │格2 │格3 │格4 │格5 │格6 │
  │ 12 │ 18 │ 15 │ 20 │ 17 │ 14 │  当前窗口 = 96（接近 100）
   └─ 每 10s 前移一格：删最老格、加新格
  边界两侧的请求同时落在"当前窗口"里一起统计，不再瞬间翻倍
```

#### 3. 漏桶：恒定速率流出，强制削峰

```
   突发流量（尖峰波浪）▼▼▼▼▼▼▼▼▼▼
  ┌──────────┐
  │  桶(队列)  │ ← 不管进多猛，桶满即溢出（拒绝）
  │ ████████ │
  └────┬─────┘
       │ 恒定速率 r/s 流出
       ▼ 〇 〇 〇 〇 〇 → 下游永远看到均匀流量，绝对安全
```

#### 4. 令牌桶：恒定速率发牌，允许突发

```
  恒定速率 r/s 放入令牌 ●
  ┌──────────┐
  │ ●●●●●●●● │ ← 桶容量 b：空闲时攒下的令牌 = 突发额度
  └────┬─────┘
       │ 每个请求拿走 1 个令牌才能通过
  空闲期攒满 → 突发 b 个请求瞬间全放行 ✔（允许突发）
  令牌耗尽 → 后续按 r 速率排队或被拒
```

#### 四算法对比表

| 算法 | 允许突发 | 复杂度 | 适用 |
| --- | --- | --- | --- |
| 固定窗口 | 边界处双倍突发 | 最低 | 要求不高的简单接口 |
| 滑动窗口 | 突刺大幅缓解 | 低 | 通用，Sentinel 默认 |
| 漏桶 | 不允许（恒速流出） | 中 | 保护完全扛不住突发的下游（DB） |
| 令牌桶 | 允许（攒令牌） | 中 | 绝大多数业务，Guava RateLimiter |

### 二、单机 vs 分布式限流

单机限流只管自己一台，集群总量 = N × 单机限值，保护目标对不上：

```
网关 ──┬──► 实例-1（单机限 40/s）
       ├──► 实例-2（单机限 40/s）   集群峰值 200/s
       └──► 实例-3（单机限 40/s）   若保护目标是 100/s → 失灵
       …×5 台
```

分布式限流：**Redis + Lua 原子扣减**（读-判-写必须一步完成，拆开就有并发超扣）：

```lua
-- KEYS[1]=限流key  ARGV[1]=上限  ARGV[2]=窗口秒数
local current = redis.call('INCR', KEYS[1])
if current == 1 then redis.call('EXPIRE', KEYS[1], ARGV[2]) end
if current > tonumber(ARGV[1]) then return 0 end
return 1
```

更彻底的做法是在**网关/接入层**统一限流（Nginx + Lua、Spring Cloud Gateway + Redis），在入口拦掉。常用实现一览：Guava RateLimiter（单机令牌桶）、Sentinel（滑动窗口+熔断+控制台）、Nginx `limit_req`（接入层漏桶）。

### 三、熔断器三状态机

```
             统计窗口内：请求数 ≥ 最小请求数 且 失败率 ≥ 阈值
      ┌─────────┐ ─────────────────────► ┌─────────┐
      │ Closed  │                        │  Open   │
      │ 正常放行 │ ◄───────────────────── │ 拒绝所有 │
      └─────────┘    探测成功恢复          └────┬────┘
            ▲                                  │ 冷却期(如30s)到
            │         ┌─────────────┐          ▼
            └──────── │  Half-Open  │ ◄── 放行少量探测请求
          探测成功    │  放探测请求   │
          回 Closed   └─────────────┘ ── 探测失败 ──► 回 Open 重新计时
```

| 转换 | 触发条件 |
| --- | --- |
| Closed → Open | 统计窗口内请求数 ≥ 最小请求数，且失败率 ≥ 阈值（如 10s 内 ≥ 20 次且失败率 > 50%） |
| Open → Half-Open | 冷却期（sleep window，如 30s）结束 |
| Half-Open → Closed | 探测请求全部成功，恢复 |
| Half-Open → Open | 探测仍失败，继续熔断并重新计时 |

- **为什么有最小请求数？** → 3 个请求挂 2 个"失败率 66%"显然不能熔断，样本太小没有统计意义
- **熔断的本质**：把"干等超时"换成"立刻失败"，不让下游的慢耗尽自己的线程/连接资源
- Sentinel 还支持**慢调用比例/异常比例/异常数**多种熔断策略，平均 RT 超阈值也算

### 四、降级策略清单

熔断或限流触发后，总要给用户一个交代：

| 策略 | 做法 | 典型场景 |
| --- | --- | --- |
| 兜底默认值 | 返回运营配置的固定内容 | 推荐位、广告位 |
| 缓存旧数据 | 返回过期缓存（标注更新时间） | 商品页、库存展示 |
| 简化流程 | 跳过非核心步骤，事后异步补 | 下单不送积分、不发通知 |
| 友好提示 | "系统繁忙请稍后再试" | 写操作、支付类 |
| 关闭功能 | 前端隐藏入口，直接不调用 | 大促期间关评论/签到 |

选择原则：**资金/交易链路保一致性（宁可拒绝），体验链路保可用性（给旧数据）**，实在不行才上"抱歉"页。

### 五、三者协同的完整链路

```
用户 ──► 网关【限流】流量超阈值直接拒绝（挡洪峰，保自己）
           │
           ▼
         订单服务 ──调用──► 库存服务
           │ 调用带【熔断器】
           ├─ 正常：放行
           ├─ 失败率超阈 → 熔断 Open → 不再真实调用，走【降级】
           │                        ├─ 库存展示 → 读缓存旧值
           │                        └─ 扣库存  → 友好提示 + 异步补偿
           └─ 冷却后 Half-Open 探测，成功自动回切 Closed
```

一次请求的完整防护：**入口限流保自己 → 出口熔断防传导 → 触发后降级保体验**。

## 面试答法

### 30 秒版（可背诵）

> 这三者是稳定性三板斧，各管一段：限流管入口，控制并发和速率，保自己不被流量打垮；熔断管出口，下游故障时快速失败，不让等待拖死自己的线程池；降级是熔断或限流触发后的兜底，有损服务保核心。限流算法有四种：固定窗口有临界双倍突刺问题；滑动窗口细化小格解决了突刺，是 Sentinel 的默认；漏桶恒速流出，绝对保护扛不住突发的下游；令牌桶恒速发牌允许突发，最常用。单机限流管不了集群总量，分布式用 Redis 加 Lua 原子扣减，或在网关层统一做。熔断器是三状态机：Closed 正常放行，失败率超阈值进 Open 快速失败，冷却期后 Half-Open 放探测请求，成功回 Closed、失败回 Open。降级策略按业务重要性选：兜底默认值、缓存旧数据、简化流程、友好提示。

### 常见追问

- **滑动窗口为什么能解决临界问题？** → 窗口平滑滑动，边界两侧请求同落当前窗口一起统计，没有"清零重来"
- **漏桶和令牌桶怎么选？** → 下游完全扛不住突发（如 DB）用漏桶强制匀速；允许短时突发的业务用令牌桶，体验更好
- **Redis 挂了限流怎么办？** → 限流组件要有本地降级：回退单机限流兜底，别让限流系统自己成为故障点
- **熔断和重试冲突吗？** → 熔断优先：Open 状态直接失败不重试；Half-Open 用少量探测请求验证，避免重试风暴
- **Sentinel 和 Hystrix 区别？** → Hystrix 线程池隔离较重且已停更；Sentinel 滑动窗口 + 并发线程数隔离，控制台动态规则、热点参数限流更全
