# 事务隔离级别与 MVCC

## 题目

> 事务的 ACID 分别靠什么实现？脏读、不可重复读、幻读各是什么？MySQL 四个隔离级别分别解决什么问题？MVCC 的实现原理？RC 和 RR 的区别、RR 如何防幻读？

## 为什么需要

多个事务并发读写同一批数据，不加约束的话，读的人可能读到"写到一半的数据"。解决思路有两个流派：

- **加锁排队**：读等写、写等读，安全但并发性能差——读多写少的场景太亏了
- **MVCC 多版本并发控制**：写的人改出新版本，读的人看自己当时的快照——**读写互不阻塞**。InnoDB 靠它在 RR 级别下做到普通查询不加锁

## 核心要点

### 一、ACID 与实现手段对照表

| 特性 | 含义 | 靠什么实现 |
| --- | --- | --- |
| A 原子性 | 要么全做、要么全不做 | **undo log**：记录反向操作，回滚时逐条补偿 |
| C 一致性 | 数据从一个合法状态到另一个合法状态 | 由 A、I、D 共同保障的**最终目标** |
| I 隔离性 | 事务之间互不干扰 | **锁 + MVCC**：写写靠锁、读写靠 MVCC |
| D 持久性 | 提交了就永久生效 | **redo log**：WAL 先顺序写日志再异步刷数据页，崩溃也能恢复 |

### 二、并发三问题（各画一条时间线）

```
① 脏读：读到了别人【未提交、可能回滚】的数据
   事务A（写）                        事务B（读）
    │ update 余额=200（未提交）          │
    │ ────────────────────────────────► │ select 余额 → 200 ❌
    │ rollback（余额实际回到 100）        │  B 已拿着 200 去做业务了

② 不可重复读：同一事务两次读【同一行】，值变了（别人 update 已提交）
   事务A（读）                        事务B（写）
    │ select 余额 → 100                 │
    │                                   │ update 余额=200; commit
    │ select 余额 → 200 ❌              │

③ 幻读：同一事务两次按【同样条件】查，行数变了（别人 insert 已提交）
   事务A（读）                        事务B（写）
    │ select count(*) where age>18      │
    │   → 100 行                        │
    │                                   │ insert 一条 age=19; commit
    │ select count(*) where age>18      │
    │   → 101 行 ❌                     │
```

记忆口诀：**值变了 = 不可重复读（update）；行数变了 = 幻读（insert/delete）**。

### 三、四隔离级别 vs 问题矩阵

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 一句话 |
| --- | --- | --- | --- | --- |
| 读未提交 RU | 会 | 会 | 会 | 啥也不防，基本不用 |
| 读已提交 RC | ✗ 防住 | 会 | 会 | 只读别人已提交的（Oracle/PG 默认） |
| **可重复读 RR** | ✗ | ✗ | 基本防住 | **MySQL 默认**：快照读靠 MVCC、当前读靠临键锁 |
| 串行化 Serializable | ✗ | ✗ | ✗ | 全程加锁排队，最安全也最慢 |

### 四、MVCC 三件套

#### 1. 行的隐藏列

```
┌─────────┬─────────┬───────────────┬───────────────┐
│ id      │ name    │ trx_id        │ roll_pointer  │
│ (业务列) │ (业务列) │ 最后修改它的事务id│ 指向 undo log   │
└─────────┴─────────┴───────────────┴───────────────┘
                                        中的上一历史版本
```

#### 2. undo log 版本链

```
当前行记录：name='C'，trx_id=300
     │ roll_pointer
     ▼
undo log：name='B'，trx_id=200     （改 C 之前的旧版本）
     │ roll_pointer
     ▼
undo log：name='A'，trx_id=100     （更早的版本）

→ 每次修改都把旧版本留在 undo log，串成一条链
→ 不同事务拿着各自的 ReadView 顺链找"自己能看见的那个版本"
```

#### 3. ReadView：可见性判定规则

生成 ReadView 时记录四个字段：

| 字段 | 含义 |
| --- | --- |
| creator_trx_id | 我自己（当前事务）的 id |
| m_ids | 此刻所有【活跃（未提交）】事务的 id 列表 |
| min_trx_id | 活跃列表中最小的 id |
| max_trx_id | 系统即将分配给下一个事务的 id（注意：不是 m_ids 的最大值） |

拿版本链上某个版本的 trx_id，按顺序判定：

```
trx_id == creator_trx_id ？
 ├─ 是 → 我自己改的，可见 ✅
 └─ 否 ↓
trx_id < min_trx_id ？
 ├─ 是 → ReadView 生成前就已提交，可见 ✅
 └─ 否 ↓
trx_id >= max_trx_id ？
 ├─ 是 → ReadView 生成之后才开启的事务，不可见 ❌
 └─ 否 ↓
trx_id 在 m_ids 活跃列表里？
 ├─ 是 → 还没提交，不可见 ❌
 └─ 否 → 生成时已提交，可见 ✅

不可见 → 顺 roll_pointer 找上一版本重复判定，直到链尾（还没有 → 查不到）
```

### 五、RC 与 RR 的唯一区别：ReadView 的生成时机

同一场景推演（name 初始值 'A'）：

```
事务A（RC 或 RR）              事务B
begin
select name → 生成 ReadView_V
  （此刻 B 的 trx_id=200 尚未开启，不在视野里）
                              begin
                              update name='B'（trx_id=200）
                              commit ✅ 已提交！
select name → 再查一次，顺版本链找到 trx_id=200 的新版本：
  RC：每次 select 重新生成 ReadView → 200 不在新视野的活跃列表里
      → 可见 → 读到 'B'（别人刚提交的，我马上能看见）
  RR：一直复用第一次的 ReadView → 按 V 的规则判定 200
      → 可见/不可见取决于 V 的生成时机，若 V 在 B 开启后生成前判定为活跃
      → 不可见 → 顺链读旧版本 'A'（维持"可重复读"）
```

**一句话：RC 每次 select 都生成新的 ReadView，所以能看到别人刚提交的；RR 只在第一次 select 生成、之后一直复用，所以同样的查询结果永远可重复**——这就是两种隔离级别在 MVCC 层面的全部区别。

下面用五列时间线对比同一次操作在 RC / RR 下的不同结果（balance 初始 100）：

```
时刻 | 事务A（RC）                      | 事务A（RR）                      | 事务B                  | undo 版本链
 t1  | begin; select balance → 100      | begin; select balance → 100      |                        | balance=100 (trx_id=10)
     | 生成 ReadView_RC1                | 生成 ReadView_RR1（之后一直复用） |                        |
 t2  |                                  |                                  | begin                  |
 t3  |                                  |                                  | update balance=200     | 新版本 200 (trx_id=20)
     |                                  |                                  |                        |  roll_pointer → 100(trx=10)
 t4  |                                  |                                  | commit ✅              |
 t5  | select balance →                 | select balance →                 |                        |
     | 【新建 ReadView_RC2】            | 【复用 ReadView_RR1】            |                        |
     | trx_id=20 不在活跃列表 → 可见    | trx_id=20 在 RR1 活跃列表 → 不可见|                        |
     | 读到 200                         | 顺 roll_pointer 回退找可见版本    |                        |
     |                                  |  → 找到 trx_id=10 的旧版本        |                        |
 t6  | 结果：200（不可重复读）           | 结果：100（可重复读）             |                        |
```

对比要点：同一行第二次 select，RC 读到 200（能看见 B 刚提交的），RR 读到 100（沿版本链回退）——差别只在 ReadView 是"每次重建"还是"一直复用"。

### 六、RR 怎么防幻读

- **快照读**（普通 `select`）：靠 MVCC 天然防——ReadView 固定，之后别的事务 insert 的行对它不可见，两次读结果一致
- **当前读**（`select ... for update`、`update`、`delete`）：靠 **next-key lock 临键锁 = 行锁 + 间隙锁**，把已有的行和可能插入的空隙都锁住，别人插不进来
- 注意：先快照读、再当前读的混用场景，仍可能看到新行（幻读的残留缝隙），所以说 RR 是"基本防住"幻读

### 七、长事务的危害（一句工程提醒）

- 老 ReadView 一直活着 → undo 版本链上谁也不敢删 → 回滚段膨胀
- 临键锁等锁一直持有 → 并发上不去、死锁概率变大
- 一句：`@Transactional` 别包 RPC / 慢 IO / 大循环，事务越短越好

## 面试答法

### 30 秒版（可背诵）

> ACID 的实现：原子性靠 undo log 回滚、持久性靠 redo log、隔离性靠锁加 MVCC、一致性是前三者共同保证的最终目标。并发问题三个：脏读是读到未提交的数据，不可重复读是两次读同一行值变了，幻读是两次同条件查询行数变了。MySQL 默认 RR。MVCC 靠三件套实现：每行有 trx_id 和 roll_pointer 两个隐藏列，undo log 把历史版本串成版本链，ReadView 按四个字段做可见性判定，查询时顺版本链找自己能看见的版本。RC 和 RR 的唯一区别是 ReadView 的生成时机：RC 每次 select 都生成新的，RR 只在第一次生成之后一直复用，这就是"可重复读"的由来。RR 防幻读：快照读靠 MVCC 天然防，当前读靠 next-key lock 临键锁。

### 深入版（编号答题线索）

1. **先立框架**：ACID 对照表，点出"隔离性 = 锁 + MVCC 分工"
2. **三问题**：三条时间线讲脏读 / 不可重复读 / 幻读，口诀"值变 vs 行数变"
3. **四级别矩阵**：点出 RR 是 MySQL 默认
4. **MVCC 推导**：隐藏列 → 版本链 → ReadView 四字段判定流程，一环扣一环
5. **RC vs RR**：同一时间线推演出两次 select 的结果差异，落到"ReadView 生成时机"这个唯一区别
6. **幻读收尾**：快照读靠 MVCC、当前读靠临键锁，顺带提长事务危害体现工程感

### 常见追问

- **redo log 和 binlog 什么区别？** → redo 是 InnoDB 引擎层的物理日志，用于崩溃恢复；binlog 是 Server 层的逻辑日志，用于归档和主从复制
- **RR 算完全杜绝幻读吗？** → 快照读、当前读各自场景内能防；但同一事务先快照读再当前读，仍可能看到别的事务插入的行
- **MVCC 下 update 怎么发生？** → 生成新版本写入当前行，旧版本进 undo log 并用 roll_pointer 串上链
- **RC 下 MVCC 还有意义吗？** → 有：RC 同样靠 MVCC 实现无锁快照读，只是每次 select 重建 ReadView
- **为什么 MySQL 默认 RR 而不是 RC？** → 历史原因：早期 statement 格式 binlog 在 RC 下主从可能乱序不一致，RR 加临键锁保证语句重放顺序一致
