# 索引原理与失效场景

## 题目

> InnoDB 为什么用 B+ 树做索引？聚簇索引和二级索引的区别是什么？什么是回表和覆盖索引？最左前缀原则怎么用？哪些写法会导致索引失效？

## 为什么需要

一张 1000 万行的用户表，执行 `where name = '张三'`：

- 没索引 = **全表扫描**：从第 1 行逐行翻到第 1000 万行（像在一本没目录的书里逐页找知识点）
- 有索引 = **B+ 树定位**：树高 3 层，3~4 次磁盘 IO 直接锁定目标行（先查目录，直接翻到第 328 页）

索引的本质：**用写入时维护一棵有序结构的代价，把查询从"无序的全表扫描"变成"有序结构上的二分定位"**。

## 核心要点

### 一、为什么是 B+ 树？四种结构对比

```
① 二叉搜索树：插入有序数据退化成链表
     1
      \
       2
        \
         3   → 查找退化为 O(n)，每层还对应一次磁盘 IO，废了

② B 树：非叶子节点也存整行数据
   [10|整行数据][20|整行数据]   一页 16KB，行数据占地方
   → 每页能放的键变少 → 树变高 → IO 变多
   → 范围查询要中序回溯，不友好

③ 哈希：等值查询 O(1) 很快
   name → 哈希槽位
   → 不支持范围（age > 18 没法算哈希）
   → 不支持排序、无法模糊匹配、联合索引无法只按部分列查

④ B+ 树：非叶子只存键 + 叶子有序链表
        ┌─ 10 | 20 ─┐            非叶子节点只存键：
        /     |     \            16KB 页能放约 1200 个键
   [1..9] [11..19] [21..]        三层 ≈ 1200 × 1200 × 每页约15行
     ↔ 10 ↔  20 ↔  ...           ≈ 两千万行，查询只需 3 次 IO
     叶子层双向有序链表 → 范围查询顺着链表扫即可
```

结论（面试标准句）：**非叶子只存键 → 单页存的键多 → 树更矮（3 层撑两千万行，IO 次数少）；叶子有序链表 → 范围查询、排序都友好**。

### 二、聚簇索引 vs 二级索引：两棵树 + 回表

```
  主键 id 的聚簇索引树             name 的二级索引树
  （叶子 = 完整行数据）            （叶子 = name + 主键 id）

        ┌─ 20 ─┐                        ┌─ 王五 ─┐
        │      │                        │        │
    ┌─10─┐  ┌─30─┐                  ┌─李四─┐  ┌─张三─┐
    │    │  │    │                  │      │  │      │
   ●────●────●────●                ●──────●──────●
 id=1 id=10 id=20 id=30          (李四,10)(王五,30)(张三,20)

查询流程：select * from user where name = '张三'

  ① 在 name 树走 3 层 → 叶子 (张三, 20)     此时只拿到 id
  ② 拿 id=20 回主键树再走 3 层 ◄─────────── 这一步叫【回表】
  ③ 在聚簇叶子取出整行返回
```

下面逐步推演整个过程（以 `select * from user where name = '李四'` 为例）：

```
   idx_name 二级索引树（叶子 = name + id）        id 主键聚簇索引树（叶子 = 整行）
        ┌── 王五 ──┐                                   ┌── 20 ──┐
        │         │                                   │       │
   ┌─李四─┐   ┌─张三─┐                             ┌─10─┐  ┌─30─┐
   │     │   │     │                             │   │  │   │
   ●─────●───●─────●                             ●───●──●───●
 (李四,5)(王五,10)(张三,20)                      id=1 id=5 id=10 id=20

① 从根走 idx_name 树：'李四' < '王五' → 走左子树 → 命中叶子 (李四, 5)
② 从叶子拿到主键 id = 5
③ ─────────────── 拿到 id=5，回主键树再查一遍 ───────────────►  【这就是回表】
④ 在主键树从根向下找 id=5 → 叶子取出整行 (id=5, name='李四', age=...) 返回

─────────────────────────────────────────────────────────────────────
对照：覆盖索引 select id from user where name = '李四'

   idx_name 二级索引树
   ① 走树找到叶子 (李四, 5)
   ② 直接把 id=5 返回 ✅  —— 查询列就在索引里，无需回主键树
   （没有③④，省一次树查找）

小结：回表成本 = 多一次主键树的树高查找；能用覆盖索引就别回表。
```

- InnoDB 表本身 = 一棵聚簇索引树（索引即数据）；二级索引都是挂在旁边的"辅助树"
- 没有主键时用非空唯一索引兜底，再没有就生成隐藏的 row_id

### 三、覆盖索引：让查询跳过回表

```
联合索引 idx_name_age(name, age)

select name, age from user where name = '张三'
→ 要查的列（name、age）都在索引树里 → 从 name 树直接返回 ✅ 免回表

select * from user where name = '张三'
→ 要整行 → 拿到 id 后仍要回主键树 ❌
```

这也是"不要无脑 `select *`"的底层原因之一。

### 四、联合索引与最左前缀

索引 `(a, b, c)` 内部的排序规则：先按 a 排，a 相同按 b 排，b 相同按 c 排——**等价于把 "a,b,c" 拼成字符串做字典序**。

```
a=1 ─ b=1 ─ c=1
    └── b=2 ─ c=5
a=2 ─ b=1 ─ c=3
    └── b=3 ─ c=2
a=5 ─ b=2 ─ c=1
→ 一旦跳过 a 直接按 b 找，数据在 b 维度上是"散"的，只能全扫
```

| where 条件 | 索引 (a,b,c) 能用上几列 | 原因 |
| --- | --- | --- |
| `a=1 and b=2 and c=3` | ✅ 三列全用 | 完全匹配 |
| `a=1 and b>2` | ✅ a 等值 + b 范围 | b 用了范围后，c 无序可依、失效 |
| `a=1 and c=3` | ✅ 只用 a | 中间跳过 b，c 无法直接定位 |
| `b=2` | ❌ 用不上 | 缺最左列 a，数据在 b 维度无序 |
| `b=2 and c=3` | ❌ 用不上 | 同上 |

### 五、索引失效场景清单（每条配一句示例）

| # | 场景 | 示例 SQL | 为什么失效 |
| --- | --- | --- | --- |
| 1 | 对索引列做函数/计算 | `where YEAR(create_time) = 2024` | 索引存的是原始值，套函数后的结果不保序；改写成范围条件 `create_time >= '2024-01-01' and create_time < '2025-01-01'` |
| 2 | 隐式类型转换 | phone 是 varchar：`where phone = 13800001234` | 相当于给列套了 CAST 函数，同场景 1；字符串列的条件一定带引号 |
| 3 | 前导模糊 | `like '%三'`、`like '%三%'` | 字典序只能定位开头已知的值；`like '张%'` 可以走 range |
| 4 | or 连接无索引列 | `where name = 'a' or age = 20`（age 无索引） | or 两侧有一侧走不了索引，整条只能全表扫；把 age 建索引或改写 union |
| 5 | `!=` / `not in` | `where status != 1` | 不是必然失效：匹配行占比太大（选择性差）时优化器干脆全表扫 |
| 6 | 最左列缺失 | 索引 (a,b)，`where b = 2` | 见最左前缀，b 维度无序 |

### 六、explain 一眼关注什么

- `type`：从好到差 `const > eq_ref > ref > range > index > ALL`，**至少要到 range**，出现 ALL 就是全表扫描（详见慢 SQL 排查篇）
- `key`：实际用上的索引；`rows`：预估扫描行数
- `Extra`：`Using index` 是覆盖索引（好）；`Using filesort` / `Using temporary` 要警惕

### 七、为什么推荐自增主键 + 索引的代价

```
自增主键：主键永远递增，新记录只追加在 B+ 树最右侧
  [1][2][3]...[n] → 页满了顺着开新页，顺序写 ✅

随机主键（UUID 等）：可能插进已满页的中间
  [3][7][9] 插入 5 → 页放不下 →【页分裂】把一半挪去新页
  → 写入变慢 + 页内利用率低 + 碎片 ❌
  （UUID 36 字节 vs bigint 8 字节，二级索引叶子还都存主键 → 全树膨胀）
```

索引的代价（不是越多越好）：

- **写放大**：每多一个索引，insert/update/delete 都要多维护一棵树
- **空间成本**：每棵索引树都是实打实的存储
- **优化器负担**：索引太多，选执行计划的开销也变大

## 面试答法

### 30 秒版（可背诵）

> InnoDB 选 B+ 树，是因为非叶子节点只存键不存数据，一页 16K 能放上千个键，三层就能支撑两千万行，IO 次数少；叶子节点用双向链表串起来，范围查询和排序很友好。索引分聚簇和二级：聚簇索引叶子存整行，二级索引叶子只存主键，所以走二级索引查别的列要拿主键回聚簇树再查一遍，这叫回表；select 的列都在二级索引里就是覆盖索引，不用回表。联合索引要遵守最左前缀。常见失效场景：对索引列做函数或计算、varchar 列传数字导致隐式转换、like 左模糊、or 连了没有索引的列、最左列缺失。排查用 explain 看 type，至少要到 range。另外推荐自增主键，顺序插入避免页分裂，还省空间。

### 深入版（编号答题线索）

1. **引出**：用 1000 万行表的全表扫描 vs 查目录类比，点出索引 = 用有序换定位
2. **四结构淘汰赛**：二叉退化 → B 树不够矮 → 哈希不支持范围 → B+ 树胜出（"矮"和"链表"两个关键词）
3. **两棵树**：画聚簇 + 二级索引树讲回表，再顺势带出覆盖索引
4. **最左前缀**：用字典序解释 (a,b,c) 的排序结构，能用/不能用对照表
5. **失效清单**：逐条配 SQL 讲"为什么"，重点：函数计算和隐式转换的本质都是破坏有序性
6. **收尾工程观**：自增主键避免页分裂、索引有写放大和空间代价，不是越多越好

### 常见追问

- **三层 B+ 树怎么算出两千万行？** → 非叶子页约存 1200 个键：1200 × 1200 ≈ 144 万个叶子页，每页约 15 行，≈ 2000 万行
- **为什么不要 select *？** → 用不上覆盖索引必然回表，还多传无用列浪费带宽
- **索引下推 ICP 是什么？** → 5.6+ 把联合索引中"后面列"的 where 过滤下推到存储引擎层先筛，减少回表次数
- **唯一索引和普通索引怎么选？** → 查询性能几乎无差，业务上有唯一约束需求就建唯一索引，让数据库兜底
- **联合索引的列顺序怎么定？** → 区分度高、等值查询的列放前面；范围查询的列放最后（范围之后全失效）
