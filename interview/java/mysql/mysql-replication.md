# MySQL 主从复制与分库分表

## 题目

> MySQL 主从复制的原理和流程？三种同步模式怎么选？主从延迟怎么办？什么时候该分库分表，怎么拆，会带来哪些新问题？

## 为什么需要

单库 MySQL 扛不住两件事：**读并发**（一主承担全部读写，迟早被打满）和**容灾**（库挂了业务全停）。于是有了主从：

```
                 写请求（增删改）
                      │
                      ▼
                ┌──────────┐
                │  主库 M   │─── 热备容灾：主挂了，从库顶上
                └──────────┘
                 ╱            ╲          复制（异步）
        ┌──────────┐      ┌──────────┐
        │  从库 S1  │      │  从库 S2  │
        └──────────┘      └──────────┘
            ▲                 ▲
      读请求 │                 │ 读请求
      （读写分离：读流量分摊到多台，整体 QPS 上限翻倍）
```

但复制是异步的，马上冒出新问题——**延迟、丢数据**；而且读写分离解决不了单表太大，于是又有了**分库分表**。

## 核心要点

### 复制完整流程：三组件时间线

binlog 是复制的基石（格式细节见[三大日志篇](./redo-undo-binlog.md)，不展开）：

```
主库                              从库
────                              ────
事务提交
  │ ① 写 binlog
  │
dump 线程（读 binlog 推送）─►  ② IO 线程接收
  │                             │ ③ 写入 relay log（中继日志）
  │                             │
  │                             SQL 线程读 relay log
  │                             │ ④ 回放执行 → 数据与主库一致 ✅
  ▼
主库只管写 binlog，推完就回客户端，不等从库（异步的根源）
```

三个角色各司其职：**dump（主库推送）→ IO 线程（从库接收存 relay log）→ SQL 线程（回放）**。relay log 的存在让"接收"和"回放"解耦——网络快慢不影响回放节奏。

### 三种同步模式

| 模式 | 流程 | 性能 | 数据安全 | 场景 |
| --- | --- | --- | --- | --- |
| 异步（默认） | 主库提交即返回，不等从库 | 最好 | 主挂可能丢最后几笔事务 | 一般业务，日志、评论 |
| 全同步 | 所有从库都 ack 后主库才返回 | 最差 | 最安全 | 极少用，强一致要求小规模 |
| 半同步 | **至少 1 个从库**收到 binlog 并 ack 才返回 | 介于两者 | 基本不丢（从库落盘 relay log） | 金融、支付（生产主流选择） |

半同步是折中：`rpl_semi_sync_master_timeout` 超时后可自动降级回异步，防止从库全挂拖死主库。

### 主从延迟：原因与治理

```
延迟根源：SQL 线程回放速度 < 主库写入速度
├─ ① 从库单线程回放（历史版本）→ 主库并行写、从库串行放
├─ ② 大事务：一条事务删 500 万行，主库 10 分钟，从库也要 10 分钟
├─ ③ 大表 DDL：从库回放 DDL 时全表锁
└─ ④ 从库机器差 / 从库还承担大量读压力

治理：
├─ 并行复制（multi-threaded slave / LOGICAL_CLOCK）→ SQL 线程多线程按组回放
├─ 拆大事务：批量任务分批提交（每批 1000 条）
├─ 写后立读强制路由主库（见下）
└─ 半同步 + 监控 Seconds_Behind_Master 告警
```

### 场景题：写后立刻读从库读不到

```
T1  用户改昵称 → 写主库 ✅
T2  立刻刷新页面 → 读从库 → 复制还没跟上 → 返回旧昵称 ❌ 用户："我没改成功？"
```

三种解法，按代价从低到高：

1. **强制走主库**：写后 N 秒内（或关键页面）该用户的读请求路由到主库（网关按用户 ID 标记）
2. **网关标记**：写请求响应里带标记，客户端后续带标记的请求都走主库，过期后恢复读从库
3. **半同步复制**：从库 ack 后主库才返回，读任何从库都基本可见（性能有折损）

### 分库分表：什么时候拆、怎么拆

单表 B+ 树行数过高 → 树变高、磁盘撑爆、DDL 变慢。经验值：**单表约 2000 万行或 2GB**（本质是 B+ 树 3 层放不下了，见[索引篇](./index.md)），可结合业务增长谈。

#### 垂直拆分 vs 水平拆分

```
垂直分库（按业务）：           垂直分表（按冷热拆列）：
订单库、用户库、商品库          用户表 → 基础信息表（热，高频读）
各自独立部署                    + 详情扩展表（冷，低频读）

水平分库分表（按行分片）：
user 表 8000 万行
  ├─→ db0.user_0    (分片键 hash 后的 1/4 行)
  ├─→ db0.user_1
  ├─→ db1.user_0
  └─→ db1.user_1    同构表，行打散，每片 ~2000 万 ✅
```

**垂直解决"业务耦合/字段太宽"，水平解决"行数太多"**，先垂直后水平是常见顺序。

#### 分片键与路由算法

| 算法 | 分布示意 | 优点 | 缺点 |
| --- | --- | --- | --- |
| hash 取模 | `user_id % 4 → 0/1/2/3` | 数据均匀、实现简单 | **扩容要大规模迁移**（模数变了全乱） |
| range 范围 | 按 id 1~1000万、1000~2000万 | 扩容只加新分片，**不迁数据** | **热点**（新数据集中写最新分片） |
| 一致性哈希 | 环形空间顺时针落分片 | 扩容只迁移相邻一段 | 实现复杂，需虚拟节点均衡 |

分片键选**查询最高频的字段**（通常 user_id），让 80% 查询单分片内完成。

#### 带来的新问题清单

| 问题 | 解法 |
| --- | --- |
| 跨库 join | 冗余字段（反范式）、应用层组装、宽表进 ES |
| 主键冲突 | 分布式 ID：雪花算法、号段模式 |
| 跨库事务 | 见[分布式事务篇](../distributed/distributed-transaction.md)（最终一致为主） |
| 多维度查询 | 基因法（把 user_id 基因嵌入订单号，按订单号查也能路由到同分片）、异构索引表、ES |

### 平滑扩容：双写迁移五步

不停机从单库切到分库的标准动作：

```
T1  新库双写    → 写旧库同时写新库（新写都进新库，读还走旧库）
T2  存量迁移    → 后台任务把旧库历史数据分批搬进新库
T3  比对校验    → 全量比对两库数据一致（不一致的修复重迁）
T4  切读        → 读流量灰度切到新库，观察稳定
T5  切写停旧    → 写流量切新库，旧库停写，留作回滚兜底
```

## 面试答法

### 30 秒版（可背诵口语）

> 主从复制的流程是：主库事务提交写 binlog，dump 线程推送给从库，从库 IO 线程写进 relay log，再由 SQL 线程回放。同步模式有三种：异步默认性能最好但可能丢数据，全同步最安全但延迟大，半同步至少等一个从库 ack，是金融场景的平衡选择。主从延迟主要因为 SQL 线程单线程回放慢、大事务、从库机器差，治理用并行复制、拆大事务，写后立读强制路由主库。单表超过两千万行左右考虑分库分表：先垂直按业务拆，再水平按分片键拆，路由算法 hash 均匀但扩容难、range 好扩但有热点。拆完要解决跨库 join、分布式 ID、跨库事务问题。扩容用双写迁移五步：双写、存量迁移、比对、切读、切写。我的选型原则是：能垂直不水平、能拆表不拆库，先上缓存和读写分离，都不行才水平分片。

### 常见追问

- **binlog 什么格式最适合复制？** → row 格式（主从一致性最稳），statement 可能因函数/随机值不一致，见[三大日志篇](./redo-undo-binlog.md)
- **怎么监控主从延迟？** → `Seconds_Behind_Master`（不准时可对比 GTID/心跳表时间戳）
- **主库宕机从库怎么选？** → 选 relay log 最全（GTID 最新的），配合半同步可保证不丢
- **雪花算法时钟回拨怎么办？** → 拒绝发号等待追平、或预留序列位回退，生产可用号段模式
- **基因法是什么？** → 生成订单号时把 user_id 的二进制片段嵌入，按订单号查时提取基因即可路由到同一分片
- **分片数一开始定多少？** → 按三年数据量预估，宁多勿少（预分 64/128 张表），hash 取模配合 2 的幂次扩容代价小
