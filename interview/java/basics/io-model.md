# BIO/NIO/AIO 与 IO 多路复用

## 题目

> BIO、NIO、AIO 的区别？什么是 IO 多路复用？select/poll/epoll 是什么？为什么 NIO 单线程反而更快？

## 为什么需要：先讲清"阻塞"的本质

读 socket 时，数据往往还在网卡/内核缓冲区里，用户代码拿不到。

```
read() 的真实时间线（线程视角）：

  线程状态
    │  ① 用户态: 发起 read() 系统调用
    │        ↓
  睡眠 ⏸⏸⏸⏸⏸⏸⏸⏸⏸⏸⏸  ② 内核等数据到达（客户端慢慢发…）
    │        ↓
    │  ③ 数据到了，内核拷贝到用户缓冲区
    │  ④ 唤醒线程，read 返回
    ▼
   时间 →

  ② 阶段线程干啥也干不了，纯等 —— 这就是"阻塞"（CPU 白白闲置）
```

## 核心要点

### 三种模型对比

```
【BIO】一连接一线程：来 1000 个连接开 1000 个线程

  连接1 ──► [线程1 ⏸ 等]
  连接2 ──► [线程2 ⏸ 等]      每个线程 1MB 栈内存，
  连接3 ──► [线程3 ⏸ 等]      1000 连接 ≈ 1GB + 大量上下文切换
  ...999 个都在睡              💥 线程爆炸
  连接1000► [线程1000 ⏸ 等]

【NIO】一个线程轮询所有连接（多路复用）

                    ┌────────────┐
  连接1 ──┐         │   Selector  │   一个线程问一圈：
  连接2 ──┤         │  ( epoll )  │   "你们谁的数据准备好了？"
  连接3 ──┼───────►│             │   只有就绪的才去 read，
  ...     │         │  就绪队列 ✓✓│   没就绪的连看都不看
  连接N ──┘         └──────┬──────┘
                            ▼
                     [单线程处理就绪连接]

【AIO】内核干完活主动回调

  线程: "内核，数据好了叫我" ──► 线程走人干别的
  内核: 收数据→拷贝到用户缓冲区→ 全部完成 → 回调/通知线程
        （Windows IOCP 比较成熟；Linux 实现弱，Netty 曾支持又移除了 AIO）
```

### NIO 三大组件

```
   Channel（双向管道，替代单向流）
   ├── SocketChannel / ServerSocketChannel / FileChannel
   │
   │      读写都经 Buffer（不再直接对流裸读写）
   ▼
 ┌──────────────────┐
 │ Buffer            │   flip(): 写转读的开关
 │ [pos][lim][cap]   │   position/limit/capacity 三指针
 └──────────────────┘
   ▲
   │ 注册 + 事件(OP_ACCEPT/OP_CONNECT/OP_READ/OP_WRITE)
 ┌─┴────────────────┐
 │ Selector         │   selectKeys 就绪队列流程：
 │ 单线程盯所有通道    │   ① channel.register(selector, OP_READ)
 └──────────────────┘   ② selector.select() 阻塞到有事件
                        ③ 遍历 selectedKeys，逐个处理
                        ④ key.remove() 处理过的要删掉
```

### 多路复用名词解释

本质一句话：**一个线程同时"监听多个 fd（文件描述符/socket）"**，谁就绪通知谁，避免每个 fd 都开线程干等。

| 演进 | 做法 | 突破 |
| --- | --- | --- |
| select | 每次把 fd 集合全量拷给内核、内核全量轮询，返回后再遍历 | 首次实现"一个线程管多 fd"；上限 1024 |
| poll | 链表存 fd，去掉 1024 上限 | 仍是全量拷贝 + O(n) 遍历 |
| epoll | 内核维护红黑树 + 就绪链表，事件驱动只返回就绪的 fd | O(1) 拿就绪列表，连接数再多也不慌 |

```
select/poll: "把 1 万个 fd 都拷进来，挨个问：好了吗好了吗？"
epoll:       "我登记一次；谁好了谁自己挂到就绪链表，我直接取链表"
```

这正呼应了 **Redis 单线程却高并发**（epoll 事件驱动 + 就绪才处理）、**Netty 天生基于 epoll 封装 NIO**。

### 为什么 NIO 单线程反而快

| | BIO 1000 线程 | NIO 1 线程 |
| --- | --- | --- |
| 阻塞等待 | 每个线程各睡各的 | 就绪才处理，不陪等 |
| 上下文切换 | 海量（1MB 栈×1000 + 调度开销） | 极少 |
| 内存 | ~1GB | ~1MB |
| CPU 利用 | 大部分线程在睡，真正干活的极少 | 就绪队列源源不断喂给线程 |

### 典型应用表

| 组件 | IO 模型 | 说明 |
| --- | --- | --- |
| Tomcat | BIO（旧版）→ NIO（默认） | Connector 已全面 NIO 化 |
| Netty | NIO（epoll） | 自研 Buffer、主从 Reactor 线程组 |
| Redis | IO 多路复用 | 单线程 + epoll 也能 10w QPS（新版本 IO 线程只管读写） |
| Dubbo/RPC 框架 | 多基于 Netty | 所以也间接是 NIO |

**收尾心法：选 NIO 不是"省线程"，而是"省等待"**——把无数线程干等的总时间集中到一个线程上，谁就绪处理谁。

## 面试答法

### 30 秒版（可背诵）

> BIO 是阻塞 IO，一连接一线程，连接多了线程爆炸；NIO 用 Selector 多路复用，一个线程监听所有连接，通过 epoll 只处理就绪的，线程不用陪睡；AIO 是内核把数据都准备好后再回调，Linux 上实现不成熟所以实际用得少。多路复用的本质是一个线程监听多个 fd，select 到 poll 到 epoll 的演进就是把"全量轮询"优化成"事件驱动的就绪链表"。NIO 单线程反而快，是因为省掉了大量阻塞等待和线程上下文切换。所以 Tomcat、Netty、Redis 都是这个路子，选 NIO 省的不是线程是等待。

### 常见追问

- **零拷贝了解吗？** → sendfile/mmap：数据不进用户态，内核直接发给网卡；Netty、Kafka、RocketMQ 都在用
- **epoll 的 LT/ET？** → 水平触发没处理会反复通知；边缘触发只通知一次，必须一次读完，Netty 用的 ET
- **NIO 的线程一定是一个吗？** → 不，Netty 是主从 Reactor：boss 接连接、worker 组处理读写，多个 worker 也能多核利用
- **为什么 Netty 放弃 AIO？** → Linux 的 AIO 实现不完善（内核版本碎片化），epoll 已经够快，收益覆盖不了复杂度
