# HashMap 底层原理

## 题目

> HashMap 的底层结构是什么？put 一个元素的完整流程是怎样的？扩容时元素如何迁移？为什么说它线程不安全？JDK 1.7 和 1.8 有哪些区别？

## 核心要点

### JDK 1.8 存储结构：数组 + 链表 + 红黑树三合一

```
table 数组（容量 n 恒为 2 的幂；默认 16，负载因子 0.75）
┌───┬───┬───┬───┬───┬───┬───┐
│ 0 │ 1 │ 2 │ 3 │ 4 │...│n-1│
└─┬─┴───┴─┬─┴───┴───┴───┴───┘
  │       │
  ▼       ▼
 null    链表: k1 → k2 → k3 → ... → k8    链长 ≥ 8 且数组 ≥ 64
                                      │
                                      ▼ 树化
                                红黑树: 查找 O(n) → O(log n)
                                （节点 ≤ 6 时退化回链表）
```

- 定位桶：`index = (n - 1) & hash`，一步位运算，O(1)
- 桶冲突用拉链法挂链表；链太长有退化风险 → 红黑树兜底

### 扰动函数：hash = 高 16 位 ^ 低 16 位

```java
static final int hash(Object key) {
    int h;
    return (h = key.hashCode()) ^ (h >>> 16);
}
```

定位桶只用到 hash 的低几位。如果 hashCode 高位差异大、低位凑巧相同，不扰动的话它们会全撞进同一个桶。扰动把高位"折叠"进低位，让高位也参与定位：

```
h        = 1111 1111 1111 1111 1010 1010 1010 1010
h >>> 16 = 0000 0000 0000 0000 1111 1111 1111 1111
hash     = 1111 1111 1111 1111 0101 0101 0101 0101   ← 高16位异或进低16位

n=16 时 index = hash & 1111：
  不扰动 → 1010（高位信息完全丢失）
  扰动后 → 0101（高位差异被折进来，碰撞更少）
```

### put 完整流程

```
put(key, value)
  ① hash = hashCode 高16位 ^ 低16位（扰动函数）
  ② i = (n - 1) & hash 定位桶下标
  ③ table[i] 为空？ → 直接放入新节点，跳到 ⑦
  ④ 桶首节点 key 相同？ → 覆盖 value，结束
  ⑤ 该桶已是红黑树？ → 树插入（key 相同则覆盖），跳到 ⑦
  ⑥ 还是链表 → 沿链表尾插遍历：
        途中 key 相同 → 覆盖 value，结束
        插到链尾后：链长 ≥ 8 且数组长度 ≥ 64 → 树化
  ⑦ ++size > threshold（容量 × 0.75）？ → resize() 扩容 2 倍并迁移
```

### 扩容：不重算 hash，元素"原位 / 原位+oldCap"二选一

容量翻倍后，新掩码只比旧掩码多掩一位（权值恰为 oldCap）。每个元素只需看 hash 在这一位是 0 还是 1：

```
oldCap = 16  →  newCap = 32

旧定位：hash & 01111 = i           新定位：hash & 11111 = ?

hash 在新增那一位（权值 16）= 0 → 留在【原位 i】
hash 在新增那一位（权值 16）= 1 → 搬去【原位 i + 16】

例：hash = 17 (1 0001)：17 & 15 = 1，17 & 16 ≠ 0 → 新桶 17 = 1 + 16
    hash = 1  (0 0001)：1 & 15 = 1， 1 & 16 = 0   → 新桶 1，原地不动
```

迁移时一个桶的链表按这一位直接拆成"低位链 / 高位链"两条，各接各的新桶，不用每个节点重新走一遍定位，省掉大量 hashCode 计算与比较。

### 容量为什么必须是 2 的幂

1. `(n-1) & hash` 等价于 `hash % n`（n 为 2 的幂时数学上成立），位运算比取模快；且 n-1 是全 1 掩码（如 15 = 1111），hash 每一位都用得上，散列才均匀。若 n=10，掩码 9 = 1001，中间两位恒为 0，一部分桶永远分不到元素
2. 扩容分流依赖它：新容量 = 旧容量左移一位，掩码只多出一位，才有"原位 / 原位+oldCap"的二选一

### 模拟：JDK 7 头插法两线程并发扩容 → 成环死循环

JDK 7 迁移用头插法，核心四步：

```java
do {
    next = e.next;           // ① 记住后继
    e.next = newTable[i];    // ② 头插到新桶（链表顺序被反转！）
    newTable[i] = e;         // ③
    e = next;                // ④
} while (e != null);
```

旧桶链表：A → B → null（假设扩容后 A、B 仍路由到同一个新桶）：

```
时刻   线程1                              线程2              新桶链表
 t1   执行完①，拿到 next = B，挂起 ⏸
       （线程栈里局部变量 e=A, next=B）
 t2                                       独自跑完整个迁移    B → A → null
                                          （头插法把顺序反转！）
 t3   线程1 恢复，拿着过期的 e=A、next=B 继续：
      ②  A.next = 新桶头（= B）
          而 B.next = A 是 t2 留下的
          → A ⇄ B 互相指向，环诞生 ⚠️
      ③  新桶头 = A
      ④  e = B
 t4   下一轮：e=B → ① next=B.next=A → ④ e=A
      → ① next=A.next=B → ④ e=B ...
      指针在 A、B 之间永远打转，next 永不为 null
后续   get 命中这个桶 → while(e != null) 遍历链表 → 死循环，CPU 100%
```

JDK 8 改为尾插 + 按"原位/原位+oldCap"拆两条链、保持原顺序追加，不会再成环。但**依然线程不安全**——比如两线程同时 put 到同一个空桶，都判定"桶为空"，后写入的直接覆盖先写入的：

```
T1: put(k1) 看到桶3为空 ──┐
T2: put(k2) 看到桶3为空 ──┤ 两边都认为自己是第一个
T1: table[3] = node(k1)   │
T2: table[3] = node(k2)   → k1 无声无息丢失，size 计数也可能错
```

多线程环境一律用 ConcurrentHashMap。

### 树化 8、退化 6：为什么不取同一个数

若树化和退化阈值同为 8：桶里 8 个节点，删 1 个变 7 → 退化回链表；再插 1 个又到 8 → 又树化。在阈值附近频繁增删时会反复"拆树建树"，性能抖动。留 2 的间隙当缓冲带，避免来回横跳。

树化取 8 的依据是泊松分布：负载因子 0.75、哈希均匀时，桶内节点数近似服从泊松分布，链长达到 8 的概率约 0.00000006——正常情况几乎轮不到树化，红黑树只是哈希质量极端劣化时的保底手段。

### ConcurrentHashMap 一句话

JDK 8 抛弃分段锁，改为 CAS（空桶直接 CAS 放入）+ synchronized（只锁桶头节点），锁粒度细到单个桶，并发度 ≈ 桶数量。详见并发篇。

## 面试答法

### 30 秒版（先给框架）

> HashMap 在 JDK 8 是数组加链表加红黑树：put 时先对 hashCode 做高低 16 位异或的扰动，再用 (n-1)&hash 定位桶，冲突就尾插进链表，链长到 8 且数组到 64 就树化成红黑树。扩容翻倍后元素不用重算 hash，按新增那一位分成"原位"和"原位加旧容量"两批迁移。容量必须是 2 的幂，一是让与运算等价于取模且散列均匀，二是扩容分流依赖它。线程不安全体现在 JDK 7 头插法并发扩容会成环死循环，JDK 8 改尾插解决了成环，但并发 put 依然会丢数据，多线程要用 ConcurrentHashMap。

### 深入版（被追问时按这条线展开）

1. **结构**：数组 + 链表 + 红黑树，定位 O(1)，树化把最坏查找从 O(n) 压到 O(log n)
2. **扰动函数**：高 16 位异或低 16 位，让高位参与定位，减少碰撞
3. **put 流程**：hash → 定位 → 空桶直放 / 冲突覆盖或尾插 → 树化条件 → size 超阈值扩容
4. **扩容分流**：掩码只多一位，元素"原位或原位+oldCap"二选一，不重算 hash
5. **并发问题**：推演 JDK 7 头插成环（e/next 交叉导致 A⇄B 互指），JDK 8 尾插修复成环但依旧丢数据 → 上 ConcurrentHashMap
6. **数字背后的道理**：2 的幂、8 与 6 的间隙防抖动、泊松分布说明树化是兜底

### 常见追问

- **负载因子为什么是 0.75？** → 空间利用率和冲突概率的经验折中：太大冲突多、查找慢，太小浪费内存还频繁扩容
- **链长到 8 但数组不足 64 怎么办？** → 不树化，先扩容（小数组时冲突大概率是容量问题，扩容比树化便宜）
- **key 可以是 null 吗？** → HashMap 可以（null 的 hash 特判为 0，放 0 号桶）；Hashtable、ConcurrentHashMap 不行
- **为什么 String 适合做 key？** → 不可变（hash 不会变）、hashCode 有缓存、哈希分布均匀
- **get 一个 key 的过程？** → 同样扰动定位 → 桶首比对 → 链表遍历或树查找；hashCode 相同且 equals 为 true 才算命中
- **两个 key 的 hashCode 相同会怎样？** → 落同一个桶（哈希冲突），靠 equals 区分，这正是链表/树存在的原因
