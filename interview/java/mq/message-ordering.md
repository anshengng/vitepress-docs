# MQ 消息顺序性：为什么会乱序、怎么保证有序

## 题目

> MQ 为什么会乱序？如何保证消息的有序发送和有序消费？顺序消费时某条消息一直失败怎么办？

## 为什么需要

有些业务本质是状态机，消息乱序 = 状态倒挂：

```
订单状态机：

  CREATED ──支付──► PAID ──发货──► SHIPPED ──确认收货──► COMPLETED
     │
     └──取消──► CANCELLED

灾难场景：m3(发货) 先到先处理、m2(支付) 后到
→ 系统执行了 SHIPPED → PAID 的非法回退：要么状态机校验直接抛错，
  要么订单被悄悄"回退"，用户看到"已发货却显示未支付"的脏状态。
```

类比：MQ 是快递分拨中心。为了快，包裹被分到**多条流水线并行分拣、多个快递员并行派送**——先上架的不一定先送到。想保证先后，只能对同一订单保持"一条流水线 + 一个快递员"。**并行与有序天然互斥**，保序的本质就是给同一业务实体串行化。

## 核心要点

### 一、为什么 MQ 天然乱序

乱序源头环环相扣：生产者多线程发送、Broker 轮询分配到多分区、消费组多实例/多线程并行处理、失败重试打乱到达顺序。MQ 只承诺**单个队列/分区内 FIFO**，不存在全局有序。

**双消费者线程并发竞争时间线（同一订单消息交错消费演示）**：

```
共享状态：订单 order_7 的 status，初始 CREATED
生产者连续发三条：m1(创建) m2(支付) m3(发货)，轮询落到 3 个分区

t1  生产者: m1→P0, m2→P1, m3→P2（轮询分配，三分区并行存储）
t2  T1(负责拉 P0 的消费者线程): 拉到 m1 → status = CREATED ✓
t3  T2(负责拉 P2 的消费者线程): 拉到 m3 → 执行"发货" → status = SHIPPED
    ← 发货消息抢跑了！
t4  T1 从 P0 拉到 m2: 执行"支付" → status = PAID ← 从 SHIPPED 被"回退"
    状态机 SHIPPED→PAID 是非法转移：抛异常 / 写入脏数据
```

结论：**只要同一业务实体的消息散落在多个队列并行消费，乱序就是必然**。保序思路只有一条——让同一业务键的消息在发送、存储、消费全链路串行。

### 二、发送端：同一业务键路由到同一队列

```java
// RocketMQ：MessageQueueSelector —— orderId % 队列数，同一订单永远进同一队列
producer.send(msg, (mqs, m, arg) -> {
    long orderId = (Long) arg;
    return mqs.get((int) (orderId % mqs.size())); // 按业务键取模路由
}, order.getId());

// Kafka：key 设为订单号，broker 按 hash(key) % 分区数 固定路由
producer.send(new ProducerRecord<>("order-topic",
        String.valueOf(orderId), jsonPayload));
```

两个必须提的坑：

1. **分区/队列数变化（扩容）破坏路由**：`orderId % n` 中 n 一变，同一订单的消息会散到不同队列，新旧消息并行。RocketMQ 顺序消息靠锁定队列规避；Kafka 最好固定分区数，或接受切换窗口、靠消费端版本号兜底。
2. **生产者多线程发送本身可能乱序**：同一 key 被两个线程发送仍可能交错。Kafka 需 `enable.idempotence=true`（保证同分区发送顺序）；RocketMQ 用 `sendOrderly` 对同一队列加锁。

### 三、消费端：从"保序"到"吞吐"的三级演进

**第一级：单线程消费**——最简单，但吞吐锁死：

```
Queue ──► 1 个消费者线程逐条处理：上限约 1000 TPS，大促直接积压爆炸
```

**第二级：内存队列按 hash 分桶 + 每桶单线程**（业务常用，也是 RocketMQ 顺序消费的模型）：

```
                                     ┌─ 桶0(orderId%4=0): [m1,m4,m9] ─► Worker0 单线程按序处理
拉取线程 ──hash(orderId)%4 只投递──►  ├─ 桶1:            [m2,m6]   ─► Worker1 单线程按序处理
                                     ├─ 桶2:            [m3,m7]   ─► Worker2 单线程按序处理
                                     └─ 桶3:            [m5,m8]   ─► Worker3 单线程按序处理

同一订单 → 永远同一桶 → 桶内单线程串行 → 有序
不同订单 → 散到不同桶 → 4 线程并行     → 吞吐 ×4
```

要点：**拉取线程只做分桶投递、不做业务处理**；每个桶绑定专属 worker 线程，桶边界由业务键 hash 决定。

**第三级：数据库版本号 / 状态机兜底**（防御一切漏网乱序）：

```sql
-- 带"期望当前状态 + 版本号"的更新：乱序/迟到消息匹配 0 行，天然被拒绝，不会倒挂
UPDATE orders
   SET status = 'PAID', version = version + 1
 WHERE id = #{orderId}
   AND status = 'CREATED'           -- 状态机前置条件
   AND version = #{expectVersion};  -- 乐观锁兜底
-- 应用检查影响行数：0 行 → 说明该消息非法/迟到，走补偿或丢弃
```

Redis 兜底（setnx 记录"已处理的最新版本"，只放行更大的版本）：

```java
// setnx 思路的原子版：Lua 比较并更新，msg.version 必须大于已处理版本才放行
String lua = "local v = redis.call('get', KEYS[1]) " +
             "if v and tonumber(v) >= tonumber(ARGV[1]) then return 0 end " +
             "redis.call('set', KEYS[1], ARGV[1]) return 1";
Boolean pass = redis.execute(script, List.of("order:ver:" + orderId), String.valueOf(msg.version));
```

### 四、各方案吞吐 vs 顺序对比表

| 方案 | 顺序保证范围 | 吞吐 | 复杂度 | 适用 |
| --- | --- | --- | --- | --- |
| 全局单队列 + 单线程 | 全局有序 | 最低 | 低 | 量极小（审计日志类） |
| 业务键同队列 + 每队列单线程 | 分区内有序 | 中 | 中 | 主流方案 |
| 消费端 hash 分桶 + 每桶单线程 | 业务键有序 | 高（× 桶数） | 中高 | 高吞吐要求 |
| DB 版本号/状态机兜底 | 不保证顺序，只防状态倒挂 | 高 | 低 | 任何方案都该叠加 |

### 五、追问重点：顺序消费时某条消息一直失败怎么办

```
串行的代价——队头阻塞（Head-of-Line Blocking）：

桶0: m1 ✓ → m2 ✗ 失败 → 原地重试 m2 → m3、m4 只能干等
     m2 反复失败（如下游 DB 超时）→ 整个桶/队列"卡死"，积压持续上涨
```

RocketMQ 顺序消费的默认行为正是 **SUSPEND_CURRENT_QUEUE_A_MOMENT**：重试当前消息并挂起当前队列——故意阻塞来保序，因为放行 m3 就破坏顺序。三种取舍：

1. **阻塞等成功**（RocketMQ 默认）：严格保序，但一条毒消息卡死整个队列 → 必须配最大重试次数 + 积压告警。
2. **重试 N 次仍失败 → 跳过进死信/人工干预**：放行后续消息，牺牲该订单的顺序换队列可用；修复后人工重推，靠版本号兜底防倒挂。
3. **业务补偿**：失败消息落库记录，后续消息到达时"链式补齐"前置状态（处理 m3 时发现 m2 没做，直接推进到 SHIPPED），m2 修复后幂等丢弃。

结论：**顺序与可用性互斥——要么阻塞队列等成功，要么跳过破坏顺序，必须二选一；工程底线是重试上限 + 告警 + 人工通道。**

## 面试答法

### 30 秒版（直接背诵）

> MQ 天然乱序，因为消息被轮询散到多个分区、多个消费者线程并行处理，同一订单的创建、支付、发货消息交错消费，就会出现"先发货后支付"的状态倒挂。保序思路统一是让同一业务键全链路串行：发送端按订单号 hash 路由到同一队列，RocketMQ 用 MessageQueueSelector、Kafka 用 key；消费端要么每队列单线程，要么内存队列按业务键 hash 分桶、每桶单线程来兼顾吞吐；最后再叠加数据库状态机加版本号的乐观锁兜底防倒挂。代价是队头阻塞：顺序消费里一条消息反复失败会卡住整个队列，RocketMQ 默认重试当前消息并挂起队列，实践上设重试上限，超限进死信人工处理，用牺牲局部顺序换整体可用。

### 深入版（被追问时按这条线展开）

1. **为什么乱序**：并行无处不在；用双消费者线程时间线演示 SHIPPED→PAID 倒挂
2. **发送端**：业务键 hash 固定队列；两个坑——扩容改路由、多线程发送交错（Kafka 幂等）
3. **消费端**：单线程 → hash 分桶多线程 → 版本号/Redis 兜底，三级演进讲吞吐
4. **对比表**：吞吐 vs 顺序 vs 复杂度
5. **毒消息**：队头阻塞原理、三种取舍、顺序与可用性互斥

### 常见追问

- **Kafka 能保证分区有序吗？** → 能：单分区追加式有序，同消费组内一个分区只分给一个消费者；但生产端重试可能乱序，需 `enable.idempotence=true`。
- **RocketMQ 顺序消息和普通消息消费的区别？** → 普通用并发监听多线程消费；顺序用 `MessageListenerOrderly` + 队列锁，失败返回 SUSPEND_CURRENT_QUEUE_A_MOMENT 阻塞队列重试。
- **分桶数变了会怎样？** → 同一 orderId 换桶，旧桶在途消息与新桶并行、顺序失守 → 低峰变更、先排空再切换，并用版本号兜底覆盖窗口期。
- **为什么不用分布式锁保证顺序？** → 锁只能防"并发处理"，防不了"到达顺序"：后到的 m2 也可能先抢到锁。真顺序必须队列串行化，锁只是低效的串行化手段。
- **业务既不能阻塞又不能乱序怎么办？** → 改消息设计：把"状态变更事件"合并成"目标状态 + 版本号"的状态同步消息，任意一条最新消息都能独立把状态机推进到正确位置，天然抗乱序。
