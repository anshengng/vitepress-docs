# MQ 高可用与消息积压

## 题目

> Kafka/RocketMQ 的高可用架构是怎样的？线上出现消息积压怎么处理？

## 为什么需要

单节点 Broker 就像全城只有一个快递仓库：

```
单节点：
  生产者 ──► [唯一 Broker] ──► 消费者
                 │
                 ├─ 宕机 10 分钟 → 消息进不来也出不去，上下游全堵死 💥
                 └─ 磁盘写满 → 新消息全部被拒 → 上游跟着连环挂
```

机器一定会坏（内存、磁盘、网络、断电），高可用要回答的是：**任何一台挂了，读写照常、消息不丢**。另一面，集群再稳也怕"消费速度 < 生产速度"——积压是可用性的另一杀手。

## 核心要点

### 一、Kafka 多副本机制

```
topic 被切成多个分区，每个分区多副本、打散到多台 Broker：

Broker-1               Broker-2               Broker-3
┌───────────────┐    ┌───────────────┐    ┌───────────────┐
│ P0 [Leader]   │    │ P1 [Leader]   │    │ P2 [Leader]   │
│ P1 [Follower] │    │ P2 [Follower] │    │ P0 [Follower] │
└───────▲───────┘    └───────────────┘    └───────────────┘
        │
   读写都找 Leader（生产/消费只跟 Leader 打交道）
   Follower 拉取 Leader 数据同步，平时待命不对外服务
```

#### 三个关键概念

| 概念 | 含义 | 作用 |
| --- | --- | --- |
| Leader | 每分区一个，处理该分区所有读写 | 读写入口 |
| ISR | 与 Leader 保持同步的副本集合（含 Leader），落后太多被踢出 | 决定谁能当新 Leader |
| HW 高水位 | ISR 中同步进度最慢的那个位置 | 消费者可见性的边界 |

#### HW 为什么决定消费者可见性

```
Leader 日志：  [0.......10] [11....15]
                ▲ 已被 ISR 全员同步  ▲ 只有 Leader 写到
                └─ HW=10：消费者最多读到 10
                   11~15 尚未同步到所有 ISR 副本 → 对消费者不可见

为什么？若允许读到 15，此刻 Leader 挂了、新 Leader 只同步到 10
→ 消费位点回退，15 这条消息"重来一遍" → 不一致
所以宁可晚点可见，也不让消费者读到可能"回退消失"的数据
```

#### Leader 故障切换时间线

```
时刻  事件
 t1   Broker-1（P0 的 Leader）宕机 💥
 t2   Controller 通过心跳超时感知（秒级）
 t3   从 P0 的 ISR [B1, B3] 中选出 Broker-3 任新 Leader
 t4   元数据变更广播，客户端刷新后自动重连 B3
 t5   读写恢复（期间秒级不可写，生产端靠重试扛过）
```

要点：**新 Leader 只能从 ISR 里选**——ISR 外的副本数据落后，用它当选等于丢已确认的消息（`unclean.leader.election.enable` 一般禁用）。

### 二、RocketMQ / RabbitMQ 方案对比

| MQ | 高可用方案 | 一句话特点 |
| --- | --- | --- |
| Kafka | 分区多副本 + ISR 选举（Controller 由 ZK/KRaft 选出） | 天然分布式，水平扩展强 |
| RocketMQ 主从 | Master 读写、Slave 只同步备份；Master 挂后不可写（Slave 可读），需人工切换 | 简单，但故障要人肉 |
| RocketMQ DLedger | 基于 Raft 协议自动选主，过半副本写入成功才回 ack | 自动切换 + 不丢，至少 3 副本 |
| RabbitMQ 镜像队列 | 每个队列镜像到多个节点，主队列挂了镜像提升为主 | 配置简单，但同步开销大、吞吐受限 |

另外别忘了**客户端也是高可用的一环**：客户端缓存元数据、自动重连、故障转移（生产者换分区重试、消费者组再均衡）。

### 三、刷盘 × 复制的可靠性等级

| 组合 | 可靠性 | 性能 | 适用 |
| --- | --- | --- | --- |
| 同步刷盘 + 同步复制 | 最高：机器坏/断电都不丢 | 最差 | 资金、计费 |
| 异步刷盘 + 同步复制 | 高：机器坏不丢（断电丢 PageCache 由多机摊薄） | 中 | **最常用** |
| 同步刷盘 + 异步复制 | 中：本机不丢，但主从切换瞬间可能丢 | 中 | 少用 |
| 异步刷盘 + 异步复制 | 低 | 最好 | 日志等可容忍丢失场景 |

### 四、消息积压

#### 原因分析

本质一句话：**消费能力 < 生产速度，差额持续累积**。

```
      生产 10000 条/s                消费 3000 条/s
           │                             │
           ▼                             ▼
  ═════════► queue/分区 ═════════════════►
           ┌─────────────────────┐
           │ 差额 7000/s 持续累积 │ ← lag 一路飙升
           └─────────────────────┘
  常见诱因：
  ① 消费者 bug：卡死 / OOM / 抛异常没 ack → 反复重投越滚越多
  ② 下游慢：消费依赖的 DB/接口变慢，拖慢整条链
  ③ 突发流量：大促、批量推送，生产瞬间翻 10 倍
  ④ 上游 bug：循环里狂发消息（事故型）
```

#### 应急三板斧（先止血，再溯源）

```
发现积压（lag 告警）
   │
   ▼
① 横向扩消费者：消费者数 ≤ queue 数（超过无效，见下图）
   ├── 够了 → 消费提速，积压回落 ✔
   │
   └── queue 数本身到顶了（分区数不能加或加也没用）
        ▼
② "搬家"方案：新建 10 倍 queue 的临时 topic
   │   原消息 → 只做搬运不做业务 → 快速落临时库/转存
   │   修复/扩容原消费逻辑后 → 离线慢慢消化临时数据
   ▼
③ 磁盘逼近上限 → 丢非核心消息（重置 offset / 按标签丢弃）
   │   保住 Broker 活命（磁盘写满 = 整个集群拒写，殃及所有业务）
   ▼
 事后：定位根因（慢日志、线程 dump、流量来源）+ 复盘改进
```

**为什么消费者数 ≤ queue 数**——多余消费者空转图：

```
queue-0 ──► 消费者-1（干活）
queue-1 ──► 消费者-2（干活）
queue-2 ──► 消费者-3（干活）
            消费者-4（空转）❗ 同一 queue 同一时刻只归一个消费者
            消费者-5（空转）❗ → 扩容前先数 queue 的数量
```

#### 预防手段清单

- **监控告警**：lag 指标（分区最新 offset − 消费组提交 offset）接入监控，分级告警
- **生产端限流/削峰**：洪峰别直灌 MQ（配合限流篇）
- **消费端提效**：批量拉取、批量落库、业务多线程（注意顺序与幂等）
- **容量规划**：分区数按峰值 N 倍预留；注意事后扩分区会改变 key 路由、打破分区内顺序
- **演练预案**：消费重投、死信告警、搬家方案提前演练

## 面试答法

### 30 秒版（可背诵）

> Kafka 的高可用靠分区多副本：每个分区一个 Leader 负责读写，Follower 同步，跟得上的副本组成 ISR；消费者只能读到 ISR 全部同步到的高水位 HW。Leader 挂了，Controller 从 ISR 里选新 Leader，秒级切换。RocketMQ 有主从和 DLedger 两种，DLedger 用 Raft 自动切主、过半写入才算成功；RabbitMQ 用镜像队列。可靠性等级上，同步刷盘加同步复制最安全但最慢，一般选异步刷盘加同步复制。消息积压遵循先止血再溯源：第一步横向扩消费者，但消费者数不能超过 queue 数，多了空转；queue 到顶就上搬家方案，新建十倍 queue 只搬运不做业务，快速转存落库，修复后再离线消化；磁盘快满只能丢非核心消息保 Broker 不死。最后定位根因，平时靠 lag 告警、生产端限流、消费端批量加多线程预防。

### 深入版（编号答题线索）

1. **引入**：单节点两大风险——宕机全瘫、磁盘写满，引出"多副本"与"积压"两条线
2. **Kafka 副本机制**：按"分区 → 副本 → Leader/ISR → HW → 选举"顺序讲，配图
3. **HW 可见性**：讲清"读到未同步数据 + 切主回退"的不一致场景，这是区分度所在
4. **横向对比**：RocketMQ 主从 vs DLedger、RabbitMQ 镜像队列各一句，别忘客户端重连
5. **可靠性等级表**：刷盘 × 复制四组合，点出常用中间档
6. **积压**：先给"消费<生产"本质，再三板斧（扩容→搬家→丢弃），强调消费者数 ≤ queue 数
7. **收尾**："先止血再溯源"，落到预防手段，体现线上意识

### 常见追问

- **为什么新 Leader 只能从 ISR 选？** → ISR 外副本数据落后，用它当选等于丢已确认的消息；宁可短暂不可用也不丢
- **HW 和 LEO 区别？** → LEO 是每条日志自身末端；HW = ISR 中最小 LEO，是消费者可见线
- **消费者扩了没效果？** → 超过 queue/分区数的消费者抢不到队列只能空转；得先扩分区（注意扩分区影响 key 路由与顺序）
- **积压时消息过期怎么办？** → 看是否有 TTL；核心消息应提前搬运转存，过期的按业务定取舍
- **怎么监控积压？** → lag = 分区最新 offset − 消费组提交 offset，求和接告警（如超 10 万条且持续 5 分钟）
- **主从切换会不会丢消息？** → 同步复制（或 DLedger 过半写入）不丢；异步复制在主挂瞬间可能丢未同步部分
