# 消息不丢失、不重复、顺序消费

## 题目

> MQ 如何保证消息不丢失？为什么重复消费不可避免，怎么兜底？如何保证顺序消费？

## 为什么需要

把 MQ 想成快递中转站：

```
生产者(寄件人) ──发件──► Broker(中转仓库) ──派件──► 消费者(收件人)
```

任何一环掉链子包裹就丢：寄件时车翻了（发送失败却"以为成功"）、仓库着火（Broker 宕机没落盘）、签收了却说没收到（ack 时机不对）。而且 MQ 承诺的是 at-least-once——**宁可重复投递，绝不漏投**，所以"不重复"也别指望 MQ，只能自己幂等兜底。顺序问题则出在并行：同一订单的两条消息被两个消费者同时处理，先来后到就乱了。

## 核心要点

### 一、不丢失：按生命周期三段把关

```
┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│ ① 生产段     │ ─► │ ② 存储段     │ ─► │ ③ 消费段     │
│ 生产者发送    │    │ Broker 落盘  │    │ 消费者处理    │
├─────────────┤    ├─────────────┤    ├─────────────┤
│ 丢法：网络失败│    │ 丢法：宕机时  │    │ 丢法：自动ack │
│ 却"假装成功"  │    │ 未刷盘/未同步 │    │ 后进程崩溃    │
│ 解法：重试    │    │ 解法：刷盘    │    │ 解法：手动ack │
│ +确认回执    │    │ +多副本复制   │    │ 成功才确认    │
└─────────────┘    └─────────────┘    └─────────────┘
```

#### 1. 生产段：重试 + 确认机制（Broker 回执才算成功）

丢失场景：`send()` 正常返回、日志打了"发送成功"，但消息还躺在网卡缓冲区或半路丢了，应用一崩就没了。

```
生产者                               Broker
  |──① 发送消息 ────────────────────►|
  |    网络超时/失败 ✗                 |
  |──①' 客户端自动重试 N 次 ─────────►|
  |◄─② confirm 回执(ack) ────────────|  ← 拿到回执才算成功
  |  重试仍失败 → 记本地发送表+告警 → 定时任务补发
```

- Kafka：`acks=all`（Leader 等 ISR 全部副本写入才回执）+ `retries` 重试 + 发送回调判断成败
- RocketMQ：同步发送检查 `SendResult`；更严的场景用事务消息/本地消息表
- 心法：**"send() 不抛异常" ≠ "发送成功"，Broker 回执才算数**

#### 2. 存储段：刷盘 + 复制

| 策略 | 含义 | 一句话 |
| --- | --- | --- |
| 同步刷盘 | 真正写进磁盘才回 ack | 宕机不丢，吞吐低 |
| 异步刷盘 | 写入 PageCache 即回 ack，后台批量刷盘 | 快，宕机可能丢几秒 |
| 同步复制 | 主从都写到才回 ack | 主机坏了也不丢 |
| 异步复制 | 主写完即回 ack，从异步追 | 主挂瞬间可能丢 |

常用组合：**异步刷盘 + 同步复制**（机器坏不丢，断电丢 PageCache 的风险被多机摊薄）；资金级场景才上同步刷盘。

#### 3. 消费段：手动 ack（处理成功才确认）

```
消费者                          Broker
  |◄──① 拉取消息 ────────────────|
  |    ② 执行业务（落库/更新）      |
  |    成功 → ③a ack ───────────►|  消息出队，投递下一条 ✔
  |    失败 → ③b nack/超时不确认 ─►|  重投 → 重试队列 → 超限进死信队列
```

自动 ack 的丢消息风险（时间线）：

```
时刻  消费者                       Broker
 t1   收到 msg，框架自动 ack ─────►  出队，标记消费成功
 t2   还没执行业务，进程崩溃 💥
 → 业务没做、消息没了、Broker 认为你成功了 = 丢！
```

### 二、顺序消费

#### 为什么乱序：模拟两个消费者并行处理同一订单

订单 1001 依次发出「创建」「支付」两条消息，被负载均衡分给两个消费者并行处理：

```
时刻  生产者         Broker队列      消费者A（拿到"支付"）  消费者B（拿到"创建"）
 t1   发"创建" ─────► [创建, 支付]
 t2   发"支付" ─────►      ▲
 t3                   轮询分发：      拿到"支付"           拿到"创建"
 t4                                 执行支付SQL            执行创建SQL
 t5   结果：订单先被置为"已支付"，再被"创建"覆盖 ❌ 状态机错乱
```

根因：**同一业务的多条消息进了不同 queue / 被不同线程并行处理，而 FIFO 只在单个 queue 内成立**。

#### 解法：分区保序

```
生产端：同一业务 key hash 路由到固定 queue
  订单1001：创建/支付/发货 ──hash(1001)──► queue-2（全进同一队列）
  订单2001：创建/支付/发货 ──hash(2001)──► queue-0
  → 全局乱序无所谓，单订单内有序即可

消费端：queue 内单线程，或按 key 分段加锁
  queue-2：[创建]→[支付]→[发货] ──► 单线程顺序处理 ✔
  或：多线程拉取 + 按 msgKey 再哈希到内存队列（同 key 同线程）
```

- Kafka：按 key 自动分区 + 单分区单线程消费
- RocketMQ：`MessageQueueSelector` 按 key 选 queue + 顺序消费模式（队列级锁 + `ConsumeMessageOrderlyService`）
- 代价：**消费并行度 = queue 数**，保序与吞吐是跷跷板

### 三、重复消费：为什么不可避免 + 幂等兜底

at-least-once 语义下，**丢是不会丢了，但重复必然存在**。根源是 ack 可能丢：

```
模拟：业务处理成功了，但 ack 没传回去

时刻  消费者                      Broker
 t1   拉取消息 ─────────────────►  投递（未确认状态）
 t2   业务执行成功（加积分）✅
 t3   发送 ack ────────────────►  ✗ 网络抖动 / ack 后瞬间宕机
 t4                               超时未收到 ack → 判定消费失败 → 重投
 t5   再次收到同一条消息 → 再加一次积分？❌ 重复消费！
```

Broker 区分不了"没处理完"和"处理完了但 ack 丢了"，为了不丢只能宁重复勿漏。

#### 幂等兜底三招（详见幂等篇）

1. **数据库唯一索引**：业务唯一键（订单号+消息类型）建唯一索引，重复插入直接失败
2. **状态机校验**：只允许合法流转（"已支付"再来"支付"直接忽略）
3. **Redis setnx**：以 msgId 为 key，首次 setnx 成功才处理，带过期时间

### 总结

```
分段防丢：生产确认回执 + 存储刷盘复制 + 消费手动 ack
幂等防重：唯一索引 / 状态机 / Redis setnx
分区保序：同 key 同 queue + queue 内单线程
```

## 面试答法

### 30 秒版（可背诵）

> 消息可靠性我按消息生命周期的三段来讲。生产段靠重试加确认：发送失败自动重试，且必须拿到 Broker 的回执才算成功，Kafka 里就是 acks=all。存储段靠刷盘和复制：同步刷盘加同步复制最安全但慢，一般选异步刷盘加同步复制这个中间档。消费段靠手动 ack：业务处理成功才确认，失败重投进重试队列。重复消费避免不了——at least once 语义下，处理完了但 ack 丢了，Broker 只能重投，所以要用幂等兜底：唯一索引、状态机、Redis setnx 三招。顺序消费靠分区保序：同一个业务 key hash 到同一个 queue，queue 内单线程消费，保证单个业务内有序，代价是并行度受 queue 数限制。

### 深入版（编号答题线索）

2. **生产段**：画确认往返图，强调"回执才算成功"，提 Kafka `acks=all` + `retries`、RocketMQ 事务消息/本地消息表
3. **存储段**：同步/异步刷盘 × 同步/异步复制四个组合各一句话，点出常用中间档
4. **消费段**：手动 ack 流程 + 自动 ack 丢消息时间线（很多人答不全的点）
5. **重复问题**：先讲"为什么不可避免"（ack 丢失时间线），再给幂等三招

7. **收尾**：可靠性是木桶，三段任何一段短板都会漏

### 常见追问

- **Kafka acks=all 和 acks=1 区别？** → 1 只要 Leader 写入就回执（Leader 挂且未同步完则丢）；all 等 ISR 全部写入，且要配 `min.insync.replicas>=2` 才有意义
- **重试会造成乱序/重复吗？** → 会。`max.in.flight` 大于 1 时重试可能乱序，严格有序要设为 1；重复靠消费端幂等
- **消费失败一直重投怎么办？** → 重试队列设最大次数，超限进死信队列 + 告警人工处理
- **怎么发现消息真的丢了？** → 生产端本地发送表定时对账 + 消费端业务侧对账（两端各记一笔，比对差额）
- **顺序消费时消费者挂了怎么办？** → queue 重新分配给组内其他消费者，RocketMQ 队列级锁保证同一时间只有一个消费者持有该 queue
- **为什么不做 exactly-once？** → 跨系统做不到真正的 EOS，代价极高；工程共识是 at-least-once + 消费端幂等
