# 列表渲染为什么需要 key

## 题目

> 列表渲染时为什么必须加 key？用 index 做 key 有什么问题？Vue 和 React 在这件事上机制一样吗？key 为什么不能重复？什么情况下用 index 反而没问题？

## 为什么需要 key

diff 的本质问题：**新旧两堆节点，怎么知道"谁还是谁"？**

```
没有 key：只能按位置猜 —— 第 1 个对第 1 个，第 2 个对第 2 个……
有 key：  按身份证认人 —— key=a 的旧节点 配 key=a 的新节点

类比：合影换座位
  无 key = 按座位号认人：换了座位，照片对不上号，每个人都被迫"换脸"
  有 key = 按姓名认人：坐哪儿都行，叫到名字站到对应位置即可
```

key 就是给每个虚拟节点发的**身份证**，让 diff 能跨位置认出"同一个人"，从而**复用真实 DOM**。

## 核心要点

### 1. 无 key（或位置错位）时按位置对比的代价

场景：列表头部插入一项 `[A, B, C] → [X, A, B, C]`，每项渲染成 `<li>{text}</li>`

```
按位置逐一 patch（无 key 的灾难）：

  旧DOM:   [ A ]  [ B ]  [ C ]
  新VNode: [ X ]  [ A ]  [ B ]  [ C ]
            │      │      │      │
            ▼      ▼      ▼      ▼
  位置0:  A→X  ✏️ 改 textContent
  位置1:  B→A  ✏️ 改 textContent
  位置2:  C→B  ✏️ 改 textContent
  位置3:  新增 C  ➕ 创建 DOM 插入

  结果：3 次属性修改 + 1 次创建插入（本应只需 1 次插入）

有 key（X:'x', A:'a', B:'b', C:'c'）：

  旧:   a  b  c          新:  x  a  b  c
              按 key 匹配 → a/b/c 全部【原地复用，0 改动】
                          → 只为 x 创建 1 个新节点插到头部

  结果：1 次创建插入 ✅
```

DOM 操作是浏览器里最贵的一类操作（触发样式重算、布局回流），能复用绝不重建。

### 2. index 做 key：增删/排序时状态串位（重点模拟）

列表项带**输入框**（有内部状态），数据 `[张三, 李四, 王五]`，用户在"李四"的输入框里打了"hello"，然后**删除第 0 项**：

```
删除前（key = index）：
  index0  [张三] <input>""</input>      DOM 节点 D0
  index1  [李四] <input>"hello"</input> DOM 节点 D1   ← 状态在 D1 上
  index2  [王五] <input>""</input>      DOM 节点 D2

删除"张三"后，数据变成 [李四, 王五]，index 重排：
  新 index0 = 李四    → diff 按 key 找 "0" → 复用 D0（张三的节点！）
  新 index1 = 王五    → 复用 D1（李四的节点，里面还留着 "hello"）
  新 index2 = 不存在  → 删除 D2

patch 后：
  [李四] <input>""</input>       ← D0 空输入框，hello 丢了 ❌
  [王五] <input>"hello"</input>  ← 王五"继承"了李四的内容 ❌ 状态串位！

同样操作，key = 唯一 id：
  新列表 key: u2(李四) u3(王五) → 直接找到 D1、D2 原样复用，
  D0 整体删除。李四的 "hello" 完好无损 ✅
```

排序、中间删除同理：index 会整体错位，导致**复用错节点 → 输入框串内容、复选框状态错乱、CSS 过渡动画乱飞、子组件生命周期错乱**。

### 3. Vue2 就地复用策略 & React reconciliation

```
Vue2（无 key 时）：官方就叫 "in-place patch"（就地更新）
  只按 index 一一对比，tag 相同就复用该 DOM 打补丁，不做移动
  → 所以 Vue2 列表必须 key 才能做"基于 key 的最优匹配"

React（reconciliation）：
  <li key={i}> 和 <li>（不写 key）本质等价 —— 不写 key 时 React 隐式用 index
  无 key 头部插入：oldChain A→B→C 对 newChain X→A→B→C 按位置遍历，
    type 相同 tag 相同 → 就地改 props，效果与 Vue2 就地复用一样差
  有稳定 key：遍历时按 key 匹配，识别出"同一个人换了位置" → 移动/复用节点
  → 机制细节不同，但"key 提供身份、避免错位复用"的结论完全一致
```

### 4. key 为什么不能重复

```
Vue3 中间片段 diff：先建 key → index 的 Map
  新列表 [a, b, a] → Map.set('a', 2) 覆盖了 0
  → 同名 key 后者覆盖前者，第一个 a 找不到匹配 → 被卸载重建
React：同一父节点下 key 必须唯一，重复直接控制台警告
  重复 key 让"身份证"失去唯一性 → 匹配歧义 → 状态错乱/节点误删

结论：key 唯一 = 身份证号码不能重号
```

- 也不该用随机数当 key（如 `Math.random()`/`nanoid()`）：每次重渲染 key 全变 → 全部销毁重建，比不加还慢

### 5. 什么时候 index 反而可以用

| 场景 | 用 index 安全吗 | 说明 |
| --- | --- | --- |
| 纯静态列表（不增删、不排序、无内部状态） | ✅ 可以 | 位置即身份，永不变化，省了生成 id 的事 |
| 列表项无状态、只读展示文本 | ⚠️ 勉强 | 错位复用只是改文本，看不出 bug，但仍是坏习惯 |
| 会增删/排序/筛选 | ❌ 禁止 | 状态串位 + 大量无效 patch |
| 列表项含输入框/组件内部状态 | ❌ 禁止 | 见上面模拟 |
| 数据本身没有天然唯一 id | ❌ 别用 index 兜底 | 用业务组合键（如 `name+date`）或生成稳定 id |

## 面试答法

### 30 秒版

> key 是虚拟节点的"身份证"，diff 时靠它判断新旧节点是不是同一个，从而跨位置复用真实 DOM。不加 key 就退化成按位置对比：头部插入一项，后面每一项都被迫改一遍属性，而用唯一 key 只需在头部插入一个新节点。用 index 做 key 最大的坑是状态串位——删除第 0 项后 index 整体重排，李四的输入框会被张三的节点复用，内容就错到王五那行了。Vue2 叫就地复用策略，React 的 reconciliation 不写 key 时默认也是 index，机制细节不同但结论一致。key 必须唯一，否则匹配有歧义。只有纯静态、不增删排序、无内部状态的列表才可以偷懒用 index。

### 深入版（被追问时按这条线展开）

1. **先讲 diff 的本质**：两堆节点要配对，无 key 只能按位置猜，有 key 按身份认
2. **画时间线**：头部插入 `[A,B,C]→[X,A,B,C]`，无 key 3 改 1 增 vs 有 key 只 1 增，强调 DOM 操作昂贵
3. **模拟 index 串位**：带输入框的列表删第 0 项，index 重排 → D0 复用给李四、hello 跑到王五行；换唯一 id 后原样复用
4. **两个框架对照**：Vue2 in-place patch、React 不写 key 默认 index + 链表遍历；Vue3/React 都靠 key 做跨位置匹配
5. **key 唯一性**：Map 覆盖导致误删/重建；随机 key 导致全量重建
6. **收尾**：给出"静态列表可用 index"的边界条件，体现不是死记规则

### 常见追问

- **不写 key 会怎样？** → Vue 控制台警告并按位置就地 patch；React 用 index 当 key，同样有串位风险
- **key 变化会发生什么？** → 旧节点被卸载销毁（连同内部状态和实例），新节点创建——所以 key 要稳定
- **为什么不建议用 random/Date.now 做 key？** → 每次渲染 key 都不同，diff 认为全换了人，整列表销毁重建
- **Vue 的 key 和 React 的 key 原理一样吗？** → 目的一样（标识身份供 diff 复用）；实现不同（Vue3 双端+LIS+key Map，React 单链表遍历+可中断 Fiber）
- **列表项是组件时 index 串位更严重吗？** → 是：组件实例连同内部 state、生命周期、ref 全被错位复用，可能出现"编辑表单串单"级事故
